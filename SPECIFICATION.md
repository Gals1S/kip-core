## 1. Среда эксплуатации

Общие ограничения для всех инструментов учёта КИП:

- Windows 10/11 x64 (целевая ОС).
- UI через браузер (Chromium: Яндекс.Браузер, Chrome, Edge).
- Без прав администратора.
- Без доступа в интернет (все ресурсы локальные).
- Портативность: перенос на другой ПК копированием папки.
- Без CDN и внешних сервисов в рантайме.

### Модель развёртывания

- **Портативные версии, без установки.** Утилиты распространяются как папки, запускаются без инсталляции и без прав администратора.
- **Развёртывание индивидуальное.** Один человек разворачивает утилиты по отдельности (копирует папки на машины пользователей, обновляет их). Пакет — это набор утилит одной версии, а не один установщик.
- **Коллектив — порядка 10 человек.**
- **Единая версия.** У всех пользователей одна версия пакета; использование разных версий исключено.
- **Данные учёта — в общей базе данных, доступ по локальной сети.** Конкретное размещение БД и топология — в SPEC утилиты (определяет управляющий чат БД).
- **Одновременная работа — ориентир до 10 пользователей** (не жёсткий лимит).
- **Обновление — централизованное.** Один человек заменяет папки утилит; миграция БД выполняется при обновлении.
- **Файлы обмена (CSV) хранятся локально** на машинах пользователей, не в БД.

Конкретная архитектура (локальный Flask, клиент-сервер, топология сети) — в SPEC соответствующей утилиты.

### Среда и контракт — в чём разница

**Среда** (этот раздел) — условия, в которых работают утилиты.
Изменение среды (например, Windows 12) требует адаптации каждой
утилиты, но **не меняет контракт** между ними.

**Контракт** — модель данных (раздел 2 и архитектурный документ)
и формат обмена (раздел 3). Изменение контракта требует осознанного
обновления утилит; порядок присвоения версии — в `handover.md`,
раздел 7.

## 2. Модель данных

> **Точка входа.** Полное описание модели — в архитектурном документе
> `CORE-ARCH-data-model.md`. Настоящий раздел — перечень сущностей
> и ключевые принципы. При расхождении SPEC с архитектурным
> документом — прав архитектурный документ; при расхождении
> архитектурного документа с ADR — прав ADR.

### Состав экосистемы

| Утилита | Функция |
|---|---|
| **Reader** | Извлечение данных из принципиальных схем в табличный файл (CSV) |
| **Register** | Хранение базы данных проекта, проверки данных, табличные документы |
| **Generator** | Формирование векторных документов (DWG) из данных Register |

Данные обрабатываются тремя утилитами; обмен между ними — только
табличными файлами. Все данные проекта хранятся в базе Register.
Распределение функций по утилитам определено в Core; утилита
не может переопределить свои границы. Поток данных и участие
человека на каждом шаге — в `CORE-ARCH-data-flow.md`.

### Сущности

| Сущность | Что это | Источник |
|---|---|---|
| **Проект** | Совокупность приборов, кабелей, помещений, документов | — |
| **Справочники** | Стандартизованные значения (IP, Ex, материалы, электрические реализации, уровни уставок, системы управления, помещения, типы монтажа и др.) | ADR-002, ADR-004, ADR-006, ADR-008 |
| **Модель прибора** | Справочная запись: название, тип, производитель | ADR-002 |
| **Проектный стандарт** | Состав сигналов и значения по умолчанию для модели на проекте | ADR-002 |
| **Прибор** | Единица оборудования КИПиА: позиция, характеристики, параметры процесса, статус закупки, документы | ADR-002 |
| **Сигнал** | Часть прибора: позиция, электрическая реализация, система управления, уставки | ADR-002, ADR-006 |
| **Помещение** | Номер, наименование, палуба, строительный район | ADR-004 |
| **Монтажная группа** | Данные прибора о монтаже: помещение, тип монтажа, ссылка на чертёж | ADR-004, ADR-008 |
| **Документ** | Тип, номер, ревизия, наименование; связывается с приборами | ADR-002 |
| **Физический сегмент** | Участок физического кабеля: индекс, два адреса, привязка к сигналам, физические атрибуты | ADR-007 |
| **Клеммная коробка, шкаф, панель** | Точки подключения; адреса физических сегментов | ADR-007 |

Все данные проекта хранятся в базе Register. Выходные документы —
представление модели: табличные формирует Register, векторные —
Generator (см. `CORE-ARCH-data-flow.md`).

**Логический кабель в модели отсутствует** (ADR-007): подсистема —
поле сигнала, индекс — принадлежность физического сегмента.

### Ключевые принципы

- **Логические и физические данные.** Логические данные (что, куда,
  зачем) ведутся при учёте; физическая детализация (сегменты,
  коробки, шкафы, марки, обратные жилы) заполняется при подготовке
  вывода. И то и другое хранится в Register; логические данные
  при подготовке вывода не переписываются (ADR-011).
- **Наследование и переопределение.** Прибор наследует значения
  из проектного стандарта; инженер может переопределить любое
  значение для конкретного прибора. Переопределение видимо
  и отслеживаемо (ADR-002, ADR-006). Диапазон измерений — исключение:
  всегда вводится вручную, не наследуется (ADR-006).
- **Связь «сигнал ↔ физический сегмент» — many-to-many.**
  Один сигнал может проходить по нескольким сегментам; один сегмент
  может нести несколько сигналов. Это выражает разделение и объединение
  кабелей в коробках (ADR-007).
- **Справочники vs свободный ввод.** Стандартизованные коды —
  в справочниках; вариативные значения — свободный ввод или
  «справочник + уточнение» (ADR-002). Число жил — атрибут справочника
  электрических реализаций, не поле сигнала (ADR-006).

## 3. Форматы обмена

Обмен между инструментами — только через табличные файлы.

- **Формат:** CSV.
- **Кодировка:** `utf-8-sig` (BOM для совместимости с Excel).
- **Разделитель:** `;`.
- **Структура:** одна строка — одна запись; первая строка — заголовки
  колонок.
- **Состав колонок** — определяется моделью данных (архитектурный
  документ и ADR) и источником (схема, проект, инструмент). Маппинг
  колонок на модель — в утилите-приёмнике, не в Core. Изменение
  состава — изменение контракта; порядок присвоения версии — в
  `handover.md`, раздел 7.
- **Версионирование формата:** формат обмена версионируется вместе
  с контрактом (см. `handover.md`, раздел 7).

Внутренние форматы инструментов (ручной ввод, выгрузка в Excel для
пользователя) — не входят в обмен и описываются в SPEC утилиты.

## 4. Глоссарий

> Термины, одинаковые для всех инструментов экосистемы. Развёрнутые
> определения — в архитектурных документах `CORE-ARCH-data-model.md`
> и `CORE-ARCH-data-flow.md` и ADR модели данных.

### Утилиты и данные

| Термин | Значение |
|---|---|
| **Утилита** | Инструмент экосистемы KIP, решающий одну задачу. Синоним — инструмент. Три утилиты: Reader, Register, Generator |
| **Reader** | Утилита извлечения данных из принципиальных схем в табличный файл (CSV) |
| **Register** | Утилита учёта: хранит все данные проекта, проверяет их, выдаёт табличные документы |
| **Generator** | Утилита вывода: строит векторные документы (DWG) из данных Register |
| **Логические данные** | Что, куда, зачем: приборы, сигналы, помещения, документы, справочники. Ведутся при учёте |
| **Физические данные** | Марка, размеры, монтаж, сегменты, коробки, шкафы. Заполняются при подготовке вывода |

### Прибор и сигнал

| Термин | Значение |
|---|---|
| **Прибор** | Единица оборудования КИПиА (датчик, клапан, преобразователь). Имеет позицию (`tag`), тип, модель |
| **Позиция** (`tag`) | Уникальное обозначение прибора в рамках проекта |
| **Модель прибора** | Справочная запись: название, тип, производитель |
| **Проектный стандарт** | Состав сигналов и значения по умолчанию для модели на проекте |
| **Переопределение** | Значение на уровне прибора/сигнала, отличающееся от проектного стандарта |
| **Диапазон измерений** | Поле прибора; вводится вручную, не наследуется из стандарта; необязательное (у реле, сигнализаторов — пустое) |
| **Сигнал** | Часть прибора: позиция (`AI1`, `AO1`, `DI1`…), электрическая реализация, система управления, уставки |
| **Позиция сигнала** | Обозначение сигнала внутри прибора (`AI1`, `DI2`…); уникальна в рамках прибора; задаётся составом |
| **Электрическая реализация** | Тип электрического сигнала из справочника (`I420`, `HART`, `DRY_NO`, `NAMUR`, `RTD_3W`…). У записи справочника — ровно одно число жил |
| **Число жил** | Атрибут записи справочника «Электрические реализации сигналов», не поле сигнала. Варианты (RTD 3/4 провода) — отдельные записи |
| **Уставка** | Пороговое значение сигнала: уровень (`HHH`…`LLL`) + число |
| **Система управления (подсистема)** | РСУ, ПАЗ, ПЛК — система, к которой относится сигнал. Поле сигнала; всегда вводится, не наследуется |

### Кабельная модель

| Термин | Значение |
|---|---|
| **Физический сегмент** | Участок физического кабеля. Атрибуты: индекс, **два адреса**, привязка к сигналам, физические атрибуты (марка, длина, экран и т.п.) |
| **Два адреса** | Концы физического сегмента. Каждый адрес — прибор, клеммная коробка или шкаф/панель. Ровно два адреса на сегмент |
| **Связь «сигнал ↔ сегмент»** | Many-to-many: один сигнал может проходить по нескольким сегментам; один сегмент может нести несколько сигналов |
| **Занятость жил** | Вычисляется при подготовке вывода: сумма числа жил по связанным сигналам |
| **Обратная жила** | Общая обратная жила дискретных сигналов; атрибут физического сегмента, не учётной модели |
| **Точка подключения** | Прибор, клеммная коробка, шкаф или панель — объект, который может быть адресом физического сегмента |
| **Разделение кабеля** | Ситуация, когда общий участок до коробки несёт сигналы разных подсистем, после коробки — два сегмента к разным шкафам |
| **Объединение кабеля** | Ситуация, когда кабели от разных приборов сходятся в коробке и идут к шкафу одним сегментом |

### Помещение и монтаж

| Термин | Значение |
|---|---|
| **Помещение** | Место установки прибора или шкафа: номер, наименование, палуба, строительный район |
| **Палуба** | Атрибут помещения (текст: «верхняя палуба», «средняя палуба»); вводится один раз при создании помещения |
| **Строительный район** | Атрибут помещения (текст); вводится один раз при создании помещения |
| **Монтажная группа** | Данные прибора о монтаже: помещение (ссылка на номер), тип монтажа, ссылка на чертёж |
| **Тип монтажа** | Значение из справочника (фланец, кронштейн, стойка, трубопровод, стена, встроенный); состав — данные проекта |

### Общие

| Термин | Значение |
|---|---|
| **Проект** | Совокупность приборов, кабелей, помещений, документов |
| **Справочник** | Стандартизованные значения; отдельный ссылочный слой, не копируется в модель |
| **Loop** | Функциональная группировка «зачем» (петля регулирования). **В модель не вводится**; триггеры пересмотра — ADR-007 |

Термины «проектный стандарт», «переопределение», «физический сегмент», «два адреса» раскрыты в ADR модели данных и архитектурных документах. Глоссарий — краткая шпаргалка, не замена ADR.

# CORE-ARCH: Поток данных в экосистеме KIP

**Проект:** KIP_Core
**Класс:** B (живой) — правится после утверждения новых ADR, от которых зависит
**Источник:** дистилляция решений из CORE-ADR-007, CORE-ADR-010, CORE-ADR-011
**Связанные документы:** `decisions/CORE-ADR-REGISTRY.md` (реестр ADR), `SPECIFICATION.md` (контракт), `CORE-ARCH-data-model.md` (модель данных)

> Документ содержит **только решения** — без обоснований, последствий и отклонённых вариантов.
> Воспринимается как правило, пока не изменён новым ADR. При сомнениях — обращение к ADR.

---

## 1. Утилиты и границы

Экосистема состоит из трёх утилит. Границы не пересекаются.

| Утилита | Функция | Что не делает |
|---|---|---|
| **Reader** | Извлекает данные из принципиальных схем в табличный файл (CSV) | Не хранит данные, не дополняет их, не проверяет по справочникам |
| **Register** | Хранит базу данных проекта; проверяет данные; выдаёт табличные документы | Не строит векторные документы |
| **Generator** | Строит векторные документы (DWG) из данных Register | Не хранит данные, не проверяет их |

Обмен между утилитами — только табличными файлами. Прямого API,
общего чтения базы, встраивания одной утилиты в другую нет.

## 2. Поток данных

### 2.1. Reader → Register

Reader читает принципиальную схему и формирует CSV. Извлекается всё,
что можно привязать к условному изображению символа, вместе
с индексом прибора. Состав колонок определяется при разработке
Reader и не фиксируется.

Обязательное требование к файлу — колонка `tag`. Без индекса
прибора данные не к чему привязать.

### 2.2. Приём в Register

Register принимает CSV:

1. Показывает, как собрался принять данные: что распознал сам,
   что нет. Нераспознанные колонки — пустые поля для ручного
   сопоставления.
2. Человек подтверждает сопоставление или правит его.
3. Нераспознанные колонки игнорируются. Сырой CSV сохраняется —
   потери нет.

Запись в базе создаётся, если есть `tag`; остальные поля могут быть
пустыми. Дополнение — из CSV, вручную или копированием из табличного
редактора.

### 2.3. Register → Generator

Данные для вывода выгружаются **непосредственно перед выводом**
и передаются табличным файлом. Generator строит векторные документы;
задача обратна Reader.

### 2.4. Generator → Register (обратный поток)

Сформированный документ не является учётной записью, пока человек
не инициирует его выпуск. После выпуска запись документа (тип,
номер, ревизия, наименование) возвращается в Register табличным
файлом и принимается как любой импорт — с показом сопоставления
и подтверждением человека. Запись связывается с прибором, заполняя
поле «документы».

Если Generator не смог что-то построить, он сообщает об этом
человеку (отчёт или лог). В Register этот отчёт не возвращается.

## 3. Участие человека

Человек инициирует каждый поток и принимает каждое решение.

| Шаг | Что делает человек |
|---|---|
| Чтение CSV | Инициирует чтение |
| Приём в Register | Подтверждает сопоставление колонок |
| Повторный импорт | Подтверждает обновление записей (по `tag`); подтверждение — один раз за цикл приёма |
| Поля, которых нет в новом файле | Решает при подтверждении; по умолчанию сохраняется существующее значение |
| Генерация физических данных | Вводит параметры, которых нет в правилах (например, параметры коробок) |
| Выгрузка для вывода | Инициирует выгрузку |
| Выпуск документа | Инициирует выпуск |
| Проверки целостности | Запускает проверки по запросу |

## 4. Физические данные

Физические данные — физические сегменты, клеммные коробки, шкафы,
марки, длина, экран, броня — хранятся в базе Register.

Три пути заполнения (модель поддерживает все):

1. **Генерация по правилам** — основной путь. Правила настраиваются
   как данные проекта и могут отличаться от проекта к проекту.
   Коробки могут генерироваться по правилам; параметры коробок
   вводит человек; кабели собираются по заполнению коробок.
2. **Ручной ввод.**
3. **Импорт** — приём как обычного табличного файла.

Логические данные (приборы, сигналы, помещения, документы) ведутся
при ведении учёта. Физическая детализация заполняется при подготовке
вывода. Логические данные при подготовке вывода не переписываются
(ADR-011).

## 5. Проверки данных

Проверки — функция Register:

- при вводе и импорте: несоответствие справочнику, дубликаты `tag`,
  отсутствие обязательных связей;
- по запросу: целостность базы (висячие ссылки, противоречия между
  связанными данными).

При несоответствии справочнику запись создаётся без значения поля;
пользователь информируется (отчёт после приёма или лог на экране).

## 6. Взаимодействие и развёртывание

| Утилита | Где работает | С чем связана |
|---|---|---|
| **Register** | С общей базой данных по локальной сети; ориентир — до 10 пользователей | Единственная утилита, работающая с общей БД |
| **Reader** | Локально на машине пользователя | Обменивается с Register файлами |
| **Generator** | Локально на машине пользователя | Получает файл от Register; при выпуске документа возвращает файл в Register |

Generator локальный и автономный: при наличии файла документ можно
сформировать, даже когда Register выключен.

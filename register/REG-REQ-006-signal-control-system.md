# Запрос в Core: `control_system_id` сигнала при пересоздании по новому стандарту

**Файл:** `REG-REQ-006-signal-control-system.md`
**Проект:** KIP_Register
**От кого:** Управляющий чат утилиты Register
**Кому:** Управляющий чат Core
**Дата:** 15.11.2026
**Связанное задание:** `CORE-TASK-006-signals-crud.md`

---

## Что нужно

Решить, что делать с `signal.control_system_id` при автоматическом пересоздании сигналов по шаблону нового стандарта (смена `project_standard_id` прибора).

Сейчас: `control_system_id` — `NOT NULL` (REG-ARCH-db.md, раздел 6), по модели Core «всегда вводится, не наследуется» (CORE-ARCH-data-model.md, раздел 3). В `project_standard_signal` поля нет — наследовать неоткуда.

## Зачем

`CORE-TASK-006` требует: при смене `project_standard_id` старые сигналы удаляются, новые создаются по шаблону нового стандарта. Но `control_system_id` при автоматическом создании **взять неоткуда**:
- в шаблоне стандарта его нет (по модели);
- у старого сигнала — только если позиция совпадает (у нового стандарта может быть другой состав);
- пользователь не может задать его «до» создания — сигналов ещё нет.

## Что будет, если не решить

- Код не может выполнить требование задания без скрытого решения (дефолт, пропуск, ошибка) — любое из них искажает модель.
- При смене стандарта с другим составом сигналов часть позиций останется без `control_system` — либо ошибка, либо неполный состав.
- Скрытый дефолт всплывёт при эксплуатации: «почему у новых сигналов РСУ, хотя я не выбирал?».

## Варианты

**A. Автосоздание при смене стандарта не делаем.** При `PUT` прибора старые сигналы удаляются, новые **не создаются**; пользователь создаёт вручную. `POST` прибора — сигналы не создаются.
- Плюсы: структура не меняется, модель не нарушается.
- Минусы: **противоречит заданию** («новые создаются по шаблону»); пользователь после смены модели заново вводит весь состав и `control_system` — много ручной работы.

**B. Пересоздание с переносом `control_system_id` по совпадающим позициям.**
- Плюсы: для совпадающих позиций — без потерь.
- Минусы: для **новых** позиций (которых не было в старом стандарте) `control_system_id` неоткуда взять → ошибка (смена не проходит), пропуск (неполный состав), или дефолт (скатывается в C). Не решает задачу полностью.

**C. Пересоздание с дефолтным `control_system_id`.** Например, первая запись `ref_control_system` (РСУ).
- Плюсы: смена стандарта проходит, состав полный.
- Минусы: **скрытое решение**, которого нет в модели. «Всегда вводится» превращается в «иногда подставляется РСУ». Пользователь может не заметить и оставить неверную подсистему — риск для ПАЗ-сигналов.

**D. Изменение модели: `control_system_id` — nullable.** При пересоздании по шаблону — `NULL`; пользователь заполняет вручную.
- Плюсы: честно отражает «неоткуда взять»; не скрывает дефолт; пользователь видит незаполненные сигналы и заполняет; состав полный.
- Минусы: **изменение контракта Core** (nullable); нужна миграция; UI/проверки целостности должны учитывать «сигнал без подсистемы»; для I/O-листов и кабельных журналов `control_system` важен — незаполненный сигнал нельзя выпускать.

**E. Иное** — если Core видит решение, не перечисленное.

## Рекомендация Register

**D** — `control_system_id` nullable, при пересоздании `NULL`, заполняется вручную.

Причины:
- A нарушает задание;
- B неполно (новые позиции);
- C вводит скрытый дефолт, риск для ПАЗ;
- D честно фиксирует состояние «сигнал создан по шаблону, подсистема не назначена» и заставляет пользователя её указать — что соответствует «всегда вводится вручную» (ввод откладывается, но не подменяется).

**Условие D:** нужен признак «сигнал без подсистемы» в проверках целостности Register и в будущих выгрузках (I/O-лист, кабельный журнал) — незаполненный `control_system_id` должен блокировать выгрузку или помечаться. Это отдельная задача, не часть `CORE-TASK-006`.

## Влияние

- **Модель Core:** `signal.control_system_id` — nullable (изменение контракта).
- **Структура БД:** миграция Alembic (одна колонка).
- **`REG-ARCH-db.md`:** раздел 6, `control_system_id` — nullable.
- **`CORE-TASK-006`:** пересоздание сигналов с `NULL`; CRUD сигналов принимает `control_system_id` при ручном создании/обновлении.
- **Независимое тестирование:** контракт сигналов дополнить — «при пересоздании `control_system_id = null`».
- **Будущее:** проверка «сигнал без подсистемы» при выгрузке — отдельная задача.

## Если D неприемлемо

Просим указать вариант (A/B/C/E) — Register реализует согласно решению. При A задание `CORE-TASK-006` в части «новые создаются по шаблону» требует корректировки (противоречие).

# Запрос в Core: аудит справочников Register

**Файл:** `REG-REQ-001-refs-audit.md`
**Проект:** KIP_Register
**От кого:** Управляющий чат утилиты Register
**Кому:** Управляющий чат Core
**Дата:** 13.11.2026
**Связанное задание:** `CORE-TASK-003-refs-crud.md`

---

## Что нужно

Добавить в модель данных Core поля аудита для 18 справочников Register: `created_by`, `created_at`, `updated_by`, `updated_at` — по аналогии с `device`, `signal`, `segment`.

Сейчас аудит есть только у приборов, сигналов и сегментов. Справочники (`ref_device_type`, `ref_manufacturer`, `ref_device_model`, `ref_electrical_implementation`, `ref_setpoint_level`, `ref_ip_rating`, `ref_ex_marking`, `ref_climate_rating`, `ref_wetted_material`, `ref_body_material`, `ref_process_connection_type`, `ref_cable_entry_type`, `ref_unit`, `ref_document`, `ref_purchase_status`, `ref_control_system`, `ref_room`, `ref_mounting_type`) — без аудита.

Это расширение модели Core v1.1, которого сейчас нет.

## Зачем

Справочники — фундамент проекта: на них ссылаются приборы и сигналы. Изменение записи справочника (переименование производителя, изменение числа жил электрической реализации, кода IP) влияет на все связанные приборы и сигналы. В многопользовательском режиме (до 10 пользователей) нужно знать, кто и когда изменил запись.

Сейчас аудит есть у `device`, `signal`, `segment`, но не у справочников — это разрыв в отслеживаемости: изменение справочника не оставляет следа.

## Что будет, если не изменить

- Изменения справочников не отслеживаются: нельзя узнать, кто переименовал модель или изменил код IP.
- При ошибочном изменении нельзя восстановить автора и время.
- Для проекта КИПиА, где справочники — проектные данные, это риск: ошибка в справочнике распространяется на все связанные приборы.

## Варианты решения

**A. Поля аудита во всех 18 справочниках** (`created_by`, `created_at`, `updated_by`, `updated_at`).
- Плюсы: единообразие с `device`/`signal`/`segment` (те же поля, та же логика — минимум кода), удобство пользователя (видно, кто и когда менял), минимальные изменения структуры (4 колонки на таблицу).
- Минусы: 72 новые колонки, изменения во всех 18 таблицах; история — только последнее изменение (не полная).

**B. Поля аудита только в «проектных» справочниках** (`ref_room`, `ref_document`, `ref_mounting_type`, `ref_purchase_status`, `ref_control_system`), не в «стандартизованных кодах» (`ref_ip_rating`, `ref_ex_marking`, `ref_climate_rating`, `ref_setpoint_level`).
- Плюсы: меньше изменений, аудит там, где данные проекта.
- Минусы: граница размыта, модель её не задаёт; непоследовательно.

**C. Универсальный журнал изменений** `ref_change_log` (`table_name`, `record_id`, `field_name`, `old_value`, `new_value`, `changed_by`, `changed_at`).
- Плюсы: одна таблица, полная история.
- Минусы: слабее типизация, сложнее читать и фильтровать, нужна обвязка на все 18 таблиц.

**D. Без аудита** — оставить как есть.
- Плюсы: ничего не меняется.
- Минусы: изменения не отслеживаются.

## Рекомендация

**A** — поля аудита во всех 18 справочниках. Причины: единообразие с `device`/`signal`/`segment` (те же поля, та же логика — минимум кода), удобство пользователя, минимальные изменения структуры. Если позже понадобится полная история — отдельный ADR по образцу `REG-ADR-002` (гибрид: поля в строке + таблица истории).

## Последствия для Register

- Изменение структуры БД: новая миграция Alembic (вне `CORE-TASK-003` — задание запрещает менять структуру).
- Обновление `REG-ARCH-db.md` (раздел 3).
- Обновление CRUD-кода: заполнение полей аудита.

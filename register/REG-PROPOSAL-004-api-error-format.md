# Предложение в Core: доработка формата ошибок API Register

**Файл:** `REG-PROPOSAL-004-api-error-format.md`
**Проект:** KIP_Register
**От кого:** Управляющий чат утилиты Register
**Кому:** Управляющий чат Core
**Дата:** 14.11.2026
**Связанное задание:** `CORE-TASK-004-devices-crud.md` (принято)
**Основание:** `REG-REPORT-002`, раздел 2 — 5 существенных пробелов контракта API

---

## 1. Контекст

Независимое тестирование `CORE-TASK-004` зафиксировало 21 пробел контрактов API (`REG-CONTRACT-refs.md`, `REG-CONTRACT-devices.md`). Арбитр принял решения по 5 существенным. Это **изменение контрактов утилиты** (формат JSON-ошибок), не модели данных Core: `SPECIFICATION.md`, `CORE-ARCH-data-model.md`, структура БД не меняются. Другие утилиты формат не видят (обмен — CSV, не HTTP).

Решения приняты арбитром 14.11.2026. Предлагается учесть их в следующем задании Core для Register.

## 2. Пять пунктов

**П.1 — strip-нормализация строк. Решение: да, все строковые значения очищаются от пробелов по краям до валидации и записи.**
Статус: **уже реализовано** в `_validate_value` (refs и devices). Код не меняется. Требуется только зафиксировать в контрактах (сейчас — пробел).

**П.2 — запрет системных имён ограничений БД в API. Решение: заменить `details.constraint` на стандартизированный формат `code`/`message`.**
Пример: вместо `{"constraint": "ck_device_range_max_ge_min"}` → `{"code": "range_error", "message": "..."}`.
Затрагивает: `_translate_integrity` в `refs/service.py` и `devices/service.py`; маппинг «имя ограничения → код»; контракты обоих API; наши тесты (проверяют `constraint.startswith("ck_")`); независимые тесты (проверяют точное имя).

**П.3 — `ref` для `project_standard_id` → kebab-case. Решение: `"project-standard"`, как у остальных справочников.**
Затрагивает: `FieldSpec` в `devices/service.py` (одна строка); контракт приборов; наши и независимые тесты (проверяют `"project_standard"`).

**П.4 — race-ветка 409: формат как у штатной проверки. Решение: `unique` + `values`, без `constraint`, без `operation`.**
Сейчас race-ветка возвращает `{"constraint": "uq_device_tag"}`; штатная — `{"unique": ["tag"], "values": {...}}`. Привести к единому виду: `values` брать из `cleaned`, группу — по маппингу `constraint → group`.
Затрагивает: `_translate_integrity` (нужен доступ к `cleaned`); контракты; тесты.

**П.5 — `device_document` RESTRICT при DELETE. Решение: оставить как есть, реализовать при создании CRUD документов.**
Код не меняется. Зафиксировать в отчёте как отложенное.

**Важно:** изменение формата ошибок — **breaking** для существующих независимых тестов (`test_refs_api.py`, `test_devices_api.py` проверяют `constraint` и `ref == "project_standard"`). После правки кода они упадут; нужен новый цикл независимого тестирования под обновлённые контракты (задание тестировщику + ретест). Это отдельная итерация, не «правка по ходу».

## 4. Предложение по оформлению

Просим учесть в следующем задании Core для Register (`CORE-TASK-005` или доработка `CORE-TASK-004`) как отдельный блок «Унификация формата ошибок API»:

- **Объём:** пункты 1–4 (п.1 — только контракт, п.5 — отложен).
- **Критерии готовности:** код, обновлённые контракты, обновлённые наши тесты, новый цикл независимого тестирования, отчёт.
- **Порядок:** план → код → контракты → наши тесты → задание тестировщику → ретест → отчёт.

`CORE-TASK-004` при этом остаётся принятым на текущем формате (370 passed, независимые зелёные) — честная фиксация состояния до изменения.

## 5. Рекомендация

Оформить отдельным заданием (или отдельным блоком следующего задания). Причины: breaking для независимых тестов, нужен полный цикл; смешивать с уже принятым 004 не стоит — приёмка состоялась на старом формате; объём тянет на отдельную итерацию.

Модель данных Core не затрагивается; запрос на изменение контракта экосистемы не требуется.

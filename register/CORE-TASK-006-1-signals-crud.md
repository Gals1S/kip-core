## Зачем

Сигналы — основа для I/O-листов. Мы также должны обеспечить гибкость работы инженеров (возможность создавать приборы-черновики и безопасно менять стандарты).

## Внимание: изменения в модели Core (CORE-ADR-014)

Прочитай `CORE-ADR-014`. Модель изменилась:
1. **`device.project_standard_id` теперь может быть NULL.** Прибор можно создать только с `tag` (и другими необязательными полями), а стандарт назначить позже.
2. **`signal.control_system_id` теперь может быть NULL.** При автосоздании сигналов его не нужно заполнять.
3. **Сигналы не создаются и не удаляются вручную (нет POST/DELETE).** Они жестко привязаны к проектному стандарту.

## Ключевые сложности и логика

1. **CRUD Приборов (обновление):**
   - `POST /api/devices` — разреши создавать прибор с `project_standard_id = NULL` (пользователь заполняет только `tag`). В этом случае сигналы для прибора не создаются.
   - `PUT /api/devices/<id>` — если ты назначаешь стандарт (меняешь `NULL` на ID, или меняешь один ID на другой), система должна автоматически пересоздать сигналы по шаблону нового стандарта.
2. **Логика Сигналов (GET и PUT):**
   - `GET /api/devices/<id>/signals` — вернуть список сигналов прибора (с учетом наследования от `project_standard_signal`). Если у прибора нет стандарта, вернуть пустой список.
   - `PUT /api/signals/<id>` — обновить конкретный сигнал (изменить `control_system_id`, электрическую реализацию, уставки). Создавать новые или удалять сигналы через этот эндпоинт нельзя.
   - Поле `control_system_id` принимает `NULL` или ID системы.

## Режим работы

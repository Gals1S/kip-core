## Что сделать

Реализовать серверную логику (API и работу с БД) для управления Сигналами (создание, чтение, обновление, удаление). 
Также обновить логику обновления (PUT) для Приборов, чтобы при смене проектного стандарта (модели) корректно обрабатывались связанные сигналы.
Интерфейс пользователя (UI) не делать.

## Зачем

Сигналы — это основа для формирования I/O-листов и будущих кабельных журналов. Без них система бесполезна. Кроме того, нужно обеспечить целостность данных при смене модели прибора.

## Контекст (Lean-загрузка)

Для выполнения задачи запроси у арбитра:
1. `REG-ARCH-db.md` (раздел 6 — Сигнал).
2. `CORE-ARCH-data-model.md` (раздел 3 — Сигнал).
3. `CORE-ARCH-data-model.md` (раздел 2 — подраздел «Смена модели прибора»).

## Ключевые сложности

1. **Состав сигналов.** В отличие от прибора, сигнал не может быть создан произвольно. Его позиция (`AI1`, `DI1` и т.д.) должна соответствовать составу, заданному в `project_standard_signal` для текущего стандарта прибора. Если сигнала нет в стандарте — это ошибка.
2. **Наследование.** Сигнал наследует значения из `project_standard_signal`, если они не переопределены в самом сигнале (поля `electrical_implementation_id`, `setpoint_level_id`, `setpoint_value`).
3. **Система управления.** Поле `control_system_id` всегда вводится вручную для каждого сигнала (не наследуется), так как это требование модели Core.
4. **Смена стандарта прибора.** При выполнении `PUT /api/devices/<id>` и изменении `project_standard_id` (или при смене модели), старые сигналы должны быть пересозданы по новому стандарту. Переопределения сигналов (электрическая реализация, уставки) при этом сбрасываются (согласно модели Core).

## Режим работы

1. **Включи режим строгого критика.** Логика смены стандарта и каскадного обновления сигналов — сложное место. Тщательно проверь все сценарии (что если у старого стандарта были сигналы, а у нового другая конфигурация?). Не используй заглушки.
2. **Проактивность:** Если текущая схема БД не позволяет корректно пересоздать сигналы или реализовать наследование — **остановись** и сформулируй Запрос в Core.

## Критерии готовности

1. Реализован CRUD для `signal`.
2. Реализовано наследование от `project_standard_signal` (возврат эффективных значений и `overrides`).
3. Обновлен `PUT /api/devices/<id>`: при смене `project_standard_id` старые сигналы удаляются, новые создаются по шаблону нового стандарта.
4. Написаны Unit-тесты (включая сценарий смены стандарта).
5. Проведено независимое Black-box тестирование (Level 2).
6. Обновлен CHANGELOG.
7. Сделан коммит.

## Ограничения

- Не менять структуру БД.
- Историю переопределений (override_history) пока не делаем (это будет отдельное задание).

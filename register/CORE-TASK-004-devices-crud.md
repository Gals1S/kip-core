## Что сделать

Реализовать серверную логику (API и работу с БД) для управления Приборами (создание, чтение, обновление, удаление).

Изучи их. Если для работы понадобятся другие файлы — запроси их.

## Ключевая сложность: Наследование и переопределения

В модели данных Core у прибора есть наследование от `project_standard`. 
- Если поле в `device` равно `NULL`, это означает «наследовать из стандарта».
- Если поле заполнено — это переопределение.
Твоя задача при чтении (GET) возвращать не только то, что лежит в `device`, но и вычислять итоговые значения (наследованные + переопределенные), чтобы фронтенд получал готовые данные. 
При обновлении (PUT/PATCH) нужно сохранять только переопределения (или сбрасывать их в NULL).

## Режим работы (Строгий критик и Проактивность)

1. **Включи режим строгого критика.** Логика наследования — сложное место, где легко ошибиться. Тщательно проверь все сценарии (что если стандарт пуст? что если переопределение удаляют?). Не используй «заглушки».
2. **Проактивность:** Если ты в процессе проектирования поймешь, что текущая модель данных или архитектура БД не позволяют реализовать логику наследования корректно — **остановись**. Не делай костылей. Сформулируй официальный **Запрос в Core** по шаблону и отдай его арбитру.

## Критерии готовности

1. Реализован CRUD для `device` (с учетом связи с `project_standard`).
2. Реализована логика слияния значений (наследование + переопределение) при чтении.
3. Написаны Unit-тесты (включая граничные случаи с NULL).
4. Проведено независимое Black-box тестирование (Level 2), найденные ошибки исправлены.
5. Сделан коммит.

## Ограничения

- Не писать интерфейс (UI).
- Не менять структуру БД (она уже готова).
- Не менять модель данных Core (только через Запрос в Core).

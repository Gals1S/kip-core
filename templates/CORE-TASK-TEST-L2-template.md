# Задание: Написание тестов (Уровень 2: Контрактное / Black-box)

**Файл:** `CORE-TASK-TEST-L2-NNN-<тема>.md` (или `<UTIL>-TASK-TEST-L2-...`)  
**Проект:** KIP_Core (или префикс утилиты, например, REG-)  
**От кого:** Управляющий чат (Core или утилиты)  
**Кому:** Независимый чат-тестировщик  
**Дата:** ДД.ММ.ГГГГ  

> *Правило для чата-тестировщика: Ты работаешь строго по методу черного ящика (Black-box). Ты не видишь код реализации и не должен его запрашивать. Твоя задача — проверить, насколько поведение системы соответствует заявленному контракту. Это защита от «проблемы оракула», когда разработчик проверяет сам себя.*

## 0. Режим работы
Включи режим строгого критика. Твоя цель — найти несоответствия контракту, а не подтвердить, что код «как-то работает». Тщательно проверяй граничные случаи. Не срезай углы и не пиши тесты «для галочки».

## 1. Что сделать
Написать автоматические тесты (например, на Python с использованием `pytest`) для функций/эндпоинтов, описанных в разделе «Карта контрактов».

## 2. Карта контрактов (Входные данные)
*Арбитр прикладывает к этому заданию спецификацию поведения. Это единственный источник правды для тестов.*
<Вставьте сюда карту контрактов: список функций/методов/эндпоинтов с их сигнатурами, описанием ожидаемого поведения (docstring) и списком возможных исключений/кодов ошибок. Без внутренней реализации.>

## 3. Что покрыть тестами
- **Happy path (Успешные сценарии):** Проверка базовой логики, описанной в контракте. Передача корректных данных и проверка ожидаемого результата.
- **Граничные значения (Edge cases):** Проверка нулей, пустых строк, максимальных/минимальных чисел, пустых коллекций.
- **Негативные сценарии (Ошибки):** Передача неверных типов данных или значений, которые должны вызывать конкретные исключения или коды ошибок (строго согласно контракту).
- **Проверка инвариантов:** Если контракт обещает, что функция не меняет входные данные (иммутабельность) или возвращает данные в определенном формате (например, ISO 8601 UTC) — это нужно проверить.

## 4. Ограничения
- **Запрещено** запрашивать или пытаться угадать код реализации.
- **Запрещено** тестировать внутренние (приватные) методы, которые не указаны в карте контрактов.
- Если контракт неоднозначен и ты не понимаешь, как должна вести себя система (например, какое именно исключение бросить при ошибке X) — **не пиши тест наугад**. Задай уточняющие вопросы, если ответы не получены, зафиксируй это как «Пробел в спецификации».

## 5. Порядок работы
1. Изучи карту контрактов и ограничения.
2. Сформируй краткий план: какие именно сценарии будешь проверять для каждого пункта контракта.
3. Дождись подтверждения плана от Арбитра или управляющего чата.
4. После подтверждения напиши код тестов.

## 6. Формат результата (Отчёт о завершении)
Верни результат, оформленный строго по шаблону `templates/CORE-HANDOFF-template.md`, включив в него:
- **Код тестов:** одним блоком Markdown, готовый к запуску.
- **Пробелы в спецификации:** явный список вопросов к архитектору, возникших при чтении контракта.
- **Лог покрытия:** краткое описание (1–2 предложения на функцию), какие сценарии из п.3 были покрыты.

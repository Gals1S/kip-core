# CORE-ARCH: Модель данных KIP Core (Черновик)

> Документ описывает бизнес-логику и требования к данным (без привязки к конкретным схемам БД).

## 0. Контекст экосистемы

Система KIP Core обеспечивает полный цикл работы с данными контрольно-измерительных приборов (КИП). Архитектура данных едина и поддерживает три базовые функции экосистемы:

1. Извлечение данных: первичный импорт и чтение информации из принципиальных схем.
2. Учёт и обогащение: централизованное хранение, верификация по справочникам и ручное дополнение информации пользователем.
3. Формирование выходных документов: генерация табличных и векторных отчетов на основе накопленных и проверенных данных.

Модель данных описывает бизнес-логику и требования к данным независимо от способа их ввода или вывода, а также от топологии развертывания программных компонентов.

## 1. Что моделирует система

Основная единица учета — **Сигнал**. Вся модель данных строится вокруг учета сигналов. 

**Сигнал** не существует сам по себе: он жестко привязан к **Прибору** и содержит информацию о том, в какой **Шкаф** он адресован. Для описания физического пути сигнала используются **Связи**.

**Связь** — это физический кабель. Связь всегда соединяет ровно два **Узла**. 
**Узел** — это абстрактное понятие, обозначающее любую точку подключения в системе. Узел может быть трех видов: **Прибор**, **Шкаф** или **Коробка**.

**Бизнес-логика связей:**
Связь может соединять два Прибора, либо Прибор и Шкаф. 
Коробка вводится для объединения и разъединения сигналов на маршруте между Приборами и Шкафами (когда один общий кабель раскладывается на несколько или наоборот).

### Термины раздела 1

- **Сигнал** — минимальная единица учета (например, показание датчика или команда управления).
- **Узел** — абстрактное понятие для любой точки подключения в системе.
  - **Прибор** — полевое оборудование (датчик, арматура), которое генерирует или принимает сигналы.
  - **Шкаф** — оборудование управления, которое собирает сигналы от приборов.
  - **Коробка** — пассивный узел, который не работает с сигналами, а служит только для соединения и разветвления кабелей.
- **Связь** — физический кабель, соединяющий ровно два узла.

## 2. Уровни данных (Библиотека и Проект)

В первом разделе мы определили, что физическая структура объекта состоит из **Узлов** и **Связей**. Чтобы работать с несколькими объектами параллельно, система разделяет эти данные на два уровня: **Библиотеку** и **Проект**.

**Библиотека (Типы).**
Это справочный каталог, единый для всей системы. В Библиотеке нет конкретных физических объектов, там хранятся только их Типы:
- *Типы узлов:* Модели приборов, типы шкафов, типы клеммных коробок.
- *Шаблоны сигналов:* Для каждой модели прибора в Библиотеке задается перечень сигналов, которые должны быть у этой модели.
- *Типы связей:* Марки кабелей.
- *Типы документов:* Справочник видов документов (Схема соединений, Опросный лист и т.д.).

**Проект (Экземпляры).**
Это конкретный объект проектирования (судно, платформа). Внутри Проекта инженер собирает структуру из конкретных Экземпляров:
- *Узлы (Экземпляры):* Конкретное оборудование (например, Прибор с тегом `PT-101`). Каждый узел в Проекте ссылается на свой Тип из Библиотеки.
- *Связи (Экземпляры):* Конкретные физические кабели, соединяющие узлы. Ссылаются на Тип (марку) из Библиотеки.
- *Сигналы (Экземпляры):* Принадлежат конкретным узлам. Создаются на основе Шаблона сигналов из Библиотеки, но хранят фактические данные для этого проекта (уставки, подсистемы).
- *Помещения:* Области внутри Проекта, в которых размещаются узлы. Задают ограничения по условиям среды.
- *Документы:* Конкретные документы проекта (схемы, чертежи, опросные листы), которые связываются с узлами.

### Термины раздела 2

- **Библиотека** — глобальный справочник типовых данных, не зависящий от конкретного проекта.
- **Проект** — конкретный объект учета, содержащий экземпляры узлов, связей и помещений.
- **Тип** — справочное описание (модель прибора, марка кабеля), которое лежит в Библиотеке.
- **Экземпляр** — конкретный объект в Проекте (например, конкретный прибор), созданный на основе Типа.
- **Шаблон сигналов** — заданный в Библиотеке перечень сигналов для определенной модели прибора.
- **Помещение** — область в Проекте, накладывающая ограничения на размещенные в ней узлы.
- **Документ** — файл или запись (чертёж, схема), привязанная к узлам Проекта для фиксации проектных решений.

## 3. Узлы

Узлы делятся на три вида: Приборы, Шкафы и Коробки. Рассмотрим их подробнее.

### 3.1. Прибор

Прибор — это узел с сигналами, представляющий собой конкретное полевое оборудование в рамках Проекта. Прибор является Экземпляром и ссылается на Тип (Модель) в Библиотеке.

**Что задается на уровне Типа (в Библиотеке):**
- *Заводские характеристики:* перечень доступных для этой модели исполнений (например, какие степени защиты IP или маркировки Ex выпускает завод для этой модели).
- *Шаблон сигналов:* жесткий перечень сигналов, которые есть у этой модели (например, `AI1` — измерение, `DI1` — неисправность).

**Что задается на уровне Экземпляра (в Проекте):**
- *Идентификация:* Уникальный тег (позиция) в рамках проекта (например, `PT-101`).
- *Размещение:* Привязка к конкретному Помещению.
- *Фактические характеристики:* Инженер выбирает из доступных заводских характеристик те, которые подходят для конкретного помещения (например, выбирает исполнение IP66, если помещение этого требует). Также инженер вручную вводит параметры, которых нет в каталоге (например, конкретный диапазон измерений для этой задачи).
- *Фактические сигналы:* Экземпляры сигналов, созданные на основе Шаблона сигналов. Для них инженер указывает фактические данные (уставки, привязку к системе управления).

### 3.2. Информация, хранимая по Прибору

Данные прибора делятся на два уровня: то, что диктует производитель (в Библиотеке), и то, что фиксирует инженер для конкретного объекта (в Проекте). 

**Правило по умолчанию:** при создании прибора в Проекте система автоматически подтягивает значения из Библиотеки (если они там заданы). Инженер может переопределить любое из этих значений для конкретного прибора, если этого требуют условия проекта.

| Информация | В Библиотеке (Тип / Модель) | В Проекте (Экземпляр Прибора) | Правило |
|---|---|---|---|
| **Идентификация** | | | |
| Тег (Позиция) | — | Текст (до 50 символов). Уникален в проекте. | Задается только в Проекте |
| Модель (Тип) | Название, производитель. | Ссылка на Модель | Может быть пустым (см. примечания) |
| **Размещение** | | | |
| Помещение | — | Ссылка на Помещение в Проекте | Задается только в Проекте |

| Взрывозащита (Ex) | Доступные варианты (справочник) | Выбранное значение (текст до 30 символов) | Наследуется. Переопределяется инженером |
| Климат | Доступные варианты (справочник) | Выбранное значение (текст до 10 символов) | Наследуется. Переопределяется инженером |
| Материал среды | Доступные варианты (справочник) | Выбранное значение (текст до 30 символов) | Наследуется. Переопределяется инженером |
| Материал корпуса | Доступные варианты (справочник) | Выбранное значение (текст до 20 символов) | Наследуется. Переопределяется инженером |
| Присоединение к процессу | Тип (справочник) + базовый размер | Тип (справочник) + Размер (текст до 20 символов) | Наследуется. Переопределяется инженером |

### Примечания к разделу 3.2

1. **Черновики (Создание без Модели).**
   Инженеру часто нужно быстро занести приборы на объект (например, при импорте из схем), не выбирая сразу конкретную модель оборудования. Для этого предусмотрен режим «Черновик».
   - Если Модель не выбрана, прибор создается только с Тегом и привязкой к Помещению. 
   - В этом состоянии у прибора нет унаследованных характеристик, и для него **не создаются Сигналы**.
   - Позже инженер может вернуться к прибору, выбрать Модель, и система автоматически подтянет все заводские характеристики и создаст нужный набор сигналов.

2. **Наследование и переопределение.**
   Поля, для которых указано «Наследуется», не обязательно дублируют информацию в базе данных. Если инженер не менял значение, система при отображении берет его из выбранной Модели в Библиотеке. Если инженер ввел свое значение (переопределил), оно сохраняется в Проекте и имеет приоритет над Библиотекой.

3. **Обязательность заполнения.**
   Обязательным является только Тег. Остальные поля могут оставаться пустыми (если это допускает бизнес-логика), однако для полноценной работы и выгрузки документов инженер должен заполнить Модель и Помещение.

### 3.3. Сигналы Прибора

Сигналы не создаются инженером вручную по одному. Они автоматически генерируются для конкретного Прибора на основе **Шаблона сигналов**, который задан в его Модели (в Библиотеке). 

Инженер не может добавить прибору сигнал, которого нет в Шаблоне его Модели. Состав сигналов жестко фиксирован.

| Информация | В Библиотеке (Шаблон модели) | В Проекте (Экземпляр Сигнала) | Правило |
|---|---|---|---|
| **Идентификация** | | | |
| Позиция (например, `AI1`, `DI1`) | Задается в шаблоне. | Копируется из шаблона. | Жестко задается шаблоном. На уровне прибора не меняется. |
| **Характеристики сигнала** | | | |
| Электрическая реализация | Задается значение по умолчанию (например, `I420`). | Выбранное значение из справочника. | Наследуется из шаблона. Инженер может переопределить. |
| Уставки (уровень + значение) | Могут быть заданы по умолчанию (например, `HH` = 10). | Выбранный уровень + число. | Наследуется из шаблона. Инженер может переопределить или оставить пустым. |
| **Привязка к системе** | | | |
| Система управления (РСУ, ПАЗ, ПЛК) | — (не задается в шаблоне) | Выбранное значение из справочника (или `NULL`). | **Всегда вводится вручную.** Не наследуется. |
| Шкаф назначения | — | Ссылка на Шкаф в Проекте | **Обязательно для маршрутизации.** |

### Примечания к разделу 3.3

1. **Автоматическое создание.**
   Сигналы создаются автоматически в двух случаях:
   - Когда инженер назначает прибору Модель (при создании или позже).
   - Когда инженер меняет Модель у уже существующего прибора (старые сигналы удаляются, создаются новые по шаблону новой модели).
   
2. **Сброс переопределений.**
   При смене Модели у прибора все введенные ранее данные по сигналам (системы управления, переопределенные уставки и реализации) **сбрасываются**. Инженеру выдается предупреждение о том, какие данные будут потеряны. (Это защищает от того, чтобы данные от одного типа прибора «переехали» на совершенно другой).

3. **Число жил.**
   Информация о количестве жил в кабеле для конкретного сигнала не хранится в самом сигнале. Она определяется через справочник Электрических реализаций (для `I420` — одно число, для `RTD_3W` — другое).

### 3.4. Шкаф

Шкаф — это узел с сигналами, представляющий собой оборудование системы управления (РСУ, ПАЗ, ПЛК), в которое адресуются сигналы от приборов. Как и Прибор, Шкаф является Экземпляром и ссылается на Тип в Библиотеке.

| Информация | В Библиотеке (Тип шкафа) | В Проекте (Экземпляр Шкафа) | Правило |
|---|---|---|---|
| **Идентификация** | | | |
| Тег (Позиция) | — | Текст (до 50 символов). Уникален в проекте. | Задается только в Проекте |
| Модель (Тип) | Название типа шкафа. | Ссылка на Модель | Может быть пустым (черновик) |
| **Размещение** | | | |
| Помещение | — | Ссылка на Помещение в Проекте | Задается только в Проекте |
| **Системная принадлежность** | | | |
| Система управления (РСУ, ПАЗ, ПЛК) | Значение по умолчанию для этого типа. | Выбранное значение (справочник) | Наследуется. Переопределяется инженером |
| **Характеристики (подбор под среду)** | | | |
| Степень защиты (IP) | Доступные варианты (справочник) | Выбранное значение | Наследуется. Переопределяется инженером |
| Взрывозащита (Ex) | Доступные варианты (справочник) | Выбранное значение | Наследуется. Переопределяется инженером |

### Примечания к разделу 3.4

1. **Отсутствие шаблона сигналов.**
   В отличие от Прибора, Шкаф не имеет собственного шаблона сигналов. Сигналы не «рождаются» в шкафу, они в него адресуются от Приборов. Принадлежность шкафа к определенной системе управления (например, РСУ) используется для проверки соответствия входящих сигналов.

### 3.5. Коробка (Клеммная коробка)

Коробка — это пассивный узел. Она не генерирует и не принимает сигналы, а служит исключительно для физического соединения, разветвления или объединения связей (кабелей) на маршруте между Приборами и Шкафами. 

Как и другие узлы, Коробка является Экземпляром и ссылается на Тип в Библиотеке.

| Информация | В Библиотеке (Тип коробки) | В Проекте (Экземпляр Коробки) | Правило |
|---|---|---|---|
| **Идентификация** | | | |
| Тег (Позиция) | — | Текст (до 50 символов). Уникален в проекте. | Задается только в Проекте |
| Модель (Тип) | Название типа коробки. | Ссылка на Модель | Может быть пустым (черновик) |
| **Размещение** | | | |
| Помещение | — | Ссылка на Помещение в Проекте | Задается только в Проекте |
| **Характеристики (подбор под среду)** | | | |
| Степень защиты (IP) | Доступные варианты | Выбранное значение | Наследуется. Переопределяется инженером |
| Взрывозащита (Ex) | Доступные варианты | Выбранное значение | Наследуется. Переопределяется инженером |

### Примечания к разделу 3.5

1. **Пассивность.**
   У коробки нет системы управления (РСУ/ПАЗ) и нет шаблона сигналов. Она является «черным ящиком» для системы, внутри которого кабели могут менять свою топологию (один кабель входит, два выходят). 

2. **Связи.**
   Коробка всегда имеет как минимум две связи (входящую и исходящую). Количество связей, которые могут сходиться в коробке, определяется её физическими характеристиками, но на уровне архитектуры данных это не ограничивается.

## 4. Помещения

Помещение — это область внутри Проекта, в которой физически размещаются Узлы. Помещения не имеют аналогов в Библиотеке, так как являются уникальными для каждого объекта (судна, платформы).

Каждое помещение задает **требования к условиям среды**, которым должны соответствовать размещенные в нем Узлы.

| Информация | Описание | Правило |
|---|---|---|
| **Идентификация** | | |
| Номер | Текст (до 20 символов). Уникален в проекте. | Обязательно для заполнения |
| Наименование | Текст (до 100 символов). | Обязательно для заполнения |
| Палуба | Текст (например, «Главная палуба»). | Задается один раз при создании |
| Строительный район | Текст. | Задается один раз при создании |
| **Требования к среде (Ограничения)** | | |
| Требуемая степень защиты (IP) | Текст / Справочник | Определяет минимальные требования для узлов |
| Требуемая взрывозащита (Ex) | Текст / Справочник | Определяет допустимые маркировки для узлов |
| Требуемое климатическое исполнение | Текст / Справочник | Определяет допустимый климат для узлов |

### Примечания к разделу 4

1. **Требования, а не факты.**
   Поля «Требования к среде» описывают то, что *должно быть* в помещении, а не то, что фактически установлено. Фактические характеристики хранятся в карточках Узлов (Приборов, Шкафов, Коробок).

2. **Привязка узлов.**
   Узел может быть привязан только к одному помещению. При этом в одном помещении может находиться неограниченное количество узлов.

3. **Связь с диагностикой.**
   Наличие требований в помещении и фактов в узлах позволяет системе проводить диагностику (Раздел 7), сравнивая эти данные и выявляя несоответствия.

## 5. Связи

Связь — это физический кабель (сегмент), который передает сигналы между узлами. Одна связь всегда имеет ровно два конца (Адрес А и Адрес Б) и соединяет два узла. 

**Универсальное правило (Черновик):** как и Узлы, Связь может быть создана в виде черновика. Инженер может указать только Индекс (Тег) кабеля, а адреса (куда он идет) и длину заполнить позже.

| Информация | В Библиотеке (Марка кабеля) | В Проекте (Экземпляр Связи) | Правило |
|---|---|---|---|
| **Идентификация** | | | |
| Индекс (Тег) | — | Текст (до 50 символов). Уникален в проекте. | Задается только в Проекте |
| Марка кабеля (Тип) | Название марки. | Ссылка на Марку | Может быть пустым (черновик) |
| **Топология (Адреса)** | | | |
| Адрес А | — | Ссылка на Узел | Может быть пустым (черновик) |
| Адрес Б | — | Ссылка на Узел | Может быть пустым (черновик) |
| **Характеристики проекта** | | | |
| Длина | — | Число (в метрах). | Задается в Проекте (уточняется при прокладке) |

**Состав марки кабеля (в Библиотеке):**
Марка кабеля (Тип) содержит заводские характеристики: число жил, сечение, наличие экрана, наличие брони и другие физические параметры. Они не дублируются в карточке Связи в Проекте, так как уже заданы выбранной маркой.

### Примечания к разделу 5

1. **Два адреса.**
   Связь не может соединять сама с собой (Адрес А и Адрес Б должны быть разными узлами). Если нужно соединить три прибора, используется промежуточный узел (Коробка).

2. **Автоматическая трассировка сигналов (Ключевое правило!).**
   Сигналы **не привязываются к связям вручную**. 
   - Сигнал привязан к Прибору (Источник) и к Шкафу (Назначение). Указание Шкафа обязательно, иначе система не сможет построить маршрут.
   - На основе топологии (какой Узел с каким соединен Связями) система автоматически строит граф и находит путь (трассу) от Прибора до Шкафа. 
   - Все Связи, через которые проходит этот путь, автоматически считаются несущими данный Сигнал.

3. **Диагностика подсистем.**
   Так как каждый Сигнал имеет свою подсистему (РСУ, ПАЗ, ПЛК), а каждый Шкаф тоже относится к подсистеме, система может проверять логику: если Сигнал принадлежит ПАЗ, а путь ведет в Шкаф РСУ, диагностика выдаст предупреждение.
   *Примечание:* Одна Связь (кабель) может нести сигналы разных подсистем (например, общий участок от Прибора до Клеммной коробки). Это не является ошибкой самой Связи. Однако при выходе из Коробки сигналы ПАЗ должны идти в Шкаф ПАЗ, а сигналы РСУ — в Шкаф РСУ. Диагностика проверяет именно конечные точки маршрута каждого сигнала, а не подсистему кабеля.

4. **Расчет занятости жил.**
   Количество занятых жил в связи не хранится как отдельное поле, а вычисляется. Система находит все Сигналы, путь которых проходит через эту Связь, и суммирует их количество жил (взяв данные из характеристик марки кабеля).

   *Примечание:* Если между двумя узлами проложено несколько параллельных связей (кабелей), архитектура не требует автоматического распределения сигналов по конкретным физическим кабелям. Система отслеживает прохождение сигнала по участкам (узлам), а детальное распределение по параллельным кабелям выполняется на этапе вывода или вручную.

## 6. Документы

Документы — это проектные артефакты (схемы, чертежи, опросные листы), которые описывают инженерные решения. Документы всегда относятся к конкретному Проекту (они не переносятся в Библиотеку).

| Информация | Описание | Правило |
|---|---|---|
| **Идентификация** | | |
| Тип документа | Схема соединений, Чертёж установки, Опросный лист и т.д. (из справочника). | Обязательно для заполнения |
| Номер | Текст (до 50 символов) | Обязательно для заполнения |
| Ревизия | Текст (до 10 символов) | Обязательно для заполнения |
| Наименование | Текст (до 150 символов) | Задается в Проекте |
| Файл | Ссылка на файл | Может быть пустым |

### Бизнес-логика связи «Прибор ↔ Документ»

1. **Документы описывают приборы.** К одному документу (например, к общей схеме соединений) может быть привязано множество приборов. 
2. **Ограничение по типу.** Для каждого типа документа инженер может привязать к прибору только один документ. (Например, у одного прибора может быть только одна схема соединений, но при этом он может быть привязан к схеме соединений, чертежу установки и опросному листу).

## 7. Диагностика (Проверки)

Система не блокирует сохранение данных, если они противоречат бизнес-правилам (инженер может вносить исключения). Вместо жестких запретов предусмотрен механизм **диагностики** — набор проверок, который запускается по команде инженера и формирует отчет о выявленных несоответствиях.

### Перечень проверок

1. **Соответствие узлов помещению (Среда).**
   Система сравнивает фактические характеристики узла (IP, Ex, климат) с требованиями помещения, в котором он размещен. Если характеристики узла ниже требуемых (например, прибор с IP54 стоит в помещении, требующем IP66), в отчет выводится предупреждение.
   
2. **Соответствие сигналов шкафам (Подсистемы).**
   Каждый сигнал имеет свою подсистему (РСУ, ПАЗ, ПЛК). Каждый шкаф также относится к определенной подсистеме. Система проверяет маршруты сигналов: если сигнал ПАЗ приходит в шкаф РСУ, выдается предупреждение о несоответствии систем управления.
   *Примечание:* Одна Связь (кабель) может нести сигналы разных подсистем (например, общий участок от Прибора до Клеммной коробки). Это не является ошибкой самой Связи. Однако при выходе из Коробки сигналы ПАЗ должны идти в Шкаф ПАЗ, а сигналы РСУ — в Шкаф РСУ. Диагностика проверяет именно конечные точки маршрута каждого сигнала, а не подсистему кабеля.

3. **Заполненность данных (Черновики).**
   Система выявляет незавершенные объекты. Например, приборы, у которых не выбрана Модель (черновики), или связи, у которых не указаны адреса (А и Б). Это помогает инженеру понять, что еще не доделано в проекте.

4. **Переполнение участков (Занятость жил).**
   Система вычисляет требуемое количество жил для прохождения сигналов. 
   Если между двумя узлами проложено несколько параллельных связей (кабелей), их емкость суммируется. 
   Диагностика выдает предупреждение только в том случае, если суммарное количество требуемых жил превышает суммарную емкость всех кабелей, проложенных на этом участке между узлами.

### Примечания к разделу 7

1. **Отчетность, а не запреты.**
   Диагностика не останавливает работу. Инженер может проигнорировать предупреждение, если это осознанное исключение, или исправить данные.

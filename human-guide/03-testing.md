# 3. Организация тестирования

Эта инструкция описывает, как проверять код, который пишут утилиты. Мы используем 4 уровня тестирования.

## 3.1. Уровень 1: Модульные тесты (Unit)
**Кто делает:** ИИ-разработчик (чат, который пишет код).
**Что делает арбитр:** Следит за одним строгим правилом.
- **Правило:** Разработчик может писать тесты, но не имеет права менять ожидаемые результаты (assertions) в тестах, чтобы «подогнать» их под свой код. Если тест падает — он должен исправить код, а не тест. Если тест изначально написан неверно, изменение ожидаемых значений разрешает только арбитр.

## 3.2. Уровень 2: Контрактные тесты (Black-box)
**Кто делает:** Отдельный, независимый ИИ-чат (не тот, что писал код).
**Что делает арбитр:** Организует процесс через ручную передачу контекста, изолируя тестировщика от кода.
1. Убедитесь, что в репозитории создан файл задания на тестирование по шаблону `templates/CORE-TASK-TEST-L2-template.md`. В этот файл разработчик (или вы) уже вставил «карту контрактов» (список функций с сигнатурами, docstring и возможными исключениями).
2. Откройте **новый чат** и задайте ему роль: «Ты независимый ИИ-тестировщик, работающий по методу черного ящика».
3. **Важно:** Не сообщайте этому чату про репозиторий и не давайте ему доступ к файлам проекта. Скопируйте из файла задания **только** раздел «Карта контрактов» и вставьте его в чат. Это критически важно для чистоты Black-box тестирования.
4. Заберите готовый код тестов из отчета чата и передайте его разработчику для запуска.

## 3.3. Уровень 3: Дымовое и нагрузочное тестирование
**Кто делает:** Core (пишет сценарии), Арбитр (запускает).
**Что делает арбитр:** 
1. Попросите Core написать скрипт (например, на Python или SQL), который имитирует базовые операции (дымовое) или одновременную работу нескольких пользователей (нагрузочное).
2. Сохраните скрипт в проект утилиты.
3. Запустите его в терминале на своем компьютере.
4. Скопируйте результат (успех или текст ошибки) и отправьте обратно в чат Core для анализа.

## 3.4. Уровень 4: Приёмочное тестирование (UAT)
**Кто делает:** Арбитр.
**Что делает арбитр:**
1. Попросите Core составить пошаговый чек-лист (сценарии: «нажать кнопку, ввести неверные данные, проверить ошибку»).
2. Запустите приложение (утилиту) в своей среде.
3. Пройдите по чек-листу как обычный пользователь.
4. Зафиксируйте, где поведение системы не совпало с ожиданиями, и верните это разработчику на исправление.

## 3.5. Правило «Evidence Pack» (Доказательства)
Не верьте отчетам ИИ на слово. При приёмке задачи требуйте конкретные доказательства в разделе Handoff:
- Хэш коммита или ссылку на ветку в Git.
- Лог прохождения тестов (текст или скриншот терминала).
- Скриншоты работы интерфейса (для UAT).
- Ссылки на обновленные файлы документации (если менялся контракт).

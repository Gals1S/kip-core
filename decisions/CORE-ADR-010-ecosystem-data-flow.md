# CORE-ADR-010: Состав экосистемы и поток данных

**Проект:** KIP_Core
**Статус:** см. `decisions/CORE-ADR-REGISTRY.md`
**Дата:** 08.11.2026
**Связанные документы:** `CORE-RSH-002`, `CORE-RSH-003`,
`CORE-RSH-004`, `CORE-RSH-005`, `CORE-ADR-005`, `CORE-ADR-007`,
`SPECIFICATION.md` (разделы «Среда эксплуатации», «Модель данных»)

---

## Контекст

SPEC определяет экосистему в общем виде: три стадии (ввод → учёт →
вывод), инструменты учёта КИП, обмен только через табличные файлы.
Но не определено:

- из каких утилит состоит экосистема и где границы их
  ответственности;
- как данные движутся от извлечения из схемы до выпуска документа;
- где на этом пути участвует человек и что именно он решает;
- где живут физические данные (сегменты, коробки, шкафы, марки)
  и как они заполняются;
- нужен ли обратный поток от вывода к учёту;
- какая утилита где работает и с чем связана.

Без этого SPEC не может описать состав экосистемы, а утилиты —
согласованно работать. Исследования RSH-002…005 дают материал:
RSH-005 описывает практику тяжёлых САПР (модульный конвейер,
логический и физический уровни, правила генерации как данные
проекта), RSH-003 — роли утилит и стадийность, RSH-002 и
RSH-004 — модель данных прибора и монтажа.

## Решение

### 1. Состав экосистемы

Экосистема состоит из **трёх утилит**:

| Утилита | Стадия | Функция |
|---|---|---|
| **Reader** | ввод | Извлечение данных из принципиальных схем в табличный файл (CSV) |
| **Register** | учёт | Хранение базы данных проекта, проверки данных, табличные документы |
| **Generator** | вывод | Формирование векторных документов (DWG) из данных Register |

Функции не пересекаются: Reader только извлекает, Register только
хранит, проверяет и выдаёт табличные данные, Generator только
строит векторные документы.

### 2. Поток данных

**Reader → Register.** Reader читает принципиальную схему и формирует
CSV. Он извлекает всё, что можно привязать к условному изображению
символа, вместе с индексом прибора. Точный состав колонок
определяется при разработке Reader; Core его не фиксирует.
Единственное обязательное требование — колонка `tag`: без индекса
прибора данные не к чему привязать.

**Приём в Register.** Register принимает CSV: показывает, как
собрался принять данные (что распознал сам, что нет), человек
подтверждает или правит соответствие колонок. Нераспознанные
колонки игнорируются — сырой CSV сохраняется, потери нет.

**Register → Generator.** Данные для вывода выгружаются
непосредственно перед выводом и передаются табличным файлом.
Generator строит векторные документы (DWG); задача обратна Reader.

**Generator → Register (обратный поток).** Сформированный
DWG-документ не является учётной записью, пока человек не
инициирует его выпуск. После выпуска запись документа (тип, номер,
ревизия, наименование) возвращается в Register табличным файлом
и принимается так же, как любой импорт — с показом сопоставления
и подтверждением человека. Запись связывается с прибором,
заполняя поле «документы».

### 3. Участие человека

Человек инициирует каждый поток и принимает каждое решение:

- инициирует чтение CSV и приём данных в Register;
- подтверждает сопоставление колонок при импорте;
- при повторном импорте подтверждает обновление записей
  (обновление по `tag`; подтверждение запрашивается один раз
  за цикл приёма, а не на каждую строку);
- решает, что делать с полями, которых нет в новом файле
  (по умолчанию — сохранить существующее значение);
- вводит параметры, которых нет в правилах генерации
  (например, параметры коробок);
- инициирует выгрузку данных для вывода;
- инициирует выпуск документа;
- запускает отдельные проверки целостности.

### 4. Физические данные

Физические данные (физические сегменты, клеммные коробки, шкафы,
марки, длина, экран, броня) **хранятся в базе Register**. Они
не являются зоной Generator: в отдельной утилите им неоткуда
взяться.

Модель поддерживает **три пути заполнения**, чтобы реализуемость
генерации не была условием модели:

1. **Генерация по правилам** — основной путь. Правила настраиваются
   как данные проекта (а не зашиты в код) и могут отличаться
   от проекта к проекту. Коробки могут генерироваться по правилам;
   параметры коробок вводит человек; кабели собираются
   по заполнению коробок.
2. **Ручной ввод** — человек заполняет данные напрямую.
3. **Импорт** — данные приходят табличным файлом, приём как обычно.

Реализуемость генерации по правилам — вопрос этапа разработки
Register; модель от этого не зависит.

### 5. Проверки данных

Проверки данных — **функция Register**, а не отдельной утилиты.
Это относится и к проверкам при вводе и импорте (несоответствие
справочнику, дубликаты `tag`, отсутствие обязательных связей),
и к проверкам целостности базы по запросу (висячие ссылки,
противоречия между связанными данными).

При несоответствии справочнику запись создаётся без значения
поля, пользователь информируется (отчёт после приёма или лог
на экране — на усмотрение утилиты).

Внутреннее устройство проверок (модуль, экран, запуск
по расписанию) — решение уровня Register, в Core не фиксируется.

### 6. Взаимодействие и развёртывание

Обмен между утилитами — **только табличными файлами**. Прямого
API, общего чтения базы, встраивания одной утилиты в другую нет.

| Утилита | Где работает | С чем связана |
|---|---|---|
| **Register** | Работает с общей базой данных по локальной сети; ориентир — до 10 пользователей | Единственная утилита, работающая с общей БД |
| **Reader** | Локально на машине пользователя | Обменивается с Register файлами |
| **Generator** | Локально на машине пользователя | Получает файл от Register; при выпуске документа возвращает файл в Register |

Generator локальный и автономный: при наличии файла документ можно
сформировать, даже когда Register выключен.

## Последствия

**Положительные:**

- Состав экосистемы определён: три утилиты, границы не пересекаются.
- Поток данных описан по шагам, с явным участием человека
  на каждом шаге.
- Физические данные имеют место в модели; три пути заполнения
  снимают риск «генерация не реализуема — модель менять».
- Обратный поток документов закрывает поле «документы» прибора
  без ручного ввода.
- Файловое взаимодействие сохраняет независимость утилит
  и автономность локального вывода.
- Register не тянет стек DWG: сбой векторной библиотеки
  не затрагивает учётную систему.

**Отрицательные и обязательства:**

- Между Register и Generator появляется передача файлов и обратный
  поток; риск построения по устаревшему файлу снимается правилом
  «выгрузка непосредственно перед выводом» — это правило работы,
  а не техническое ограничение.
- Правила генерации — данные проекта; их состав и настройка
  требуют отдельного проектирования на этапе разработки Register.
- Три пути заполнения физических данных — обязательство
  для Register: нельзя реализовать только генерацию.
- Generator должен уметь сообщать человеку о том, что не удалось
  построить и почему (отчёт или лог). В Register этот отчёт
  не возвращается: если данных нет, отчёту нечего добавить.

## Отклонённые варианты

- **Generator как модуль внутри Register.** Отклонено: жёсткая
  связка, стек DWG тянет учётную систему; автономность локального
  вывода теряется.
- **Взаимодействие по API / IPC.** Отклонено: сетевая сложность
  и поддержка версий API без выигрыша для утилит на одной машине.
- **Прямое чтение общей БД (read-only).** Отклонено: контрактом
  становится схема БД, релизы связываются, обратный поток
  всё равно требует решения; выигрыш не оправдывает связности.
- **Автоматическая передача данных по триггеру.** Отклонено:
  человек теряет контроль над моментом выпуска; инициация
  потока — решение человека.
- **Generator на машине Register (серверный вариант).**
  Отклонено: зависимость от включённой машины Register; локальный
  Generator с файлом автономен.
- **Физические данные в Generator.** Отклонено: данным неоткуда
  взяться, кроме базы Register.
- **Только генерация по правилам (без ручного ввода и импорта).**
  Отклонено: реализуемость генерации не гарантирована; модель
  должна поддерживать все три пути.
- **Правила генерации, зашитые в код.** Отклонено: правила —
  данные проекта, они различаются от проекта к проекту.
- **Отдельная утилита-валидатор.** Отклонено: для проверки
  актуальной базы ей нужно прямое чтение БД (связность), через
  файл проверяется снимок; часть проверок всё равно обязана быть
  в Register.
- **Обратный поток только с номерами документов.** Отклонено:
  теряется единообразие приёма; документ принимается так же,
  как любой импорт.
- **Generator ничего не возвращает в Register.** Отклонено:
  поле «документы» прибора осталось бы незаполненным.

## Условия пересмотра

- Если передача файлов между Register и Generator окажется узким
  местом — вернуться к вопросу о прямом чтении БД.
- Если генерация по правилам окажется нереализуемой — основной
  путь меняется на ручной ввод или импорт; модель не меняется.
- Если вывод DWG окажется неразрывно связан с учётом — вернуться
  к вопросу о модуле внутри Register.
- Если появится четвёртая утилита (например, для отдельной задачи
  вывода) — пересмотреть состав экосистемы и границы
  ответственности.
- Если правила генерации окажутся одинаковыми для всех проектов —
  пересмотреть решение «правила как данные проекта» в пользу
  общих правил.

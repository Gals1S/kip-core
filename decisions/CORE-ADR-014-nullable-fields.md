# CORE-ADR-014: Nullable-поля для приборов и сигналов

**Проект:** KIP_Core
**Статус:** см. `decisions/CORE-ADR-REGISTRY.md`
**Дата:** 15.11.2026
**Связанные документы:** `REG-REQ-006`, `CORE-ARCH-data-model.md`, `CORE-TASK-006-signals-crud.md`

---

## Контекст
Аудит модели данных выявил, что жесткое требование заполнения (NOT NULL) для некоторых полей мешает реальным сценариям работы пользователя и логике пересоздания сигналов. 

## Решение
1. **`device.project_standard_id` (стандарт прибора) становится nullable.** 
   Инженер может создать прибор, указав только `tag`, и назначить стандарт позже. При назначении стандарта система автоматически сгенерирует сигналы для этого прибора.
2. **`signal.control_system_id` (система управления) становится nullable.** 
   При автоматическом пересоздании сигналов по шаблону нового стандарта это поле остается пустым (`NULL`), так как угадывать подсистему (РСУ/ПАЗ/ПЛК) запрещено. Инженер заполняет его вручную.
3. Остальные обязательные поля (`tag`, `device_id`, `position`, поля аудита) остаются `NOT NULL`, так как заполняются автоматически или являются ключевыми.

## Последствия
- Требуется миграция БД (снятие NOT NULL с двух колонок).
- В `REG-ARCH-db.md` вносятся соответствующие правки.
- Логика работы Register: CRUD сигналов не имеет методов POST/DELETE, только GET и PUT (редактирование).

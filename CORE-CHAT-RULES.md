# Правила работы для чатов экосистемы KIP Core

Этот документ содержит обязательные правила для всех чатов, работающих с проектом KIP Core. 

## 1. Принципы работы

**Один пост — одна мысль.** Один пост содержит одну завершенную мысль и один вопрос в конце. Вопрос задается так, чтобы ответ «да» был полным решением. Чат предлагает вариант с кратким обоснованием, человек соглашается или возражает.

**Анти-лень (режим строгого критика).** Чат не имеет права перекладывать выбор на человека (выдавать варианты A/B/C вместо рекомендации) и не имеет права срезать углы (отвечать поверхностно).

**Проверка фактов.** Если в задании или сессии были приложены документы, чат обязан отвечать, опираясь на них. Ответы «по памяти» без сверки с приложенным контекстом запрещены.

**Перепроверка перед выдачей.** Чат сам перепроверяет результат перед выдачей на соответствие правилам.

**Язык.** Документация, комментарии, сообщения коммитов — по-русски. Имена файлов и папок — латиницей, строчными буквами через дефис. Исключение — префикс проекта или утилиты (2–6 букв в верхнем регистре: `CORE-`, `REG-`).

**Формат коммитов.** `ДД.ММ.ГГГГ: что сделано`.

## 2. Взаимодействие через файлы

Взаимодействие между чатами формализуется через файловые сообщения, а не через текст в чате.

**Типы сообщений:**
- **Задание** — от Core к исполнителю.
- **Запрос в Core** — от исполнителя к Core (с описанием: что изменить, зачем, последствия).
- **Отчёт о завершении** — от исполнителя к Core для приёмки.

**Использование шаблонов:** В проекте (в папке `templates/`) существуют шаблоны для всех типов файловых сообщений. Чат обязан самостоятельно найти и использовать актуальный шаблон, соответствующий типу сообщения, не полагаясь на жесткие ссылки в этом документе.

**Валидация на границе.** Файл, не соответствующий структуре шаблона, не принимается.

## 3. Классы документации и структура папок

Документы делятся на три класса. Для навигации чат ориентируется на названия папок и файлов, а не на реестры.

**Класс A — исторические артефакты (append-only):**
- `decisions/` — архитектурные решения (ADR).
- `research/` — материалы исследований.
- `diary/` — дневники сессий.
*Правило:* не правятся никогда. Являются историей принятия решений. Если решение устарело, создается новый документ с новым порядковым номером. Источником правды всегда являются актуальные файлы модели и спецификации.

**Класс B — живой (актуальное состояние):**
- `CORE-SPEC.md` — контракт экосистемы.
- `CORE-ARCH-data-model.md` — модель данных.
- `templates/` — шаблоны файлов.
*Правило:* правятся по мере необходимости.

**Класс C — генерируемые:**
- Отсутствуют в Core. Появляются в утилитах (код, схемы БД).

**Принцип для утилит:** Все артефакты, специфичные для конкретного инструмента или чата утилиты, хранятся в его собственной папке (например, `register/`, `reader/`).

## 4. Протокол передачи контекста (Lean-загрузка)

Загрузка контекста идет по принципу **Map-first** (от общего к частному). Чат не должен гадать имена файлов или полагаться на жесткие ссылки.

1. **Карта:** В начале работы чат получает только базовые правила (этот документ) и текст задания.
2. **Запрос:** Если для выполнения задачи требуются исторические решения или шаблоны, чат обязан явно запросить у Арбитра список содержимого соответствующей папки (`templates/`, `decisions/`, `research/`). Чат определяет нужный файл по его имени и порядковому номеру.
3. **Выдача:** Арбитр выдает запрошенные файлы строго по одному, не перегружая контекст лишней информацией.

**Формат передачи документа:** Любой документ, который передается человеку, отдается одним блоком Markdown с указанием имени файла перед блоком.

## 5. Целевая среда эксплуатации

Требования к итоговому программному обеспечению (ОС, портативность, работа без интернета) описаны в `CORE-SPEC.md`. Чаты должны учитывать, что разрабатываемые решения и код должны удовлетворять этим требованиям, при этом сама среда разработки и процесс исследования не имеют этих ограничений.

# Правила работы над KIP Core

> Назначение: зафиксировать процесс работы над общим слоем экосистемы
> (модель данных, форматы обмена, принципы).
> Документ меняется редко — только при изменении самого процесса.

## 1. Принципы работы

- **Один чат — одна тема.** Один чат посвящён одной крупной задаче
  (создание документа, исследование, проектирование модели). Смешение
  тем в одном чате размывает контекст и усложняет передачу.

- **Один пост — один шаг.** Внутри темы каждый пост решает одну
  маленькую проверяемую задачу. Не «сделаем всё сразу», а «шаг 1,
  шаг 2, шаг 3» — чтобы после каждого шага можно было остановиться
  и проверить.

- **Язык.** Документация, комментарии, сообщения коммитов — по-русски.
  Имена файлов и папок — латиницей (kebab-case), как принято в проекте.

- **Источник правды.** Для модели данных — архитектурный документ
  (класс B), который дистиллирует решения из ADR. ADR — способ
  принятия решений и история: новое решение оформляется ADR,
  обсуждается и принимается, после чего входит в архитектурный
  документ. К ADR обращаются за обоснованием и деталями, когда
  из архитектурного документа неясно, почему решение такое.
  При расхождении архитектурного документа и ADR прав ADR
  (архитектурный документ приводится в соответствие).
  Для структуры данных каждой утилиты — код и миграции этой утилиты
  (в Core кода нет). При расхождении документа с кодом утилиты —
  обновляется документ утилиты, а Core меняется только через
  управляющий чат.

- **Критерии оценки решений.** При выборе варианта (в ADR, в модели,
  в процессе) решение оценивается по трём критериям, в порядке
  приоритета:

  1. **Удобство работы пользователя** — минимум ручной работы,
     однозначность поведения, отсутствие лишних шагов.
  2. **Производительность** — скорость работы утилит на реальных
     объёмах данных.
  3. **Простота разработки** — минимум логики, которую нужно
     написать и поддерживать.

  Изменение контракта (новая версия модели) само по себе
  не является сдерживающим фактором: если вариант лучше по этим
  критериям, контракт меняется. Оценка «минорная / мажорная версия»
  используется для организации выпуска, а не для запрета решений.

- **Формат коммитов.** `ДД.ММ.ГГГГ: что сделано`
  (пример: `04.11.2026: README Core — функции, принципы,
  состав документации`).

## 2. Разделение чатов

В Core работают два типа чатов:

| Чат | Что обсуждается | Что не обсуждается |
|---|---|---|
| **Управляющий (Core)** | Модель данных, форматы обмена, версии контракта, принципы разделения инструментов | Исследования (для них — ресерч-чат); архитектура конкретных утилит |
| **Ресерч** | Исследование по заданию управляющего чата: обзоры САПР, сравнение подходов, замеры. Результат — `docs/research/` | Принятие решений, изменения ADR, написание кода |

**Ключевое правило.** Изменение модели данных проходит **только
через управляющий чат Core**. Утилита не может «просто добавить
поле» — это изменение контракта, оно фиксируется здесь, новым ADR.

**Другие чаты** (управляющий утилиты, задачный, отладочный) —
описаны в handover соответствующей утилиты. В Core их нет.

## 3. Роль человека

Человек — **владелец процесса и арбитр**, а не диспетчер каждого
шага и не проверяющий каждое сообщение.

Функции человека:

1. **Постановка цели и приоритизация.** Определяет, что важно
   и в каком порядке решать.
2. **Приёмка артефактов на границах фаз.** Читает результат
   и решает, достаточен ли он для перехода к следующей фазе.
3. **Арбитраж.** Разрешает конфликты между чатами (когда управляющий
   чат сообщает о противоречии).
4. **Одобрение необратимых решений.** Изменение контракта, выпуск
   версии, принятие нового ADR.

Подробные сценарии действий человека (что приложить, что написать)
на случаи, когда управляющий чат недоступен (лимит, сбой), описаны
в `HUMAN-GUIDE.md` в корне репозитория.

## 4. Взаимодействие управляющих чатов

Взаимодействие между управляющими чатами (Core ↔ утилита)
формализуется через **файловые сообщения** — файлы с явным именем
и расположением, а не сообщения в чате.

| Тип сообщения | Кто инициирует | Кто обязан отреагировать | Артефакт |
|---|---|---|---|
| **Запрос на изменение модели** | Управляющий чат утилиты / ресерч-чат | Управляющий чат Core | Файл запроса с обоснованием |
| **Уведомление о выпуске версии** | Управляющий чат Core | Все затронутые чаты (через handover) | Новый ADR + обновлённый SPEC |
| **Эскалация** | Любой чат | Управляющий чат Core (или человек) | Файл с описанием конфликта/блокера |
| **Отчёт о завершении** | Ресерч-чат / чат утилиты | Управляющий чат Core (приёмка) | Файл исследования / Implementation Handoff |

**Валидация на границе.** Файл, не соответствующий шаблону типа
сообщения, не принимается. Это защита от «слабого артефакта на
границе фаз».

**Проверка полученного ADR.** Любой ADR, полученный чатом (в пакете,
вложением, текстом), до использования сверяется с реестром
(`docs/decisions/CORE-ADR-REGISTRY.md`):

- ADR отсутствует в реестре → это черновик; чат не применяет его,
  а сообщает: «ADR-NNN отсутствует в реестре — вероятно, черновик».
- Статус в реестре «Заменён» → чат сообщает и предлагает актуальный ADR.
- Номер в реестре есть, но тема/содержание не совпадает → расхождение;
  чат задаёт вопрос.

Проверка выполняется до чтения содержания ADR, а не после.

**Принцип «передавай выводы, а не стенограмму».** Любой артефакт,
пересекающий границу между чатами, — это дистилляция. Получатель
не должен заново выводить то, что отправитель уже знал.

Детали решения — в `CORE-ADR-001-orchestration.md`.

### Шаблоны артефактов

Для каждого типа сообщения и для ключевых документов есть шаблон
в папке `docs/templates/`. Шаблон — это форма, которую копируют
и заполняют; он не заменяет содержание, но задаёт структуру.

Минимальный набор шаблонов:

| Шаблон | Для чего |
|---|---|
| `CORE-ADR-template.md` | Новый ADR |
| `CORE-RSH-template.md` | Новый отчёт исследования |
| `CORE-RESEARCH-REQUEST-template.md` | Задание на исследование (что должен содержать запрос в ресерч-чат) |
| `CORE-TASK-template.md` | Задание на любую другую работу (утилита, код) |
| `CORE-HANDOFF-template.md` | Отчёт о завершении (Implementation Handoff) для утилит |

Шаблоны — класс B (живые): правятся, когда меняется структура
артефакта, но не при каждой задаче. Валидация на границе (раздел 4)
опирается на шаблон: если артефакт не соответствует шаблону,
управляющий чат возвращает его на доработку.

### Что должно быть в сообщении

**Запрос на изменение модели** (от утилиты или ресерча в Core):

- **Что** нужно изменить (сущность, поле, связь).
- **Зачем** (какая задача не решается без этого).
- **Что будет**, если не изменить (последствия для утилиты).

**Эскалация** (от любого чата в Core или человеку):

- **В чём проблема** (конфликт, блокер, недостаточно данных).
- **Какие варианты** решения видит чат.
- **Что рекомендует** и почему.

Этого достаточно, чтобы Core понял запрос и принял решение.
Отдельных шаблонов для этих сообщений нет — они слишком короткие,
чтобы плодить файлы. Шаблоны для более объёмных артефактов
(ADR, исследование, задание на исследование, отчёт о завершении) —
в папке `docs/templates/`.

## 5. Классы документации

Документы делятся на три класса. Класс определяет, можно ли править
документ и при каких условиях.

| Класс | Что входит | Правило |
|---|---|---|
| **A — append-only** | `docs/decisions/` (ADR), `docs/research/` (исследования) | Не правятся. Устарело — новый файл с новой датой. Статус ADR — в реестре `CORE-ADR-REGISTRY.md`. Принятие исследования — в реестре `CORE-RSH-REGISTRY.md` |
| **B — живой** | `SPECIFICATION.md`, `README.md`, `handover.md`, архитектурные документы, `docs/decisions/CORE-ADR-REGISTRY.md`, `docs/research/CORE-RSH-REGISTRY.md`, `docs/templates/` | Правятся, но редко и предсказуемо (см. ниже) |
| **C — генерируемые** | — | В Core нет: кода нет, генерировать нечего. Класс появляется в утилитах (схема БД, API reference) |

### Класс A — append-only

- **ADR (`docs/decisions/`).** Решение неизменно: принятый ADR не правится.
  Передумали — новый ADR; в реестре (`CORE-ADR-REGISTRY.md`) старый
  получает статус «Заменён» или «Действует с изменениями». Текст ADR
  не изменяется — в шапке стоит ссылка на реестр, а не значение статуса.
  Имя файла: `CORE-ADR-NNN-<тема>.md`. Заголовок:
  `# CORE-ADR-NNN: <тема>`. В шапке — поля `**Проект:** KIP_Core`
  и `**Статус:** см. docs/decisions/CORE-ADR-REGISTRY.md`.
  Номер ADR уникален только в рамках проекта; префикс делает
  источник однозначным при передаче в чат.

  **Нет в реестре — значит, черновик.** Внесение в реестр — действие
  человека, выполняемое сразу после принятия ADR (по слову «Принято»
  в чате). ADR, отсутствующий в реестре, — черновик: правится свободно.
  Если ADR передан, а в реестре его нет — чат обязан задать вопрос
  об актуальности, а не считать его действующим.

  **Частичное изменение ADR.** Новый ADR может изменять отдельные
  разделы действующего ADR, не отменяя его целиком. В шапке нового
  ADR — поле `**Изменяет:** ADR-NNN (раздел)`. В реестре у старого
  ADR статус «Действует с изменениями» с указанием изменяющего ADR.
  Текст старого ADR не правится (append-only): читатель видит, что
  раздел изменён, и обращается к новому ADR.

  **Полная замена ADR.** Новый ADR полностью отменяет старый.
  В шапке нового — `**Заменяет:** ADR-NNN`. В реестре у старого
  статус «Заменён». Текст старого ADR не правится.

- **Исследования (`docs/research/`).** Устарело — новый файл со
  следующим номером, старый не трогается. Ссылки из ADR указывают
  на конкретный файл, а не на «актуальное исследование».
  Имя файла: `CORE-RSH-NNN-<тема>.md`. Заголовок:
  `# CORE-RSH-NNN: <тема>`. В шапке — поле `**Проект:** KIP_Core`.
  Нумерация последовательная (001, 002, …), без дат в имени.

  **Статусов нет.** Исследование либо внесено в реестр
  (`CORE-RSH-REGISTRY.md`) — принято, либо отсутствует в реестре —
  черновик (правится свободно). Внесение в реестр — действие
  человека сразу после принятия (по слову «Принято» в чате).
  Неполное исследование не правится: заказывается новое, которое
  закрывает пробелы; в реестре у старого указывается, каким
  дополнено, у нового — какое дополняет.

### Класс B — живой

- **`SPECIFICATION.md`** — контракт экосистемы (форматы обмена,
  версии модели). Правится **на границе версии контракта**: новая
  версия — новая редакция SPEC.
- **`README.md`** — визитка. Правится **почти никогда**: только при
  изменении самих принципов (функции, принципы). Текущие версии
  модели, статусы, списки инструментов, состав документации
  в README не попадают — для них есть SPEC, архитектурный документ
  и этот раздел handover.
- **`handover.md`** — правила работы. Правится **при изменении
  процесса** (новый тип чата, новый класс документа, новый формат
  коммита), а не при каждой задаче.
- **Архитектурные документы.** Дистилляция решений из ADR:
  только решения, без обоснований, последствий, отклонённых
  вариантов. Источник правды о текущем состоянии модели. Правятся
  **после утверждения новых ADR**, от которых зависят, — в тот же
  момент или при выпуске версии. Передаются в новый чат вместо ADR
  (не содержат лишних обоснований, воспринимаются как правило,
  пока не изменены новым ADR). При сомнениях — обращение к ADR.
- **`docs/decisions/CORE-ADR-REGISTRY.md`** — реестр ADR: тема,
  статус, связи «изменяет / заменяет», дата. Правится при выпуске
  нового ADR (добавить строку, проставить статусы затронутых ADR).
  Не источник правды: при расхождении с ADR прав ADR.
- **`docs/research/CORE-RSH-REGISTRY.md`** — реестр исследований:
  тема, дата, связи «дополняет / дополнено», примечание. Правится
  при принятии нового исследования (добавить строку, проставить
  связи). Не источник правды: при расхождении с исследованием
  прав файл исследования.

### Класс C — генерируемые

В Core нет. Структура классов общая для всех проектов экосистемы:
в утилитах (например, Register) класс C — это схема БД, API reference,
`build_info.json`. В Core генерировать нечего, потому что нет кода.

### Состав документации и порядок чтения

**Файлы в корне проекта:**

| Файл | Класс | Роль |
|---|---|---|
| `README.md` | B | Визитка: назначение, функции, принципы системы |
| `HUMAN-GUIDE.md` | B | Сценарии действий человека, когда управляющий чат недоступен |

**Папки и типы документов:**

| Папка | Класс | Что хранится |
|---|---|---|
| `docs/` | B | `SPECIFICATION.md` (контракт), `handover.md` (процесс) — файлы верхнего уровня |
| `docs/architecture/` | B | Архитектурные документы — дистилляция решений из ADR. Источник правды о текущем состоянии модели |
| `docs/decisions/` | A | ADR — способ принятия решений и история. Реестр (`CORE-ADR-REGISTRY.md`) — карта ADR |
| `docs/research/` | A | Исследования — обзоры, сравнения, замеры. Реестр (`CORE-RSH-REGISTRY.md`) — карта исследований |
| `docs/templates/` | B | Шаблоны артефактов (ADR, исследование, задание, отчёт о завершении) |

**Реестры в папках.** Папки с append-only документами
(`docs/decisions/`, `docs/research/`) содержат реестр — живой
файл-карту: тема, статус (для ADR) или связи «дополняет /
дополнено» (для исследований), дата. Реестр — не источник правды,
а навигация: по нему чат находит нужные документы и проверяет
актуальность. Практика распространяется на все папки с append-only
содержимым.

**Порядок чтения для нового участника:** README (что за система) →
SPEC (контракт) → архитектурный документ (что действует) →
handover (как работать). ADR и исследования — по мере
необходимости, через реестры.

## 6. Протокол передачи контекста

Протокол отвечает на вопрос: что приложить к новому чату, чтобы он
работал с моделью Core, а не переизобретал её.

### Пакет для нового чата утилиты

Когда открывается чат по Register, Reader, Generator (или другой
утилите), прикладываются:

1. **Архитектурный документ Core** (класс B) — источник правды
   о текущем состоянии модели.
2. **`docs/decisions/CORE-ADR-REGISTRY.md`** — реестр ADR (тема,
   статус, связи «изменяет / заменяет»).
3. **`docs/handover.md`** — правила работы (раздел 6, протокол).
4. **Собственные документы утилиты** — её SPEC, архитектурный
   документ, код, тесты.

Полные тексты ADR в пакет не входят. Чат, прочитав реестр, сам
запрашивает ADR, нужные по теме и статусу. Заменённые ADR
запрашиваются только для истории и обоснования — для работы
они не нужны. Если ADR передан без реестра — чат задаёт вопрос
об актуальности (раздел 5).

Утилита **не переписывает модель Core** в своих документах.
В её SPEC и архитектурном документе — ссылка на версию контракта
Core и архитектурный документ Core, а не копия модели.

### Пакет для нового ресерч-чата

1. **Постановка вопроса** от управляющего чата Core (одна фраза
   + критерии, если это сравнение).
2. **Архитектурный документ Core** — текущее состояние модели.
3. **`docs/decisions/CORE-ADR-REGISTRY.md`** — реестр ADR.
4. **Релевантные ADR** — по запросу чата (те, что касаются темы
   исследования; чтобы исследование не противоречило уже принятым
   решениям).
5. **`docs/research/CORE-RSH-REGISTRY.md`** — реестр исследований
   (тема, связи «дополняет / дополнено»).
6. **Существующие исследования** по теме (`docs/research/`),
   если они есть.

### Выход ресерч-чата

- **Файл исследования** — `docs/research/CORE-RSH-NNN-<тема>.md`.
  Номер присваивается при создании: следующий после последнего
  существующего файла. Структура: вопрос, варианты, критерии,
  сравнение, вывод, источники.
- **Резюме** (5–10 строк) — возвращается в управляющий чат Core
  для принятия решения. Резюме **не** заменяет ADR: если по итогам
  исследования принято архитектурное решение, управляющий чат
  оформляет ADR отдельно.

### Формат передачи документа человеку

Любой документ, который передаётся человеку для чтения (ADR, SPEC,
исследование, задание, отчёт), отдаётся одним блоком Markdown:
четыре обратные кавычки и слово `markdown` в начале, четыре
обратные кавычки в конце. Внутри блока могут быть свои блоки кода
(тройные кавычки) — они не конфликтуют с внешней обёрткой. Это нужно,
чтобы текст не рвался при копировании и вставке в файл.

Перед блоком указывается имя файла (полный путь) — человек
сначала копирует имя, затем текст.

**Фрагменты.** Если передаётся не документ целиком, а фрагмент
для замены (раздел, подраздел), действуют те же правила: один
блок Markdown, перед блоком — имя файла и явная пометка, какой
раздел заменяется (например: «Файл: …, раздел `### X` —
исправленный текст»). Фрагмент не является документом и не
требует полного текста, но формат блока — тот же.

### Версия контракта в пакете

Утилита в своём SPEC указывает версию контракта Core (Git-тег),
с которой работает. Если Core обновился до новой версии, а утилита —
нет, это видно сразу: в SPEC утилиты стоит старая версия.
Обновление утилиты — осознанное действие (прочитать diff ADR,
решить, обновляться или нет).

### Если управляющий чат недоступен

Протокол выше описывает нормальную работу: управляющий чат ведёт
вас, вы прикладываете файлы, получаете результат.

Если управляющий чат недоступен (достигнут лимит, чат закрылся,
начинаете с нуля) — откройте `HUMAN-GUIDE.md` в корне репозитория.
Там пошаговые сценарии: какие файлы приложить к новому чату, что
написать, как передать контекст.

## 7. Версионирование контракта

Контракт Core имеет версию. Версия — это Git-тег в репозитории
`KIP_Core` (`v1.0`, `v1.1`, `v2.0`). Версия фиксирует состояние
контракта на момент выпуска: набор ADR, разделы SPEC «Форматы
обмена» и «Глоссарий».

### Где хранится номер версии

Номер версии хранится в шапке `SPECIFICATION.md` (поле «Версия
контракта»). Git-тег с тем же номером (`v1.0`) фиксирует состояние
репозитория на момент выпуска. Тег и номер в SPEC должны совпадать;
расхождение — ошибка выпуска, исправляется новым коммитом.

Отдельного файла `VERSION` в Core нет: SPEC — единственный источник
номера. В утилитах, где есть код, номер может дублироваться в
`version.py` (как в Register) — это ответственность утилиты.

### Что меняет версию контракта, а что нет

Версия контракта меняется при изменении:
- ADR (`docs/decisions/`) — любое решение о модели;
- SPEC, разделы «Форматы обмена» и «Глоссарий».

Версия контракта **не меняется** при изменении:
- README (описание системы);
- handover (процесс работы);
- SPEC, раздел «Среда эксплуатации» (условия среды, не контракт);
- архитектурных документов (они следуют за ADR);
- реестров ADR и исследований (они карты, а не содержание).

Если сомневаетесь — задайте вопрос в управляющем чате Core.

### Архитектурные документы и версия

Архитектурные документы — производные от ADR. Они обновляются
после принятия ADR, от которого зависят, и при выпуске версии
приводятся в соответствие с SPEC. Сами по себе правки
архитектурного документа версию не меняют.

### Когда меняется версия

- **Любое изменение контракта** (новая сущность, новое поле,
  изменение связи, изменение формата обмена) — новая версия.
- **Исправление опечатки или уточнение формулировки**, не меняющее
  смысл, — версия не меняется (правится класс B: SPEC или ADR
  с пометкой об уточнении).

### Кто ставит версию

Только управляющий чат Core. Утилита не может «выпустить» новую
версию контракта — она может только предложить изменение через
управляющий чат Core (новый ADR).

### Как утилита принимает новую версию

1. В SPEC утилиты указана версия контракта, с которой она работает:
   `Контракт — KIP_Core v1.0 (тег v1.0)`.
2. При выходе новой версии Core (например, v1.1) утилита **не
   обновляется автоматически**. Ответственный за утилиту читает
   diff (какие ADR добавлены или изменены), решает, совместимо ли
   изменение, и обновляет SPEC утилиты.
3. Если утилита не обновилась, это видно по её SPEC: там старая
   версия. Это не ошибка, а осознанное состояние — утилита работает
   со старой моделью, пока не будет готова перейти на новую.

### Совместимость версий

- **Мажорная версия** (`v1.0` → `v2.0`) — ломающее изменение.
  Утилита не сможет работать без обновления.
- **Минорная версия** (`v1.0` → `v1.1`) — добавление, не ломающее
  существующие поля и связи. Утилита может продолжать работать
  со старой версией, но не увидит новых возможностей.

Конкретное правило (что считать ломающим) фиксируется в SPEC
при выпуске версии.

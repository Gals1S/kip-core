# CORE-ADR-001: Модель оркестрации и роль человека

**Проект:** KIP_Core
**Статус:** Принято
**Дата:** 04.11.2026
**Связанные документы:** `docs/research/CORE-RSH-001-orchestration-patterns.md`
(исследование), `docs/handover.md` (процесс), `README.md` (принципы)

---

## Контекст

KIP_Core — общий слой экосистемы, где работают управляющие чаты
(Core и утилит), ресерч-чаты, задачные и отладочные. Чаты **не имеют
общей памяти** и общаются только через файлы и человека (принцип из
`README.md`: «Независимость через файлы»).

Без формализации этой модели возникают проблемы:

- **«Расползание» решений** — один чат принял решение, другой не знает.
- **Человек как бутылочное горлышко** — если он диспетчер каждого шага,
  его внимание ограничивает всю систему.
- **Слабые артефакты на границе** — стенограмма вместо дистиллята
  разрушает цепочку передачи контекста.

Исследование `CORE-RSH-001-orchestration-patterns.md` показало, что
принцип «обмен только файлами» совместим с современными подходами
к оркестрации, и выделило наиболее подходящую модель. Настоящий ADR
фиксирует решение по этой модели.

**Расширение понятия ADR.** Настоящий ADR — первый в Core, который
описывает **процесс**, а не модель данных. Это расширяет область
применения ADR в проекте: ADR фиксирует любое архитектурное решение,
включая организацию работы. Правило действует для всех последующих
ADR Core.

## Решение

### Модель оркестрации

**Иерархический супервизор с файловым протоколом и типизированными
артефактами.**

- **Управляющий чат Core** — супервизор: декомпозирует, раздаёт
  задания, собирает резюме, проверяет на соответствие контракту.
- **Ресерч и управляющие утилит** — специализированные роли.
- **Человек** — владелец процесса и арбитр (см. ниже).

Модель сохраняет принцип «обмен только файлами»: координация идёт
через типизированные артефакты (файлы с явным именем, расположением
и шаблоном), а не через общий канал или память.

### Роль человека

**Владелец процесса и арбитр.** Не диспетчер каждого шага и не
маршрутизатор каждого сообщения.

Функции:

1. **Постановка цели и приоритизация.** Определяет, что важно
   и в каком порядке решать.
2. **Приёмка артефактов на границах фаз.** Читает результат и решает,
   достаточен ли он для перехода к следующей фазе. Это проверка
   **артефакта на границе**, а не каждого сообщения.
3. **Арбитраж.** Разрешает конфликты между чатами (например, Core
   и утилита предлагают разные решения). Решение арбитража
   фиксируется (ADR или обновление документа).
4. **Одобрение необратимых решений.** Изменение контракта, выпуск
   версии, принятие нового ADR — требуют явного одобрения человека.
   Всё остальное — выборочный аудит, а не «штампование каждого шага».

### Протокол взаимодействия: четыре типа сообщений

Взаимодействие между управляющими чатами формализуется через
**файловые сообщения** — не сообщения в чате, а файлы с явным именем
и расположением.

| Тип | Кто инициирует | Кто обязан отреагировать | Артефакт |
|---|---|---|---|
| **Запрос на изменение модели** | Управляющий чат утилиты / ресерч-чат | Управляющий чат Core | Файл запроса с обоснованием |
| **Уведомление о выпуске версии** | Управляющий чат Core | Все затронутые чаты (через handover) | Новый ADR + обновлённый SPEC |
| **Эскалация** | Любой чат | Управляющий чат Core (или человек) | Файл с описанием конфликта/блокера |
| **Отчёт о завершении** | Ресерч-чат / чат утилиты | Управляющий чат Core (приёмка) | Файл исследования / Implementation Handoff |

**Валидация на границе.** Файл, не соответствующий шаблону типа
сообщения, не принимается. Это защита от «слабого артефакта на
границе фаз».

### Принцип «передавай выводы, а не стенограмму»

Любой артефакт, пересекающий границу между чатами, — это
**дистилляция**, а не пересказ процесса. Стенограмма несёт тупики,
исправления и путаницу отправителя; получатель не должен заново
выводить то, что отправитель уже знал.

### Ограничения внимания

Ориентир для соло-инженера — **2–3 активных чата** одновременно.
Это не жёсткое правило, а следствие предела внимания: по оценке
DeepSeek (с оговоркой о статусе данных — это практическая оценка,
не контролируемый эксперимент) один человек может активно курировать
3–5 сессий агентов. При превышении узким местом становится внимание,
а не мощность модели.

### Где фиксировать

- **Настоящий ADR** — решение (модель, роль человека, протокол).
- **`handover.md`** — процесс: как именно применять решение
  (подраздел «Взаимодействие управляющих чатов», раздел «Роль
  человека», чек-листы артефактов).

Отдельный файл `docs/orchestrator.md` **не создаётся**: это
увеличило бы поверхность сопровождения без выигрыша. handover уже
описывает процесс, роль человека — его часть.

## Последствия

**Положительные:**

- Предсказуемость взаимодействия: типы сообщений фиксированы,
  валидация на границе.
- Аудируемость: каждое решение и переход оставляют след в файлах.
- Снятие нагрузки с человека: он не диспетчер каждого шага,
  а арбитр на необратимых точках.
- Совместимость с принципом «обмен только файлами»: не требует
  общей памяти или API.

**Отрицательные и обязательства:**

- **Дисциплина шаблонов.** Артефакт, не соответствующий шаблону,
  не принимается — это требует привычки и внимания от всех участников.
- **Изменения в handover.** После принятия настоящего ADR handover
  дополняется: подраздел «Взаимодействие управляющих чатов»,
  «Роль человека», чек-листы артефактов.
- **Ориентир 2–3 чата** — это рекомендация, а не жёсткий лимит;
  при превышении — не запрет, а сигнал, что внимание становится
  узким местом.
- **Расширение понятия ADR.** ADR теперь фиксирует не только модель
  данных, но и процесс. Это правило действует для всех последующих
  ADR Core (и, по аналогии, в утилитах).

## Отклонённые варианты

- **HITL (человек как точка одобрения каждого шага).** Не подходит
  как основной режим: при росте объёма одобрение вырождается
  в «штампование», а человек становится бутылочным горлышком.
  Уместен только на необратимых точках — что и зафиксировано
  в роли человека.
- **Human-as-Orchestrator (человек как диспетчер).** Не оставляет
  следа: решение «какой чат что делает» существует только в голове
  человека. Противоречит принципу «источник правды — файл».
  Допустим только при 2–3 чатах и редких переходах.
- **Group Chat (общий тред с менеджером).** Требует общего канала
  или памяти, которых у чатов Core нет. Противоречит архитектурному
  принципу «обмен только файлами».
- **Агентный режим в чистом виде.** Предполагает автономное
  выполнение, а KIP_Core строится вокруг человеческой приёмки
  контрактных решений. Элементы (автоматическая маршрутизация,
  состояние задач) — полезны, но это не смена модели.
- **Отдельный файл `docs/orchestrator.md`.** Лишняя точка
  сопровождения; роль человека — часть процесса, её место
  в handover.

## Условия пересмотра

- **Рост числа активных чатов >5** (например, несколько утилит
  одновременно) — вернуться к вопросу о вынесении состояния задач
  в отдельный файл (Task Control Plane).
- **Появление инструментов автоматической маршрутизации** —
  пересмотреть степень ручного управления переходами.
- **Изменение принципа «обмен только файлами»** (например, появление
  общего сервера или API между чатами) — пересмотреть всю модель
  оркестрации, не только этот ADR.
- **Неэффективность четырёх типов сообщений** (например, на практике
  используется только два) — упростить протокол новым ADR.

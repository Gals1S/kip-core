# CORE-ADR-005: Стадийная модель и границы Core

**Проект:** KIP_Core
**Статус:** см. `docs/decisions/CORE-ADR-REGISTRY.md`
**Дата:** 04.11.2026
**Связанные документы:** `README.md` (функции, принципы), `docs/SPECIFICATION.md` (раздел 2, раздел 3, глоссарий), `docs/decisions/CORE-ADR-002-instrument-model.md`, `CORE-ADR-003-cable-model.md`, `CORE-ADR-004-montage-model.md`, `docs/research/CORE-RSH-005-cad-modeling-principles.md`; атомарные ADR-006…008 (готовятся)

## Контекст

Семейство утилит KIP охватывает три стадии обработки данных: ввод, учёт и вывод. Core как общий слой задаёт модель данных и правила для всех трёх стадий, а утилиты реализуют их. Однако в документах Core стадийная модель как единая карта не зафиксирована: сущности описаны по темам (прибор, кабель, монтаж), но без явного указания, к какой стадии относится каждая сущность, что Core определяет на каждой стадии и где проходят стыки между утилитами.

Без такой карты:

- стыки между утилитами (что и в каком виде передаётся от ввода к учёту и от учёта к выводу) не формализованы;
- атомарные ADR по темам (сигнал, кабельная модель, монтаж) не имеют общего основания и рискуют переизобретать границы;
- неясно, что относится к модели данных (предмет Core), а что — к реализации утилиты.

Настоящий ADR закрывает следующие вопросы:

1. Какие стадии обработки данных существуют и что происходит на каждой.
2. Что Core определяет на каждой стадии и что оставляет на усмотрение утилит.
3. К какой стадии относится каждая сущность модели.
4. Где проходит точка перехода логического в физическое.
5. Как стадии обработки данных соотносятся со стадиями проектирования.

ADR-005 — общий (карта). Детали по темам фиксируются атомарными ADR (006–008), которые опираются на эту карту.

## Решение

### Стадии обработки данных

Три стадии: **ввод → учёт → вывод.** Это стадии обработки данных, а не стадии проектирования (FEED / Basic / Detailed — см. ниже). Распределение функций по конкретным утилитам — решение уровня утилит, не Core: одна утилита может покрывать несколько стадий, одна стадия может обслуживаться несколькими утилитами.

| Стадия | Что происходит |
|---|---|
| **Ввод** | Получение данных из внешних источников и приведение их к модели Core: извлечение из схем, приём табличных файлов (CSV, Excel), ручной ввод через интерфейс |
| **Учёт** | Хранение и ведение логических данных: приборы, сигналы, помещения, документы, проектные стандарты, справочники; история изменений |
| **Вывод** | Наложение физической детализации (сегменты, коробки, шкафы, марки, обратные жилы) и формирование документов: перечни, кабельные журналы, схемы, спецификации |

### Что Core определяет на каждой стадии

**Ввод.** Модель, к которой приводятся данные: сущности, обязательность полей, справочники, форматы обмена (SPEC раздел 3). Данные поступают из нескольких источников, и **ни один источник не даёт полного набора**: принципиальная схема содержит только часть атрибутов (позиция, тип, связи), табличный файл — только часть информации, остальное вводится вручную. Источники выстраиваются в цепочку через файл обмена: утилита, читающая схему, формирует CSV; утилита учёта принимает CSV и дополняет его ручным вводом. Прямого взаимодействия между утилитами нет — только через файл (README, SPEC раздел 3). Задача стадии ввода — принять частичные данные из разных источников и привести их к модели Core. Core **не** определяет: конкретные парсеры, маппинг колонок CSV на модель, правила слияния частичных данных — это в SPEC утилит.

**Учёт.** Сущности и связи логического уровня; правила наследования и переопределения (ADR-002, ADR-006); состав справочников; правила смены модели. Core **не** определяет: структуру БД, интерфейс, алгоритмы поиска — это SPEC утилиты.

**Вывод.** Принципы физического уровня: что такое физический сегмент, коробка, шкаф, обратная жила; связь «сигнал ↔ физический сегмент» (many-to-many, ADR-007); правило «индекс физического кабеля присваивается на выводе»; точка перехода логического в физическое. Core **не** определяет: конкретные правила формирования индексов, раскладку жил, шаблоны чертежей — это SPEC утилиты вывода.

### Границы Core: «не хранит» ≠ «не определяет»

- Core **не содержит реализации**: нет кода, нет БД, нет API (README, handover).
- Core **определяет модель всех трёх стадий** — это и есть его роль как общего слоя.
- Формулировки вида «Core не хранит X» в дальнейших документах заменяются на точные: «учётная модель не включает X» или «X принадлежит стадии вывода».

### Принадлежность сущностей стадиям

| Сущность | Появляется | Ведётся | Примечание |
|---|---|---|---|
| Справочники | сквозная | все стадии читают; ведение — ответственный за справочники | Ссылочный слой, не копируется в модель |
| Проектный стандарт | учёт | учёт | Задаётся для модели на проекте |
| Прибор | ввод или учёт | учёт | Может быть создан вручную или принят из файла |
| Сигнал | ввод или учёт | учёт | Часть прибора; состав задан стандартом |
| Помещение | учёт | учёт | Справочник помещений |
| Монтажная группа | учёт | учёт | Помещение, тип монтажа, ссылка на чертёж |
| Документ (метаданные: тип, номер, ревизия) | учёт | учёт | Связь с прибором |
| Физический сегмент, коробка, шкаф | вывод | вывод | В учётной модели отсутствуют |
| Обратная жила, марка кабеля, длина, раскладка жил | вывод | вывод | Физическая детализация |
| Выходные документы (перечни, журналы, схемы) | вывод | вывод | Представление модели, не первичные данные |

Сущности учёта **не переписываются** на выводе: вывод читает их и добавляет свои. Учётные данные остаются источником правды для логического уровня.

### Точка перехода логического в физическое

Переход происходит на стадии вывода. Триггер — появление физического окончания (шкаф, клеммная коробка) или применение правила генерации. До этой точки физический уровень не существует: логическая связь «прибор → подсистема» (выраженная через сигнал) может быть описана без физической реализации.

Модель допускает появление физических сущностей, но не требует их на стадии учёта.

### Связь со стадиями проекта

Стадии обработки данных соотносятся со стадиями проектирования (RSH-005, раздел 2.7), но не совпадают с ними: ввод и учёт — преимущественно ранние стадии (FEED, Basic), вывод — Detailed. Система может использоваться на любой стадии проекта; стадии обработки данных не привязаны к календарю проекта жёстко.

## Последствия

**Положительные:**

- Появляется карта: какая сущность к какой стадии относится, что Core определяет на каждой стадии. Стыки между утилитами (ввод ↔ учёт ↔ вывод) формализованы через модель и формат обмена.
- Разведены «нет реализации» и «нет физических атрибутов в учётной модели» — это позволяет точно формулировать границы в дальнейших документах.
- Атомарные ADR (006–008) получают основание: они описывают детали внутри карты, а не переизобретают границы.

**Отрицательные и обязательства:**

- **Дисциплина формулировок.** В дальнейших документах нельзя писать «Core не хранит X» без уточнения, о чём речь — об отсутствии реализации или о составе учётной модели.

## Отклонённые варианты

- **Оставить как было: «Core — только учёт, вывод — утилиты».** Не соответствует реальности (семейство утилит покрывает все стадии) и оставляет стыки неформализованными.
- **Один большой ADR на всю модель данных.** Быстро теряет актуальность при изменении одной темы; заменять его целиком — дорого. Отклонён в пользу общего ADR-карты плюс атомарных ADR по темам.
- **Общий ADR как оглавление модели (вариант B).** Оглавление устаревает и требует правок, что для класса A (append-only) неприемлемо. Оглавление живёт в реестре ADR (класс B), а общий ADR содержит решение — стадийную модель.

## Условия пересмотра

- **Появление четвёртой стадии** (например, эксплуатация и обслуживание как отдельная стадия) — пересмотр стадийной модели.
- **Изменение принципа «обмен только файлами»** (появление общего API или хранилища между утилитами) — пересмотр границ Core.
- **Если окажется, что стадии ввод / учёт / вывод не отражают реальные стыки утилит** (например, появится утилита, работающая на стыке учёта и вывода) — пересмотр карты.

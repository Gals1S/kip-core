# CORE-ADR-002: Модель данных прибора

**Проект:** KIP_Core
**Статус:** Принято

## Контекст

Изначально данные прибора пытались описать плоским набором полей
(как в табличном файле: `tag`, `type`, `setpoint`, `range` и т.д.).
Исследование предметной области (`CORE-RSH-002`) показало, что такая
модель не отражает реальность:

- одни и те же характеристики (IP, Ex, материалы) повторяются
  для всех приборов одной модели на проекте;
- невозможно отследить, где значение задано «по стандарту проекта»,
  а где инженер его изменил для конкретного прибора;
- тип и модель прибора диктуют, какие у него должны быть сигналы.

Заказчик сформулировал требования к данным: должна быть возможность
задать стандарт для модели на проекте один раз, а для конкретного
прибора — либо использовать стандарт, либо осознанно его переопределить.
Настоящий ADR фиксирует эту модель данных (что хочет заказчик),
без привязки к технической реализации (она — задача утилит).

## Решение

### Три уровня как источники значений и правила наследования

Модель данных строится на трёх уровнях. Это не технические таблицы,
а **источники значений** и правила перехода между ними.

| Уровень | Что задаёт | Кто задаёт | Можно ли переопределить ниже |
|---|---|---|---|
| **1. Справочник моделей** | Название модели, тип, производитель. Типовые характеристики (какие бывают у этой модели) | Ответственный за справочники | Нет (это «жёсткая» часть) |
| **2. Проектный стандарт** | Для каждой модели на проекте: состав сигналов (жёстко) и значения по умолчанию для характеристик (IP, Ex, климат, материалы, присоединение, кабельный ввод) | Ответственный за проект | Да, на уровне 3 |
| **3. Прибор / сигнал** | Конкретные значения. Если не переопределено — наследуется с уровня 2. Если переопределено — отличается от унаследованного, видимо и отслеживаемо | Инженер | — (конечный уровень) |

**Правила поведения (требования заказчика):**

1. При создании прибора значения **берутся** с уровня 2 (наследование).
   Инженеру не нужно заполнять их вручную.
2. Инженер может **переопределить** любое значение на уровне 3.
3. Переопределение **видимо** (отличается от унаследованного)
   и **отслеживаемо** (кто, когда, что изменил).
4. Состав сигналов задаётся на уровне 2 и **не меняется** на уровне 3.
   Если нужен другой состав — создаётся отдельная модель.
5. Характеристики сигнала (электрическая реализация, уставки)
   могут быть переопределены на уровне 3.

### Данные прибора (что хранится на уровне 3)

**Идентификация:**

- `tag` — позиция, уникальна в рамках проекта, может меняться,
  кириллица допустима.
- `type` — тип прибора (из справочника).
- `model` — модель прибора (из справочника, привязана к типу).

**Характеристики прибора:**

- IP (степень защиты).
- Ex (взрывозащита).
- Климатическое исполнение.
- Материал, контактирующий со средой.
- Материал корпуса.
- Присоединение к процессу (тип из справочника + размер свободным вводом).
- Кабельные вводы (набор пар «тип из справочника + количество»).
- Диапазон измерений (число + единица из справочника).

**Параметры процесса (вводит инженер):**

- Измеряемая среда.
- Расчётное давление.
- Расчётная температура.
- Рабочее давление.
- Рабочая температура.
- Диапазон параметра процесса.

**Статус закупки:**

- Статус (из справочника: `Предложение`, `Согласование`, `Согласован`).
- Основание (свободный текст).

**Документы:**

- Один справочник для всех типов документов с полем «тип»
  (схема принципиальная, схема соединений, монтажный чертёж и др.).
- Поля документа: номер, ревизия, наименование.
- Связь «прибор ↔ документы» без ограничений по количеству.

### Данные сигнала (что хранится на уровне 3)

- **Электрическая реализация** (из справочника: `I420`, `HART`,
  `DRY_NO`, `NAMUR`, `RTD_3W` и т.д.).
- **Уставки** — набор пар «уровень (из справочника `HHH`…`LLL`)
  + числовое значение». У сигнала может быть несколько уставок.
  Отдельные сигналы могут не иметь уставок.
- **Система управления** (из справочника `control_systems`:
  РСУ, ПАЗ, ПЛК). Определяет, в какую подсистему идёт сигнал.
- **Число жил** (1–4). Зависит от типа и электрической
  характеристики сигнала: 2 для 4–20 мА, 3–4 для термосопротивлений
  (RTD), 1 для дискретных с общей обратной. Используется для
  расчёта занятости жил кабеля (ADR-003).

### Справочники

Все стандартизованные значения хранятся в справочниках. Свободный
ввод — только там, где нет стандартизованной кодировки.

1. Типы приборов.
2. Модели (название, тип, производитель).
3. Производители.
4. Электрические реализации сигналов.
5. Уровни уставок (`HHH`, `HH`, `H`, `L`, `LL`, `LLL`).
6. Степени защиты IP (ГОСТ 14254 / IEC 60529).
7. Маркировки Ex.
8. Климатические исполнения (ГОСТ 15150).
9. Материалы, контактирующие со средой.
10. Материалы корпуса.
11. Типы присоединения к процессу.
12. Типы кабельных вводов.
13. Единицы измерения.
14. Документы проекта (тип, номер, ревизия, наименование).
15. Статусы закупки.
16. Системы управления (РСУ, ПАЗ, ПЛК).

**Принцип:** стандартизованные коды — в справочники; вариативные
значения (конкретный размер, индекс кабеля, основание закупки) —
свободный ввод или «справочник + уточнение».

### Принципы

1. **Наследование и переопределение.** Прибор наследует значения
   из проектного стандарта; переопределение — осознанное действие
   инженера, видимое и отслеживаемое.
2. **Жёсткий состав сигналов.** Состав сигналов задаётся стандартом
   и не меняется на уровне прибора.
3. **Технические детали модели не храним.** В справочнике моделей —
   только то, что используется для выбора и фильтрации (название,
   тип, производитель). Габариты, масса, принцип действия — это
   справочная информация из каталога, она не нужна для учёта.

## Последствия

**Положительные:**

- Единообразие: стандарт для модели на проекте задаётся один раз.
- Прозрачность: видно, где значение «по стандарту», а где изменено
  инженером.
- Справочники дают единообразие написания (IP, Ex, материалы), что
  важно для отчётов и поиска.
- Модель соответствует практике проектирования КИПиА.

**Отрицательные и обязательства:**

- **Расширение объема данных.** Модель включает не только «плоские»
  поля прибора, но и проектные стандарты, сигналы, справочники,
  документы.
- **Сложнее импорт.** Внешние табличные данные (плоские) нужно
  сопоставлять с этой моделью (наследование, справочники).
  Правила сопоставления — задача утилит, не Core.
- **Больше справочников.** Требуется ведение 16 справочников
  (кто отвечает, как пополняются).

## Отклонённые варианты

- **Плоская модель (все поля в одной карточке прибора).** Не отражает
  реальность: приводит к дублированию IP/Ex/материалов для всех
  приборов одной модели и невозможности отследить переопределения.
- **Отказ от справочников (все поля — свободный текст).** Приводит
  к разнобою в написании (IP `IP65`, `ip 65`, `IP-65`), что ломает
  поиск и отчёты.

## Условия пересмотра

- **Отказ от наследования** (если заказчик решит, что все приборы
  должны строго соответствовать стандарту проекта без возможности
  переопределения) — упростить модель до двух уровней.
- **Появление большого числа полей, которые есть не у всех приборов**
  — вернуться к вопросу о расширении модели.
- **Изменение состава справочников** — новый ADR (не переписывать
  этот).

## Открытые вопросы

1. **Диапазон измерений на уровне проекта.** Задавать ли значение
   по умолчанию для диапазона измерений в проектном стандарте,
   или всегда вводить вручную для конкретного прибора? (Зависит
   от практики: для типовых задач диапазон может быть стандартным,
   для уникальных — нет).
2. **Смена модели у прибора.** Если у прибора меняется модель,
   что происходит с переопределениями? Варианты: пересоздать сигналы
   по новому стандарту (потеряв переопределения), сохранить
   переопределения (если поля совпадают), запретить смену модели
   при наличии переопределений. Требует решения заказчика.

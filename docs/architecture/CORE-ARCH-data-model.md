# CORE-ARCH: Модель данных KIP Core

**Проект:** KIP_Core
**Класс:** B (живой) — правится после утверждения новых ADR, от которых зависит
**Источник:** дистилляция решений из ADR-002…008
**Связанные документы:** `docs/decisions/CORE-ADR-REGISTRY.md` (реестр ADR), `docs/SPECIFICATION.md` (контракт)

> Документ содержит **только решения** — без обоснований, последствий и отклонённых вариантов.
> Воспринимается как правило, пока не изменён новым ADR. При сомнениях — обращение к ADR.

---

## 1. Стадии обработки данных

Три стадии: **ввод → учёт → вывод.**

| Стадия | Содержание |
|---|---|
| **Ввод** | Получение данных из внешних источников и приведение к модели Core: схемы, табличные файлы (CSV, Excel), ручной ввод |
| **Учёт** | Хранение и ведение логических данных: приборы, сигналы, помещения, документы, проектные стандарты, справочники; история изменений |
| **Вывод** | Наложение физической детализации (сегменты, коробки, шкафы, марки, обратные жилы) и формирование документов |

**Правила:**

- Ни один источник ввода не даёт полного набора данных. Источники выстраиваются в цепочку через файл обмена (CSV). Прямого взаимодействия между утилитами нет.
- Сущности учёта не переписываются на выводе: вывод читает их и добавляет свои.
- Переход логического в физическое — на стадии вывода. Триггер: появление физического окончания (шкаф, клеммная коробка) или применение правила генерации.
- Распределение функций по утилитам — решение уровня утилит, не Core.

## 2. Прибор

**Три уровня источников значений:**

| Уровень | Что задаёт | Переопределение ниже |
|---|---|---|
| **1. Справочник моделей** | Название, тип, производитель; типовые характеристики | Нет |
| **2. Проектный стандарт** | Для модели на проекте: состав сигналов (жёстко) и значения по умолчанию | Да, на уровне 3 |
| **3. Прибор / сигнал** | Конкретные значения | — (конечный уровень) |

**Правила:**

- Прибор наследует значения из проектного стандарта. Инженер может переопределить любое значение на уровне 3.
- Переопределение видимо (отличается от унаследованного) и отслеживаемо (кто, когда, что изменил).
- Состав сигналов задаётся на уровне 2 и на уровне 3 не меняется. Другой состав — другая модель.
- Изменение стандарта распространяется на приборы без переопределения.

**Характеристики прибора (уровень 3):** IP, Ex, климатическое исполнение, материал, контактирующий со средой, материал корпуса, присоединение к процессу (тип + размер), кабельные вводы (тип + количество), диапазон измерений.

**Диапазон измерений** — поле прибора, не сигнала. Вводится вручную на уровне 3. Не наследуется из стандарта. Необязательное: у приборов, где диапазон не применим (реле, сигнализаторы), остаётся пустым; пустое значение — не ошибка.

**Параметры процесса (уровень 3, вводит инженер):** измеряемая среда, расчётное давление, расчётная температура, рабочее давление, рабочая температура, диапазон параметра процесса.

**Статус закупки:** статус (из справочника) + основание (свободный текст).

**Документы:** один справочник для всех типов; поля — номер, ревизия, наименование; связь с прибором без ограничений по количеству.

**Смена модели прибора:**

- Не блокируется.
- Характеристики прибора: переопределения сохраняются (поля совпадают всегда — модель равномерная, пакет единой версии).
- Сигналы: состав пересоздаётся по стандарту новой модели; переопределения сигналов (электрическая реализация, уставки) сбрасываются с предупреждением и списком потерянных значений.
- Диапазон измерений остаётся у прибора.

## 3. Сигнал

Сигнал — часть прибора. Состав сигналов (`AI1`, `AO1`, `DI1`, `DO1`…) задаётся проектным стандартом; позиция сигнала уникальна в рамках прибора.

| Поле | Уровень | Правило |
|---|---|---|
| **Позиция** (`AI1`…) | 2 (состав) | Задаётся составом; на уровне 3 не меняется |
| **Электрическая реализация** | 3 | Из справочника; переопределяемая |
| **Уставки** (уровень + число) | 3 | Переопределяемые; у части сигналов отсутствуют |
| **Система управления** (РСУ, ПАЗ, ПЛК) | 3 | Всегда вводится, не наследуется; одна подсистема на сигнал |

**Число жил** — атрибут записи справочника «Электрические реализации сигналов». У записи ровно одно число; варианты (RTD 3/4 провода) — отдельные записи. У сигнала отдельного поля нет; читается из справочника.

**Обратные жилы** — стадия вывода. В учётной модели не хранятся. Обратная жила — атрибут физического сегмента.

## 4. Кабельная модель

**Логический кабель отсутствует.** Подсистема — поле сигнала; индекс кабеля — принадлежность физического сегмента.

**Физический сегмент** — стадия вывода. Атрибуты:

- **Индекс** — присваивается на выводе, уникален в рамках проекта.
- **Два адреса** — концы сегмента. Каждый адрес — прибор, клеммная коробка или шкаф/панель. Ровно два адреса. Покрывает топологии: прибор → коробка, коробка → шкаф, прибор → прибор, прибор → шкаф.
- **Привязка к сигналам** — какие сигналы проходят по сегменту.
- **Физические атрибуты** — марка, число жил (из каталога), длина, экран, броня.

**Правила:**

- Связь «сигнал ↔ физический сегмент» — **many-to-many**. Один сигнал может проходить по нескольким сегментам; один сегмент может нести несколько сигналов.
- Подсистема сегмента отдельным полем не хранится; определяется подсистемами связанных сигналов. Сегмент, несущий сигналы разных подсистем (общий участок до коробки), — штатная ситуация.
- Занятость жил вычисляется на выводе: сумма числа жил по связанным сигналам.
- Обратные жилы — атрибут сегмента; рекомендуемое значение по умолчанию для дискретных сигналов — 1, редактируемое.
- Разделение (участок до коробки общий, после — два сегмента к разным шкафам) и объединение (кабели от разных приборов сходятся в коробке) выражаются через many-to-many.

**Кабельный журнал** — стадия вывода, строится из физических сегментов и связанных сигналов.

## 5. Помещение и монтаж

**Справочник помещений:** номер (уникальный в рамках проекта), наименование, палуба (текст), строительный район (текст).

**Правила:**

- Палуба и строительный район — атрибуты помещения. Вводятся один раз при создании записи помещения; отдельно не вводятся.
- В карточке прибора хранится только ссылка на номер помещения.
- Отчёты по палубам и районам строятся через связь «прибор → помещение → палуба / район».

**Монтажная группа (карточка прибора):** помещение (ссылка на номер), тип монтажа (из справочника), ссылка на монтажный чертёж.

**Тип монтажа** — стартовые данные справочника (фланец, кронштейн, стойка, трубопровод, стена, встроенный). Состав справочника — данные проекта, не контракт; пополняется ответственным за проект.

**Физическая детализация** (крепёж, размеры, BoM) — стадия вывода; в учётной модели не хранится.

## 6. Справочники

Справочники — отдельный ссылочный слой. Модель проекта ссылается на них, не копируя.

| № | Справочник |
|---|---|
| 1 | Типы приборов |
| 2 | Модели (название, тип, производитель) |
| 3 | Производители |
| 4 | Электрические реализации сигналов (с числом жил) |
| 5 | Уровни уставок (`HHH`, `HH`, `H`, `L`, `LL`, `LLL`) |
| 6 | Степени защиты IP |
| 7 | Маркировки Ex |
| 8 | Климатические исполнения |
| 9 | Материалы, контактирующие со средой |
| 10 | Материалы корпуса |
| 11 | Типы присоединения к процессу |
| 12 | Типы кабельных вводов |
| 13 | Единицы измерения |
| 14 | Документы проекта (тип, номер, ревизия, наименование) |
| 15 | Статусы закупки |
| 16 | Системы управления (РСУ, ПАЗ, ПЛК) |
| 17 | Помещения (номер, наименование, палуба, строительный район) |
| 18 | Типы монтажа |

**Правила:**

- Стандартизованные коды — в справочники; вариативные значения (конкретный размер, основание закупки) — свободный ввод или «справочник + уточнение».
- У каждой записи справочника электрических реализаций — ровно одно число жил.
- Состав справочников 17 и 18 — данные проекта, не контракт.

## 7. Отложенные решения

**Loop (функциональная группировка)** — в модель не вводится. Триггеры пересмотра:

- система начинает выпускать схемы электрических соединений от прибора до шкафа ввода/вывода;
- система сопровождает пусконаладку (Loop Folder, loop checks);
- заказчик требует петельные схемы КИП как отдельный документ.

При срабатывании триггера — новый ADR со ссылкой на `CORE-RSH-005`.

# Правила работы над KIP Core

> Назначение: зафиксировать процесс работы над экосистемой — принципы
> работы и правила для чатов, роль арбитра, взаимодействие чатов,
> правила документирования, передачу контекста, версионирование
> контракта, среду разработки.
> Документ меняется редко — только при изменении самого процесса.

## 1. Принципы работы

- **Новый чат — по объёму или существенной смене темы.** Чат ведётся,
  пока контекст держится и тема не сменилась существенно (например,
  переход от Core к утилите). Новый чат открывается, когда контекст
  вырос настолько, что ранние договорённости начинают теряться, или
  когда тема сменилась существенно. Дробление под каждую задачу
  на отдельный чат не требуется: это лишняя работа без пользы.

- **Один пост — одна мысль.** Один пост — одна мысль, доведённая
  до конца, и один вопрос в конце. Вопрос задаётся так, чтобы ответ
  «да» был полным решением: чат предлагает вариант с кратким
  обоснованием, человек соглашается или возражает. Открытый вопрос
  без варианта («а как вы думаете?») не задаётся — он перекладывает
  работу на человека. Вторая мысль начинается следующим постом,
  а не в том же.

  Это обязанность чата, записанная в правилах, а не просьба человека.
  Нарушение — нарушение правила чатом, а не забывчивость человека.
  Исключения возможны; проверяется практикой. Обоснование и детали —
  `CORE-ADR-009`.

- **Два режима объёма.** По умолчанию действует правило «одна мысль —
  один пост». Исключение — обратимое: материал, который переписывается
  без последствий для чего-либо ещё (черновик раздела, варианты
  формулировок, список). По обратимому чат выдаёт **только резюме**;
  полный текст — по запросу человека.

  Проверка для чата: «если этот текст окажется неверным, придётся ли
  пересматривать что-то, кроме него самого?» Нет — обратимый режим.
  Да — обычный шаг. Важность документа признаком не является:
  неважных документов в проекте нет.

- **Перепроверка перед выдачей.** Чат сам перепроверяет результат
  перед выдачей. Человеку список критериев не показывается.

- **Остановки.** Дополнительных остановок не вводится. Остановка
  существует естественным образом — в момент, когда человек копирует
  документ в файлы. В остальное время чат идёт дальше сам.

- **Язык.** Документация, комментарии, сообщения коммитов — по-русски.
  Пользователь пишет кириллицей, чат понимает; таблица соответствий
  кириллица ↔ латиница не ведётся.

  Имена файлов и папок — латиницей, строчными буквами через дефис;
  исключение — префикс проекта или утилиты (2–6 букв в верхнем регистре
  и дефис: `CORE-`, `READER-`, `REG-`) и устоявшиеся имена (`README.md`,
  `SPECIFICATION.md`, `HUMAN-GUIDE.md`, реестры). Префикс делает
  источник однозначным при передаче в чат.

- **Источник правды.** Для модели данных — архитектурный документ
  `CORE-ARCH-data-model.md`; для потока данных — архитектурный
  документ `CORE-ARCH-data-flow.md`. Оба (класс B) дистиллируют
  решения из ADR. ADR — способ принятия решений и история: новое
  решение оформляется ADR, обсуждается и принимается, после чего
  входит в архитектурный документ. К ADR обращаются за обоснованием
  и деталями, когда из архитектурного документа неясно, почему
  решение такое. При расхождении архитектурного документа и ADR
  прав ADR (архитектурный документ приводится в соответствие).
  Для структуры данных каждой утилиты — код и миграции этой утилиты
  (в Core кода нет). При расхождении документа с кодом утилиты —
  обновляется документ утилиты, а Core меняется только через
  управляющий чат.

- **Критерии оценки решений.** При выборе варианта (в ADR, в модели,
  в процессе) решение оценивается по трём критериям, в порядке
  приоритета:

  1. **Удобство работы пользователя** — минимум ручной работы,
     однозначность поведения, отсутствие лишних шагов.
  2. **Производительность** — скорость работы утилит на реальных
     объёмах данных.
  3. **Простота разработки** — минимум логики, которую нужно
     написать и поддерживать.

  Изменение контракта (новая версия модели) само по себе
  не является сдерживающим фактором: если вариант лучше по этим
  критериям, контракт меняется. Оценка «минорная / мажорная версия»
  используется для организации выпуска, а не для запрета решений.

- **Формат коммитов.** `ДД.ММ.ГГГГ: что сделано`
  (пример: `04.11.2026: README Core — функции, принципы,
  состав документации`).

  **Связь с CHANGELOG (только для утилит с кодом; в Core CHANGELOG
  нет).** При коммите, меняющем поведение программы для
  пользователя, чат даёт арбитру готовую строку для CHANGELOG
  (дата, версия или «не выпущено», категория, описание на языке
  пользователя) и говорит, что её надо дописать. При техническом
  коммите или коммите документации — говорит, что запись не нужна.
  Запись дописывается в конец файла; для чтения чат по требованию
  собирает сводку (свежее сверху, по версиям и категориям);
  сводка не хранится.

## 2. Разделение чатов

В Core работают два типа чатов:

| Чат | Что обсуждается | Что не обсуждается |
|---|---|---|
| **Управляющий (Core)** | Модель данных, форматы обмена, версии контракта, принципы разделения инструментов | Исследования (для них — ресерч-чат); архитектура конкретных утилит |
| **Ресерч** | Исследование по заданию управляющего чата: обзоры САПР, сравнение подходов, замеры. Результат — файл исследования | Принятие решений, изменения ADR, написание кода |

**Ключевое правило.** Изменение модели данных проходит **только
через управляющий чат Core**. Утилита не может «просто добавить
поле» — это изменение контракта, оно фиксируется здесь, новым ADR.

**Другие чаты** (управляющий утилиты, задачный, отладочный) —
описаны в handover соответствующей утилиты. В Core их нет.

## 3. Роль человека

Человек — **владелец процесса и арбитр**, а не диспетчер каждого
шага и не проверяющий каждое сообщение.

Функции человека:

1. **Постановка цели и приоритизация.** Определяет, что важно
   и в каком порядке решать.
2. **Приёмка артефактов на этапах работы.** Читает результат
   и решает, достаточен ли он для перехода к следующему этапу.
3. **Арбитраж.** Разрешает конфликты между чатами (когда управляющий
   чат сообщает о противоречии).
4. **Одобрение необратимых решений.** Изменение контракта, выпуск
   версии, принятие нового ADR.

Сценарии действий арбитра — настройка инструментов среды разработки,
открытие нового чата и что приложить, действия при недоступности
управляющего чата — в `HUMAN-GUIDE.md`. Чатам этот файл не передаётся.

**Как проходит сессия.** Арбитр начинает с даты и времени. Дальше —
обсуждение мелкими шагами. Когда накопилось, чат формирует документ;
арбитр копирует его в файлы — это естественная остановка. После неё
арбитр принимает или даёт замечания (мелкие или много сразу).
Завершая сессию, арбитр сообщает время окончания — тогда чат
формирует дневник.

## 4. Взаимодействие управляющих чатов

Взаимодействие между управляющими чатами (Core ↔ утилита)
формализуется через **файловые сообщения** — файлы с явным именем,
а не сообщения в чате.

| Тип сообщения | Кто инициирует | Кто обязан отреагировать | Артефакт |
|---|---|---|---|
| **Задание** | Управляющий чат Core | Чат-адресат (ресерч или утилита) | Файл по шаблону `CORE-TASK-template.md` / `CORE-RSH-REQUEST-template.md` |
| **Запрос в Core** | Управляющий чат утилиты / ресерч-чат | Управляющий чат Core | Файл с описанием запроса |
| **Уведомление о выпуске версии** | Управляющий чат Core | Все затронутые чаты (через handover) | Новый ADR + обновлённый SPEC |
| **Отчёт о завершении** | Ресерч-чат / чат утилиты | Управляющий чат Core (приёмка) | Файл исследования / Implementation Handoff |

**Расположение файлов обмена.** Все файлы обмена (задания, запросы,
отчёты) хранятся в проекте Core, в папке того чата, к которому
относятся: задание для ресерч-чата — в `research/`, задание и отчёт
чата утилиты — в `register/`, `reader/` и т.д. В проекте утилиты
переписка с Core не хранится: там только документы утилиты.

**Порядок работы с заданием.**

1. Управляющий чат Core формирует текст задания по шаблону и отдаёт
   арбитру готовым к сохранению.
2. Арбитр сохраняет этот текст в файл в папке чата (`research/`,
   `register/`, `reader/`). Содержание и структуру файла арбитр
   не меняет.
3. Арбитр открывает чат-адресат и прикладывает пакет: файл задания,
   шаблон ответа, дополнения, которые указал Core.
4. Чат-адресат работает по заданию и возвращает текст отчёта
   по шаблону. Арбитр сохраняет отчёт в ту же папку чата в Core.

**Валидация на границе.** Файл, не соответствующий шаблону типа
сообщения, не принимается. Это защита от «слабого артефакта
на границе этапов».

**Проверка полученного ADR.** Любой ADR, полученный чатом (в пакете,
вложением, текстом), до использования сверяется с реестром ADR Core:

- ADR отсутствует в реестре → это черновик; чат не применяет его,
  а сообщает: «ADR-NNN отсутствует в реестре — вероятно, черновик».
- Статус в реестре «Заменён» → чат сообщает и предлагает актуальный ADR.
- Номер в реестре есть, но тема/содержание не совпадает → расхождение;
  чат задаёт вопрос.

Проверка выполняется до чтения содержания ADR, а не после.

**Принцип «передавай выводы, а не стенограмму».** Любой артефакт,
пересекающий границу между чатами, — это дистилляция. Получатель
не должен заново выводить то, что отправитель уже знал.

Детали решения — в `CORE-ADR-001`.

### Шаблоны артефактов

Для каждого типа сообщения и для ключевых документов есть шаблон
в папке `templates/`. Шаблон — это форма, которую копируют
и заполняют; он не заменяет содержание, но задаёт структуру.

**Шаблоны, которые заполняет получатель**, передаются вместе
с заданием: ресерч-чату — шаблон исследования
(`CORE-RSH-template.md`); чату утилиты — шаблон отчёта
о завершении (`CORE-HANDOFF-template.md`).

Минимальный набор шаблонов:

| Шаблон | Для чего |
|---|---|
| `CORE-ADR-template.md` | Новый ADR |
| `CORE-RSH-template.md` | Новый отчёт исследования |
| `CORE-RSH-REQUEST-template.md` | Задание на исследование (что должен содержать запрос в ресерч-чат) |
| `CORE-TASK-template.md` | Задание на любую другую работу (утилита, код) |
| `CORE-HANDOFF-template.md` | Отчёт о завершении (Implementation Handoff) для утилит |

Шаблоны — класс B (живые): правятся, когда меняется структура
артефакта, но не при каждой задаче. Валидация на границе (раздел 4)
опирается на шаблон: если артефакт не соответствует шаблону,
управляющий чат возвращает его на доработку.

### Что должно быть в сообщении

**Запрос в Core** (изменение модели или блокер, от утилиты или
ресерча в Core):

- **Что** нужно: изменить (сущность, поле, связь) или снять блокер.
- **Зачем** (какая задача не решается без этого).
- **Что будет**, если не изменить (последствия для утилиты).
- **Варианты** решения, если они есть, и **рекомендация** отправителя.

Этого достаточно, чтобы Core понял запрос и принял решение.
Отдельных шаблонов для этих сообщений нет — они слишком короткие,
чтобы плодить файлы. Шаблоны для более объёмных артефактов
(ADR, исследование, задание на исследование, отчёт о завершении) —
в папке `templates/`.

## 5. Классы документации

Документы делятся на три класса. Класс определяет, можно ли править
документ и при каких условиях.

| Класс | Что входит | Правило |
|---|---|---|
| **A — append-only** | `decisions/` (ADR), `research/` (исследования), `diary/` (дневники сессий) | Не правятся. Устарело — новый файл с новой датой. Статус ADR — в реестре `decisions/CORE-ADR-REGISTRY.md`. Принятие исследования — в реестре `research/CORE-RSH-REGISTRY.md` |
| **B — живой** | `SPECIFICATION.md`, `README.md`, `handover.md`, `CORE-ARCH-data-model.md`, `CORE-ARCH-data-flow.md`, реестры `decisions/CORE-ADR-REGISTRY.md` и `research/CORE-RSH-REGISTRY.md`, `templates/`, `CHANGELOG.md` (у утилит) | Правятся, но редко и предсказуемо (см. ниже) |
| **C — генерируемые** | — | В Core нет: кода нет, генерировать нечего. Класс появляется в утилитах (схема БД, API reference) |

### Класс A — append-only

- **ADR (`decisions/`).** Решение неизменно: принятый ADR не правится.
  Передумали — новый ADR; в реестре (`decisions/CORE-ADR-REGISTRY.md`)
  старый получает статус «Заменён» или «Действует с изменениями».
  Текст ADR не изменяется — в шапке стоит ссылка на реестр, а не
  значение статуса. Имя файла: `CORE-ADR-NNN-<тема>.md`. Заголовок:
  `# CORE-ADR-NNN: <тема>`. В шапке — поля `**Проект:** KIP_Core`
  и `**Статус:** см. decisions/CORE-ADR-REGISTRY.md`. Номер ADR
  уникален только в рамках проекта; префикс делает источник
  однозначным при передаче в чат.

  **Нет в реестре — значит, черновик.** Внесение в реестр — действие
  человека, выполняемое сразу после принятия ADR (по слову «Принято»
  в чате). ADR, отсутствующий в реестре, — черновик: правится свободно.
  Если ADR передан, а в реестре его нет — чат обязан задать вопрос
  об актуальности, а не считать его действующим.

  **Частичное изменение ADR.** Новый ADR может изменять отдельные
  разделы действующего ADR, не отменяя его целиком. В шапке нового
  ADR — поле `**Изменяет:** ADR-NNN (раздел)`. В реестре у старого
  ADR статус «Действует с изменениями» с указанием изменяющего ADR.
  Текст старого ADR не правится (append-only): читатель видит, что
  раздел изменён, и обращается к новому ADR.

  **Полная замена ADR.** Новый ADR полностью отменяет старый.
  В шапке нового — `**Заменяет:** ADR-NNN`. В реестре у старого
  статус «Заменён». Текст старого ADR не правится.

- **Исследования (`research/`).** Устарело — новый файл со
  следующим номером, старый не трогается. Ссылки из ADR указывают
  на конкретный файл, а не на «актуальное исследование».
  Имя файла: `CORE-RSH-NNN-<тема>.md`. Заголовок:
  `# CORE-RSH-NNN: <тема>`. В шапке — поле `**Проект:** KIP_Core`.
  Нумерация последовательная (001, 002, …), без дат в имени.

  **Статусов нет.** Исследование либо внесено в реестр
  (`research/CORE-RSH-REGISTRY.md`) — принято, либо отсутствует
  в реестре — черновик (правится свободно). Внесение в реестр —
  действие человека сразу после принятия (по слову «Принято» в чате).
  Неполное исследование не правится: заказывается новое, которое
  закрывает пробелы; в реестре у старого указывается, каким
  дополнено, у нового — какое дополняет.

- **Дневники сессий (`diary/`).** Один файл на сессию; имя —
  дата и слово `diary`: `2026-11-06-diary.md`. В заголовке —
  дата, время начала и конца сессии. Класс A: не правится;
  следующая сессия — новый файл. Дневник читает человек по
  завершении сессии; следующую сессию он начинает с даты и времени.
  Структура дневника: где остановились, что сделано, что решено,
  что отклонено и почему, открыто, что дальше. Обоснование —
  `CORE-ADR-009`.

### Класс B — живой

- **`SPECIFICATION.md`** — контракт экосистемы KIP_Core. Определяет:
  состав экосистемы (перечень утилит и их функции), границы
  ответственности между утилитами, модель данных, форматы обмена,
  версию контракта, общие правила пользовательского интерфейса.
  Обязателен для всех утилит; утилита не может его изменить — только
  запросить изменение через Core. Правится свободно до первой
  передачи контракта потребителю; после — на границе версии
  контракта (раздел 7).
- **`README.md`** — визитка: назначение, функции, принципы.
- **`handover.md`** — правила работы. Правится **при изменении
  процесса** (новый тип чата, новый класс документа, новый формат
  коммита), а не при каждой задаче.
- **`CORE-ARCH-data-model.md`** — архитектурный документ. Дистилляция
  решений из ADR: только решения, без обоснований, последствий,
  отклонённых вариантов. Источник правды о текущем состоянии модели.
  Правится **после утверждения новых ADR**, от которых зависит, —
  в тот же момент или при выпуске версии. Передаётся в новый чат
  вместо ADR (не содержит лишних обоснований, воспринимается как
  правило, пока не изменён новым ADR). При сомнениях — обращение
  к ADR.
- **`CORE-ARCH-data-flow.md`** — архитектурный документ. Поток
  данных в экосистеме и участие человека на каждом шаге. Только
  решения, без обоснований. Правится после утверждения новых ADR,
  от которых зависит. При сомнениях — обращение к ADR.
- **`decisions/CORE-ADR-REGISTRY.md`** — реестр ADR: тема, статус,
  связи «изменяет / заменяет», дата. Правится при выпуске нового
  ADR (добавить строку, проставить статусы затронутых ADR).
  Не источник правды: при расхождении с ADR прав ADR.
- **`research/CORE-RSH-REGISTRY.md`** — реестр исследований: тема,
  дата, связи «дополняет / дополнено», примечание. Правится при
  принятии нового исследования (добавить строку, проставить связи).
  Не источник правды: при расхождении с исследованием прав файл
  исследования.
- **`templates/`** — шаблоны артефактов. Пока общие; при
  специализации шаблон уходит в папку той утилиты, для которой
  он специфичен.
- **`CHANGELOG.md` (у утилит с кодом).** Лента: новые записи
  дописываются в конец файла. Каждая запись — дата, версия
  (или «не выпущено»), категория, описание на языке пользователя.
  Для чтения чат по требованию собирает сводку (свежее сверху,
  по версиям и категориям); сводка не хранится. Правило записи —
  в разделе 1, пункт «Формат коммитов».

### Класс C — генерируемые

В Core нет. Структура классов общая для всех проектов экосистемы:
в утилитах (например, Register) класс C — это схема БД, API reference,
`build_info.json`. В Core генерировать нечего, потому что нет кода.

### Состав документации и порядок чтения

**Файлы в корне проекта:**

| Файл | Класс | Роль |
|---|---|---|
| `README.md` | B | Визитка: назначение, функции, принципы |
| `SPECIFICATION.md` | B | Контракт: модель данных, форматы обмена, версия |
| `handover.md` | B | Правила работы: принципы, чаты, роль человека, документация, передача контекста, среда разработки |
| `CORE-ARCH-data-model.md` | B | Архитектурный документ — модель данных |
| `CORE-ARCH-data-flow.md` | B | Архитектурный документ — поток данных в экосистеме и участие человека |
| `HUMAN-GUIDE.md` | B | Инструкции для арбитра |

**Папки в корне:**

| Папка | Класс | Что хранится |
|---|---|---|
| `decisions/` | A | ADR — способ принятия решений и история. Реестр (`CORE-ADR-REGISTRY.md`) — карта ADR. Шаблон ADR |
| `research/` | A | Исследования — обзоры, сравнения, замеры. Реестр (`CORE-RSH-REGISTRY.md`) — карта исследований. Задания ресерч-чату, шаблоны исследований |
| `diary/` | A | Дневники сессий — один файл на сессию |
| `research/` | A | Исследования — обзоры, сравнения, замеры. Реестр (`CORE-RSH-REGISTRY.md`) — карта исследований. Задания ресерч-чату |
| `templates/` | B | Шаблоны артефактов (ADR, исследование, задание, отчёт о завершении) |

**Правило папки.** Файлы группируются в папку по назначению, когда
их становится много. Пока файлов мало — лежат плоско, на уровень
выше. Примеры: ADR — в `decisions/`, исследования — в `research/`,
дневники — в `diary/`. У утилиты документов много и разного
назначения — поэтому `docs/`; у Core только документы и их мало —
поэтому плоско.

**Правило копий.** Документ (файл) хранится в одном месте; копии
не создаются. Состав пакета для чата — раздел 6.

**Порядок чтения для нового участника:** README (что за система) →
SPEC (контракт) → CORE-ARCH-data-model и CORE-ARCH-data-flow
(что действует) → handover (как работать). ADR и исследования —
по мере необходимости, через реестры.

### Документация утилит

Правила Core распространяются на утилиты. Документация утилиты
**дополняет** `handover.md` Core, а не повторяет его: общий порядок
работы (формат поста, режимы объёма, остановки, дневник) описан
в Core и в утилите не переписывается.

**Обязательные документы утилиты:**

| Документ | Класс | Что содержит |
|---|---|---|
| `handover.md` | B | Только то, что дополняет Core: специфика утилиты, порядок переноса контекста |
| `<UTIL>-SPEC.md` | B | Описание утилиты: назначение, функции, состав данных, поведение. Не контракт экосистемы; обязательна ссылка на версию контракта Core (`Контракт — KIP_Core vX.Y`) |
| ADR | A | Имя файла с префиксом утилиты: `<UTIL>-ADR-NNN-<тема>.md` (например, `READER-ADR-001`) — источник однозначен при передаче в Core. Реестр ADR обязателен (`<UTIL>-ADR-REGISTRY.md`) |
| дневник | A | Обязателен; имя `YYYY-MM-DD-diary.md`, формат задаёт Core |

**Документы по наличию работы** (если ведутся — правила те же,
что в Core):

- архитектурный документ — дистилляция ADR утилиты,
  `docs/architecture/`, класс B;
- исследования — `docs/research/` + реестр (`<UTIL>-RSH-REGISTRY.md`),
  класс A, имена файлов с префиксом утилиты
  (`READER-RSH-NNN-<тема>.md`);
- `CHANGELOG.md` — если у утилиты есть версии кода;
- `README.md` — визитка: назначение, функции, принципы.

**Правила документации, задаваемые Core:**

- У утилиты документация — в папке `docs/`. У Core — плоско, без
  `docs/`: в Core нет кода, только документы.
- Имена файлов и папок — латиницей, строчными буквами через дефис;
  исключение — префикс и устоявшиеся имена (см. раздел 1).
- Документы утилиты в имени содержат префикс `<UTIL>-` — 2–6 латинских
  букв в верхнем регистре, узнаваемо указывающих на утилиту (например,
  `READER-`, `REG-`). Если имя утилиты длиннее 6 букв, используется
  узнаваемое сокращение; оно фиксируется в handover утилиты.
- Классы документов (A / B / C) — как в Core.
- Реестры для папок с тематическими и append-only документами —
  как в Core (`CORE-ADR-REGISTRY.md`, `CORE-RSH-REGISTRY.md`);
  у утилиты — с её префиксом (`READER-ADR-REGISTRY.md`).
- Архитектурных документов может быть несколько, по темам (обзор,
  БД, ядро, UI, алгоритмы). Реестр архитектурных документов —
  по общему правилу реестров.

**Граница решений.** ADR утилиты не может изменить контракт Core.
Если решение требует изменения модели — это запрос в Core, а не ADR
утилиты.

Контракт в handover — всегда контракт Core. `<UTIL>-SPEC.md`
контрактом экосистемы не является: он описывает утилиту для неё
самой, другие чаты с ним не сверяются.

**Чего Core не задаёт:** имена папок, зависящие от стека (`src/`,
`tests/`, `scripts/` и т.п.) — это решение утилиты.

## 6. Протокол передачи контекста

Протокол отвечает на вопрос: что приложить к заданию, чтобы получатель
работал с моделью Core, а не переизобретал её.

### Пакет для получателя

**Обязательный минимум:** задание и шаблон ответа. Шаблон зависит
от типа задания: исследование — шаблон исследования, работа
утилиты — шаблон отчёта о завершении.

**Дополнения** (handover Core, архитектурные документы Core —
`CORE-ARCH-data-model.md` и `CORE-ARCH-data-flow.md`, реестр
ADR Core, реестр исследований Core, `<UTIL>-SPEC.md` утилиты, её код
и тесты, существующие исследования) — не обязательны. Их определяет
управляющий чат Core под конкретное задание и сообщает арбитру,
что приложить.

Получатель **не переписывает модель Core** в своих документах.
В `<UTIL>-SPEC.md` и архитектурном документе, которые он создаёт, —
ссылка на версию контракта Core и архитектурные документы Core,
а не копия модели.

### Выход ресерч-чата

- **Файл исследования** — имя `CORE-RSH-NNN-<тема>.md`. Номер
  присваивается при создании: следующий после последнего
  существующего файла. Структура: вопрос, варианты, критерии,
  сравнение, вывод, источники.
- **Резюме** (7–10 строк — ориентир) — возвращается в управляющий
  чат Core для принятия решения. Если важное не влезает, резюме
  может быть длиннее; сокращать за счёт выводов нельзя. Резюме
  **не** заменяет ADR: если по итогам исследования принято
  архитектурное решение, управляющий чат оформляет ADR отдельно.

### Формат передачи документа человеку

Любой документ, который передаётся человеку для чтения (ADR, SPEC,
исследование, задание, отчёт), отдаётся одним блоком Markdown:
четыре обратные кавычки и слово `markdown` в начале, четыре
обратные кавычки в конце. Внутри блока могут быть свои блоки кода
(тройные кавычки) — они не конфликтуют с внешней обёрткой. Это нужно,
чтобы текст не рвался при копировании и вставке в файл.

Перед блоком указывается имя файла. Папку для сохранения арбитр
определяет по правилу расположения файлов обмена (раздел 4).

**Фрагменты.** Если передаётся не документ целиком, а фрагмент
для замены (раздел, подраздел), действуют те же правила: один
блок Markdown, перед блоком — имя файла и явная пометка, какой
раздел заменяется (например: «Файл: …, раздел `### X` —
исправленный текст»). Фрагмент не является документом и не
требует полного текста, но формат блока — тот же.

### Версия контракта в пакете

Утилита в своём `<UTIL>-SPEC.md` указывает версию контракта Core
(Git-тег), с которой работает. Если Core обновился до новой версии,
а утилита — нет, это видно сразу: в `<UTIL>-SPEC.md` стоит старая
версия. Обновление утилиты — осознанное действие (прочитать diff
ADR, решить, обновляться или нет).

### Если управляющий чат недоступен

Протокол выше описывает нормальную работу: управляющий чат ведёт
вас, вы прикладываете файлы, получаете результат.

Если управляющий чат недоступен (достигнут лимит, чат закрылся,
начинаете с нуля) — откройте `HUMAN-GUIDE.md` — инструкции
для арбитра.

## 7. Версионирование контракта

Контракт Core имеет версию. Версия — это Git-тег в репозитории
`KIP_Core` (`v1.0`, `v1.1`, `v2.0`). Версия фиксирует состояние
`SPECIFICATION.md` на момент выпуска.

### Где хранится номер версии

Номер версии хранится в шапке `SPECIFICATION.md` (поле «Версия
контракта»). До первой передачи контракта потребителю тег
отсутствует, в SPEC указана текущая редакция. После первой
передачи Git-тег с тем же номером (`v1.0`) фиксирует состояние
репозитория на момент выпуска; тег и номер в SPEC должны
совпадать — расхождение является ошибкой выпуска и исправляется
новым коммитом.

Отдельного файла `VERSION` в Core нет: SPEC — единственный источник
номера. В утилитах, где есть код, номер может дублироваться в
`version.py` (как в Register) — это ответственность утилиты.

### Что меняет версию контракта, а что нет

Версия нужна потребителю: она фиксирует состояние контракта, с которым
работает утилита.

**До первой передачи:** `SPECIFICATION.md` правится свободно, номер
версии не меняется. Версия фиксируется тегом в момент первой передачи
контракта потребителю.

**После первой передачи:** версия меняется при **любом изменении
`SPECIFICATION.md`** — потребитель должен видеть, с чем работает.

ADR сам по себе версию не меняет: он — триггер. Цепочка: ADR принят →
SPEC обновлён → (если контракт уже передан) новая версия и тег.

Версия **не меняется** при изменении:
- README (описание системы);
- handover (процесс работы);
- архитектурных документов (они следуют за ADR);
- реестров ADR и исследований (они карты, а не содержание);
- шаблонов.

Если сомневаетесь — задайте вопрос в управляющем чате Core.

### Архитектурные документы и версия

Архитектурные документы — производные от ADR. Они обновляются
после принятия ADR, от которого зависят, и при выпуске версии
приводятся в соответствие с SPEC. Сами по себе правки
архитектурного документа версию не меняют.

### Когда меняется версия

- **После первой передачи контракта:** любое изменение контракта
  (новая сущность, новое поле, изменение связи, изменение формата
  обмена, изменение состава экосистемы, границ ответственности,
  правил интерфейса) — новая версия.
- **Исправление опечатки или уточнение формулировки**, не меняющее
  смысл, — версия не меняется (правится SPEC с пометкой
  об уточнении).

### Кто ставит версию

Только управляющий чат Core. Утилита не может «выпустить» новую
версию контракта — она может только предложить изменение через
управляющий чат Core (новый ADR).

### Как утилита принимает новую версию

1. В `<UTIL>-SPEC.md` указана версия контракта, с которой она
   работает: `Контракт — KIP_Core v1.0 (тег v1.0)`.
2. При выходе новой версии Core (например, v1.1) утилита **не
   обновляется автоматически**. Ответственный за утилиту читает
   diff (какие ADR добавлены или изменены), решает, совместимо ли
   изменение, и обновляет `<UTIL>-SPEC.md`.
3. Если утилита не обновилась, это видно по её `<UTIL>-SPEC.md`:
   там старая версия. Это не ошибка, а осознанное состояние —
   утилита работает со старой моделью, пока не будет готова
   перейти на новую.

### Совместимость версий

- **Мажорная версия** (`v1.0` → `v2.0`) — ломающее изменение.
  Утилита не сможет работать без обновления.
- **Минорная версия** (`v1.0` → `v1.1`) — добавление, не ломающее
  существующие поля и связи. Утилита может продолжать работать
  со старой версией, но не увидит новых возможностей.

Конкретное правило (что считать ломающим) фиксируется в SPEC
при выпуске версии.

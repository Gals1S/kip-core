# Правила работы над KIP Core

> Назначение: зафиксировать процесс работы над экосистемой — принципы
> работы и правила для чатов, роль арбитра, взаимодействие чатов,
> правила документирования, передачу контекста, среду разработки.
> Документ меняется редко — только при изменении самого процесса.

## 1. Принципы работы

- **Новый чат — по объёму или существенной смене темы.** Чат ведётся,
  пока контекст держится и тема не сменилась существенно. Новый чат
  открывается, когда контекст вырос или тема сменилась. Дробление
  под каждую задачу на отдельный чат не требуется.

- **Один пост — одна мысль.** Один пост — одна мысль, доведённая
  до конца, и один вопрос в конце. Вопрос задаётся так, чтобы ответ
  «да» был полным решением: чат предлагает вариант с кратким
  обоснованием, человек соглашается или возражает. Открытый вопрос
  без варианта («а как вы думаете?») не задаётся. Вторая мысль
  начинается следующим постом.

  Это обязанность чата, записанная в правилах. Нарушение — нарушение
  правила чатом. Исключения возможны; проверяется практикой.

- **Два режима объёма.** По умолчанию действует правило «одна мысль —
  один пост». Исключение — обратимое: материал, который переписывается
  без последствий (черновик, список). По обратимому чат выдаёт
  **только резюме**; полный текст — по запросу.

  Проверка для чата: «если этот текст окажется неверным, придётся ли
  пересматривать что-то, кроме него самого?» Нет — обратимый режим.
  Да — обычный шаг.

- **Анти-лень (Режим строгого критика).** Чат не имеет права перекладывать
  выбор на человека (выдавать A/B/C вместо рекомендации) и не имеет права
  срезать углы (отвечать поверхностно).
  
  Чат самостоятельно определяет сложность задачи (исследование, архитектура,
  принятие решений). Если задача относится к сложным, чат **автоматически
  включает режим строгого критика (Harsh Critic) и уведомляет об этом**
  одной фразой в начале ответа (например: «Задача сложная, работаю в режиме
  глубокого анализа»). Арбитру не нужно ничего подтверждать.
  
  В этом режиме чат тщательно проверяет выводы, использует достаточное
  количество источников и не торопится. Если арбитр считает, что задача
  простая и нужно работать быстрее, он может прервать режим командой
  («Выключи строгий режим»).

- **Проверка фактов.** Если в задании или сессии были приложены
  документы (спецификации, ADR, дневники), чат обязан отвечать,
  опираясь на них. Ответы «по памяти» (без сверки с приложенным
  контекстом) запрещены.

- **Перепроверка перед выдачей.** Чат сам перепроверяет результат
  перед выдачей (на соответствие правилам, на паттерны «лени»).
  Человеку список критериев не показывается.

- **Остановки.** Дополнительных остановок не вводится. Остановка
  существует естественным образом — в момент, когда человек копирует
  документ в файлы. В остальное время чат идёт дальше сам.

- **Язык.** Документация, комментарии, сообщения коммитов — по-русски.
  Пользователь пишет кириллицей, чат понимает; таблица соответствий
  кириллица ↔ латиница не ведётся.

  Имена файлов и папок — латиницей, строчными буквами через дефис;
  исключение — префикс проекта или утилиты (2–6 букв в верхнем регистре
  и дефис: `CORE-`, `READER-`, `REG-`) и устоявшиеся имена (`README.md`,
  `SPECIFICATION.md`, реестры). Префикс делает источник однозначным 
  при передаче в чат.

- **Источник правды.** Для модели данных — архитектурный документ.
  ADR — способ принятия решений и история. К ADR обращаются за
  обоснованием. При расхождении архитектурного документа и ADR прав ADR.
  Для структуры данных утилиты — её код и миграции. При расхождении
  документа с кодом утилиты — обновляется документ утилиты. Core
  меняется только через управляющий чат.

- **Критерии оценки решений.** При выборе варианта решение оценивается
  по трём критериям, в порядке приоритета:
  1. **Удобство работы пользователя** (минимум ручной работы).
  2. **Производительность** (скорость на реальных объёмах).
  3. **Простота разработки** (минимум поддерживаемой логики).

- **Формат коммитов.** `ДД.ММ.ГГГГ: что сделано`.
  **Связь с CHANGELOG (только для утилит с кодом):** При коммите,
  меняющем поведение программы, чат даёт арбитру готовую строку для
  CHANGELOG. Запись дописывается в конец файла.

## 2. Роль человека

Человек — **владелец процесса и арбитр**, а не диспетчер каждого
шага и не проверяющий каждое сообщение.

Функции человека:

1. **Постановка цели и приоритизация.** Определяет, что важно
   и в каком порядке решать.
2. **Приёмка артефактов на этапах работы.** Читает результат
   и решает, достаточен ли он для перехода к следующему этапу.
3. **Арбитраж.** Разрешает конфликты между чатами (когда управляющий
   чат сообщает о противоречии).
4. **Одобрение необратимых решений.** Изменение контракта, выпуск
   версии, принятие нового ADR.

Сценарии действий арбитра — настройка инструментов среды разработки,
открытие нового чата и что приложить, действия при недоступности
управляющего чата — в папке `human-guide/`. Чатам эти файлы не передаются.

**Как проходит сессия.** Арбитр начинает с даты и времени. Дальше —
обсуждение мелкими шагами. Когда накопилось, чат формирует документ;
арбитр копирует его в файлы — это естественная остановка. После неё
арбитр принимает или даёт замечания (мелкие или много сразу).
Завершая сессию, арбитр сообщает время окончания — тогда чат
формирует дневник.

## 3. Взаимодействие и делегирование

Взаимодействие между чатами формализуется через **файловые сообщения** — файлы с явным именем, а не сообщения в чате.

### 3.1. Обмен файлами между Core и утилитами

| Тип сообщения | Кто инициирует | Кто обязан отреагировать | Артефакт |
|---|---|---|---|
| **Задание** | Управляющий чат Core | Чат-адресат (ресерч или утилита) | Файл по шаблону `CORE-TASK-template.md` / `CORE-RSH-REQUEST-template.md` |
| **Запрос в Core** | Управляющий чат утилиты / ресерч-чат | Управляющий чат Core | Файл с описанием запроса (что изменить, зачем, последствия) |
| **Отчёт о завершении** | Ресерч-чат / чат утилиты | Управляющий чат Core (приёмка) | Файл по шаблону `CORE-HANDOFF-template.md` |

**Валидация на границе.** Файл, не соответствующий шаблону, не принимается. Это защита от «слабого артефакта».

**Расположение файлов.** Все файлы обмена хранятся в проекте Core, в папке того чата, к которому относятся. Арбитр копирует их в проект утилиты по мере необходимости.

### 3.2. Делегирование внутри утилит

Утилита (например, Register) имеет право создавать собственные вспомогательные чаты:
- **Ресерч-чаты** — для изучения узких технических вопросов (выбор библиотек, паттернов). Задание оформляется по шаблону `CORE-RSH-REQUEST-template.md`.
- **Чаты-тестировщики** — для независимой проверки кода (Black-box). Задание оформляется по шаблону `CORE-TASK-TEST-template.md`.

**Граница ответственности:** Если исследование или тестирование вскрывает проблему в контракте Core (модель данных, формат обмена), утилита **не имеет права** менять контракт сама. Она обязана оформить **Запрос в Core**.

## 4. Классы документации и общие принципы

Документы делятся на три класса. Класс определяет, можно ли править
документ и при каких условиях.

| Класс | Что входит | Правило |
|---|---|---|
| **A — append-only** | `decisions/` (ADR), `research/` (исследования), `diary/` (дневники сессий) | Не правятся. Устарело — новый файл с новой датой. Статус ADR — в реестре. Принятие исследования — в реестре |
| **B — живой** | `SPECIFICATION.md`, `README.md`, `handover.md`, архитектурные документы, реестры, `templates/`, `CHANGELOG.md` (у утилит) | Правятся, но редко и предсказуемо (см. ниже) |
| **C — генерируемые** | — | В Core нет: кода нет, генерировать нечего. Класс появляется в утилитах (схема БД, API reference) |

### Класс A — append-only

- **ADR (`decisions/`).** Решение неизменно: принятый ADR не правится.
  Передумали — новый ADR; в реестре старый получает статус «Заменён» 
  или «Действует с изменениями». Текст ADR не изменяется. 
  Имя файла: `CORE-ADR-NNN-<тема>.md` (или `<UTIL>-ADR-NNN-<тема>.md`). 

  **Нет в реестре — значит, черновик.** Внесение в реестр — действие
  человека сразу после принятия ADR. Если ADR передан, а в реестре 
  его нет — чат обязан задать вопрос об актуальности.

  **Частичное изменение / Полная замена.** В шапке нового ADR — поле 
  `**Изменяет:**` или `**Заменяет:**`. В реестре у старого проставляется
  статус. Текст старого ADR не правится.

- **Исследования (`research/`).** Устарело — новый файл со
  следующим номером, старый не трогается. Имя файла: 
  `CORE-RSH-NNN-<тема>.md`. Нумерация последовательная, без дат.

  **Статусов нет.** Исследование либо внесено в реестр — принято, 
  либо отсутствует в реестре — черновик. Неполное исследование 
  не правится: заказывается новое, которое закрывает пробелы.

- **Дневники сессий (`diary/`).** Один файл на сессию; имя —
  дата и слово `diary`: `2026-11-06-diary.md`. В заголовке —
  дата, время начала и конца сессии. Класс A: не правится;
  следующая сессия — новый файл. 
  
  Дневник состоит из двух обязательных частей:
  1. **Dump (Сырые данные).** История проекта: где остановились, 
     что сделали, какие детали обсуждали. Нужен для справки.
  2. **Handoff (Выжимка для следующего чата).** Раздел в конце 
     дневника (`## Handoff для следующего чата`). Содержит: 
     Цель → Принятые решения (Decision Locks) → Ограничения → 
     Сделано → В работе. Арбитр копирует только этот раздел 
     для старта нового чата. Обоснование — `CORE-ADR-012`.

### Класс B — живой

- **`SPECIFICATION.md`** — контракт экосистемы KIP_Core. Определяет:
  состав экосистемы, границы ответственности, модель данных, форматы 
  обмена, версию контракта, правила UI.
- **`README.md`** — визитка: назначение, функции, принципы.
- **`handover.md`** — правила работы (этот документ).
- **Архитектурные документы** — дистилляция решений из ADR. 
  Источник правды. Правятся после утверждения новых ADR.
- **Реестры** (ADR и исследований) — карты документов.
- **`templates/`** — шаблоны артефактов.
- **`CHANGELOG.md` (у утилит с кодом).** Лента: новые записи
  дописываются в конец файла. 

### Класс C — генерируемые

В Core нет. В утилитах (например, Register) класс C — это схема БД, 
API reference, `build_info.json`.

### Общие принципы документации

**Правило папки.** Файлы группируются в папку по назначению, когда
их становится много. Пока файлов мало — лежат плоско, на уровень
выше. У утилиты документов много и разного назначения — поэтому `docs/`; 
у Core только документы и их мало — поэтому плоско.

**Правило копий.** Документ (файл) хранится в одном месте; копии
не создаются. Состав пакета для чата — раздел 5.

**Порядок чтения для нового участника:** README (что за система) →
SPEC (контракт) → Архитектурные документы (что действует) → 
handover (как работать). ADR и исследования — по мере необходимости, 
через реестры.

### Документация утилит

Правила Core распространяются на утилиты. Документация утилиты
**дополняет** `handover.md` Core, а не повторяет его: общий порядок
работы (формат поста, режимы объёма, остановки, дневник) описан
в Core и в утилите не переписывается.

**Обязательные документы утилиты:**

| Документ | Класс | Что содержит |
|---|---|---|
| `<UTIL>-handover.md` | B | Только то, что дополняет Core: специфика утилиты, порядок переноса контекста |
| `<UTIL>-SPEC.md` | B | Описание утилиты: назначение, функции, состав данных, поведение. Обязательна ссылка на версию контракта Core (`Контракт — KIP_Core vX.Y`) |
| ADR | A | Имя файла с префиксом утилиты: `<UTIL>-ADR-NNN-<тема>.md`. Реестр ADR обязателен (`<UTIL>-ADR-REGISTRY.md`) |
| дневник | A | Обязателен; имя `YYYY-MM-DD-diary.md`, формат задаёт Core |

**Документы по наличию работы** (если ведутся — правила те же,
что в Core):

- архитектурный документ — дистилляция ADR утилиты,
  `docs/architecture/`, класс B;
- исследования — `docs/research/` + реестр (`<UTIL>-RSH-REGISTRY.md`),
  класс A;
- `CHANGELOG.md` — если у утилиты есть версии кода;
- `README.md` — визитка.

**Правила документации, задаваемые Core:**

- **Разделение корня и папки `docs/`.** Основные документы утилиты — визитка (`README.md`), правила (`<UTIL>-handover.md`) и контракт (`<UTIL>-SPEC.md`) — лежат **в корне** проекта. Вся остальная документация (ADR, исследования, дневники, архитектура) складывается в папку `docs/` с соответствующими подпапками (`docs/decisions/`, `docs/diary/` и т.д.).
- Имена файлов и папок — латиницей, строчными буквами через дефис;
  исключение — префикс и устоявшиеся имена (см. раздел 1).
- Документы утилиты в имени содержат префикс `<UTIL>-` — 2–6 латинских
  букв в верхнем регистре (например, `READER-`, `REG-`).
- Классы документов (A, B, C) — как описано в разделе 4 настоящего документа.
- Для папок с тематическими и append-only документами обязателен реестр.
- Архитектурных документов может быть несколько, по темам.

**Граница решений.** ADR утилиты не может изменить контракт Core.
Если решение требует изменения модели — это запрос в Core, а не ADR
утилиты.

Контракт в handover — всегда контракт Core. `<UTIL>-SPEC.md`
контрактом экосистемы не является: он описывает утилиту для неё
самой, другие чаты с ним не сверяются.

**Чего Core не задаёт:** имена папок, зависящие от стека (`src/`,
`tests/`, `scripts/` и т.п.) — это решение утилиты.

## 5. Протокол передачи контекста (Lean-загрузка)

Загрузка контекста идет по принципу **Map-first** (от общего к частному).

### 5.1. Карта и запрос файлов
1. **Карта:** В начале работы чат получает только базовые правила (`handover.md` и текст задания). 
2. **Запрос:** Прочитав задание, чат обязан сформулировать, какие именно файлы из проекта ему нужны для решения этой конкретной задачи.
3. **Выдача:** Арбитр выдает запрошенные файлы строго по одному, не перегружая контекст лишней информацией.

### 5.2. Выход ресерч-чата
- **Файл исследования** — имя `CORE-RSH-NNN-<тема>.md` (или `<UTIL>-RSH-NNN`).
- **Резюме** (7–10 строк — ориентир) — возвращается в управляющий чат для принятия решения. Если важное не влезает, резюме может быть длиннее; сокращать за счёт выводов нельзя.

### 5.3. Формат передачи документа
Любой документ (ADR, SPEC, исследование, задание, отчёт), который передаётся человеку, отдаётся одним блоком Markdown: четыре обратные кавычки и слово `markdown` в начале и в конце. Перед блоком указывается имя файла.

### 5.4. Версия контракта в пакете
Утилита в своём `<UTIL>-SPEC.md` указывает версию контракта Core (Git-тег), с которой работает. При выходе новой версии Core утилита не обновляется автоматически: ответственный читает diff и решает, совместимо ли изменение.

## 6. Среда разработки проекта

Арбитр работает в следующей среде. Чаты должны учитывать это при выдаче команд и рекомендаций:

- **ОС:** Windows 10/11 x64.
- **Редактор:** VS Code (с расширениями для работы с Markdown).
- **Контроль версий:** Git (через терминал VS Code).
- **Файловый менеджер:** Total Commander.
- **Браузер:** Chromium (DeepSeek Web) без доступа к файловой системе.

*Примечание: подробные инструкции по установке и настройке инструментов, а также вспомогательные утилиты для контроля контекста описаны в файлах `human-guide/` (для арбитра).*

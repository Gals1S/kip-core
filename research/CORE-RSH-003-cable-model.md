## 1. Контекст и уточнение по экосистеме утилит

Планируется группа утилит для инженеров КИП:

1. **KIP Reader** — читает принципиальные схемы, сохраняет данные в табличном формате.
2. **KIP Register** — накапливает, обогащает и хранит данные приборов.
3. **Будущий KIP Generator** — на основе данных из Register (выгруженных в табличном формате) создаёт документы: схемы электрических соединений, возможно чертежи установки КИП.

**Ключевое уточнение:** прямые связи (API, общая БД) между утилитами **не предполагаются**. Обмен — только через **табличные файлы** (CSV/Excel). Register, как и Reader, на выходе даёт табличные данные; Generator забирает их и, возможно, сравнивает с существующими схемами.

**Что это значит для текущего ресерча:** Register не должен «подстраиваться» под будущий Generator на уровне API. Но формат выгрузки должен быть **достаточно полным и предсказуемым**, чтобы Generator мог на его основе построить схему соединений. Перечень кабелей с составом сигналов — один из таких выходных форматов.

**Разделение ответственности (обсуждалось, см. раздел 7):** Register работает с «логическим» кабелем (откуда, куда, индекс, привязка к сигналам), Generator — с «физическим» (марка, тип, экран, броня, огнестойкость). Это соответствует стадийности реального проектирования (Basic/Conceptual → Detailed).

**Стадийность и детализация «Куда» (обсуждалось, см. раздел 3.2):** на раннем этапе конкретная точка подключения (шкаф/коробка) может быть неизвестна — известна только подсистема (РСУ/ПАЗ/ПЛК). Модель должна допускать это без принудительного указания точки.

## 2. Чего не хватает текущей модели

В ADR-004 группа «Электрические подключения» на уровне прибора содержит:

| Поле | Что хранит |
|---|---|
| Принадлежность к системе | РСУ, ПАЗ, ПЛК |
| Индекс кабеля | Номер кабеля |
| Марка кабеля | Например, `СКАБ 250нг(А)-HF` |
| Типоразмер | Сечение/жилы |
| Куда | Точка подключения |

**Что уже работает:** можно ответить на вопрос «какие приборы подключены кабелем X» (если считать, что кабель связан с прибором целиком).

**Чего не хватает для перечня кабелей с составом сигналов:**

1. **Связь «кабель ↔ сигнал».** Сейчас кабель привязан к прибору целиком, а не к конкретному сигналу. У клапана 5 сигналов, часть может идти по одному кабелю, часть — по другому. Текущая модель скажет «клапан подключён кабелями C-101 и C-102», но не скажет, **какой сигнал в каком кабеле**.
2. **Кабель как самостоятельная сущность.** Марка, типоразмер, «куда» сейчас дублируются для каждого прибора. Если кабель один — дублирования нет; но если у прибора несколько кабелей — дублирование и риск расхождения.
3. **Корректная модель «две точки».** Уточнено: **кабель имеет две точки подключения** и не может быть подключён к двум приборам одновременно. Кабель может идти от прибора к шкафу/коробке **или от прибора к прибору**. Это меняет модель: у кабеля есть «откуда» (прибор или точка подключения) и «куда» (прибор или точка подключения), но всего две точки.
4. **Необязательность «Куда» на раннем этапе.** На стадии предварительного проектирования конкретная точка подключения часто неизвестна — известна только подсистема. Модель должна допускать кабель без `to_point_id`, с указанием подсистемы.

## 3. Предлагаемое расширение модели

### 3.1. Кабель как самостоятельная сущность

Выносим кабель в отдельную таблицу проекта. У кабеля — уникальный в рамках проекта индекс, «откуда» и «куда».

- **«Откуда»** — ссылка на прибор или точку подключения (обязательно; это точка, от которой идёт кабель).
- **«Куда»** — ссылка на прибор или точку подключения (на раннем этапе может быть не указана — вместо неё подсистема; см. 3.2).
- **Две точки:** кабель не может иметь два «откуда» или два «куда».

**Что хранится в Register (обсуждалось, см. раздел 7):** только «логические» атрибуты — индекс, «откуда», «куда», привязка к сигналам. «Физические» атрибуты (марка, типоразмер, экран, броня, огнестойкость) — зона ответственности Generator.

### 3.2. Точки подключения («Куда» и «Откуда») и подсистема на раннем этапе

**Рассматривался вопрос:** нужны ли отдельные сущности для шкафов, клеммных коробок, панелей, или достаточно одного справочника с типом.

**Варианты:**

**Вариант A. Отдельные справочники для каждого типа** (`cabinets`, `junction_boxes`, `panels`).
- Плюс: можно хранить разные поля для разных типов.
- Минус: дублирование полей, усложнение запросов («покажи все точки подключения проекта» — union по трём таблицам), усложнение UI (три выпадающих списка).

**Вариант B. Один справочник «точки подключения» с полем `тип`** (`шкаф`, `клеммная коробка`, `панель`).
- Плюс: проще для запросов, UI, импорта. Единый список с фильтром по типу.
- Минус: поля, специфичные для одного типа, будут пустыми для других (но для лёгкого Register это приемлемо).

**Вариант C. «Шкаф» как тип прибора** (в той же таблице `instruments`).
- Плюс: не нужно создавать новую сущность.
- Минус: шкаф попадёт в реестр КИП, на него начнут действовать трёхуровневая модель, аудит характеристик, импорт из Reader — всё, что для шкафа избыточно. Смешивать средства измерения и элементы инфраструктуры в одной таблице — значит засорять реестр приборов.

**Приоритетным представляется Вариант B** — один справочник с типом. Он соответствует практике моделирования инженерных активов (в AVEVA `equipment definitions` включают шкафы, клеммные коробки и полевые устройства в одной модели, различаясь типом) и проще для лёгкого Register.

**Минимальный набор полей для «точки подключения» (для обсуждения):**

| Поле | Зачем |
|---|---|
| `тип` | `шкаф` / `клеммная коробка` / `панель` |
| `обозначение` | «Шкаф РСУ1», «КК-5» |
| `проект` | Принадлежность проекту |

**Номер панели/слота** — обсуждался. В практике AVEVA это `marshalling cabinet card slot`, но для лёгкого Register представляется избыточным: при необходимости можно использовать сущность «панель» вместо «шкаф», или хранить номер в обозначении как часть строки («Шкаф РСУ1, панель 3»).

**Ёмкость точки подключения** — обсуждалась. Варианты: (а) хранить `ёмкость жильных клемм`, `ёмкость клемм экранов`, `ёмкость клемм брони` в справочнике; (б) не хранить, а вычислять из кабелей, приходящих в точку.

**Приоритетным представляется вариант (б)** — не хранить ёмкость в справочнике. Ёмкость — это производная величина: количество кабелей и жил, приходящих в точку, считается запросом. Хранение ёмкости в справочнике создаёт риск расхождения («в справочнике 30 клемм, а по факту 32»). Контроль переполнения возможен сравнением вычисленного числа с паспортной ёмкостью, если её хранить опционально (как справочное поле, не обязательное для работы).

#### 3.2.1. Подсистема вместо точки подключения на раннем этапе

**Контекст.** На стадии предварительного проектирования (Basic/Conceptual) конкретная структура подключения — какой именно шкаф, клеммная коробка, слот — часто ещё не определена. Известно только, **в какую подсистему** (РСУ, ПАЗ, ПЛК) пойдёт кабель. Требование обязательно указывать точку подключения на этом этапе искусственно усложняет учёт.

**Практика подтверждает:** в кабельных журналах на предварительных стадиях в графе «To» нередко указывают подсистему или тип панели (например, «Marshalling panel», «DCS»), а конкретный шкаф и клеммник появляются позже, на стадии детального проектирования. В инженерной литературе прямо признаётся: «на этом этапе вы не знаете точную трассировку, размеры и детальный электротехнический дизайн» — и это нормально, цель ранней стадии — зафиксировать связи и оценить объёмы.

**Рассмотренные варианты:**

**Вариант 1. Оставить `to_point_id` обязательным для каждого кабеля.**
- Плюс: единообразие.
- Минус: на раннем этапе инженер вынужден «придумывать» точку, которой ещё нет, или откладывать ввод кабеля.

**Вариант 2. Сделать `to_point_id` необязательным; на раннем этапе указывать подсистему.**
- Плюс: соответствует стадийности проектирования; не заставляет инженера фиксировать несуществующую точку.
- Минус: на раннем этапе нельзя построить полный монтажный перечень по шкафам (но это и не требуется — это задача Generator).

**Вариант 3. Убрать справочник точек подключения полностью, оставить только подсистему.**
- Плюс: максимальное упрощение.
- Минус: теряется возможность детализировать подключение до конкретного шкафа/коробки — а это нужно на стадии Generator и для перечня кабелей по шкафам.

**Приоритетным представляется Вариант 2.** Справочник точек подключения **остаётся**, но `to_point_id` становится **необязательным**. На раннем этапе вместо него может быть указана **подсистема** — из того же справочника систем управления (РСУ/ПАЗ/ПЛК), что уже есть на уровне сигнала (ADR-004). Когда структура подключения проясняется, инженер заменяет подсистему на конкретную точку; история изменений (ADR-003) фиксирует это уточнение.

**Следствия для модели:**

- Отдельный справочник подсистем для кабелей **не нужен** — используется существующий справочник систем управления (`control_systems` из ADR-004).
- У кабеля может быть заполнено **либо** `to_point_id`, **либо** `to_system_id` (подсистема). Не оба одновременно (или оба — если подсистема известна, а точка ещё нет; см. открытый вопрос ниже).
- Подсистема кабеля может также **вычисляться** из сигналов, привязанных к кабелю (если все сигналы принадлежат одной подсистеме). Это ещё больше упрощает модель: явное хранение `to_system_id` нужно только тогда, когда кабель идёт в подсистему, отличную от подсистемы сигналов, или когда сигналы ещё не привязаны.

**Открытый вопрос:** нужно ли хранить `to_system_id` явно у кабеля, или достаточно вычислять его из сигналов? Аргументы за явное хранение: (а) кабель может быть создан до привязки сигналов; (б) кабель может идти в подсистему, отличную от подсистемы всех его сигналов (например, транзитный). Аргументы за вычисление: проще модель, меньше полей. Для обсуждения в управляющем чате.

### 3.3. Связь «кабель ↔ сигнал»

Отдельная таблица-связка: для каждого кабеля — список сигналов (с указанием прибора и префикса сигнала), которые по нему идут. Это позволяет строить перечень кабелей с составом сигналов и вычислять число занятых жил (см. раздел 9).

**Обсуждение привязки к жилам** — см. раздел 8.

**Ограничение:** сигналы в одном кабеле должны принадлежать прибору, указанному в «откуда» (если «откуда» — прибор). Если сигналы идут от нескольких приборов, они сначала агрегируются в клеммной коробке, и уже от неё идёт отдельный кабель.

### 3.4. Согласование с ADR-006 (пункт 7)

В ADR-006 записано: «индекс кабеля — справочная строка с проверкой на дубликаты, но без жёсткой уникальности "один кабель — один прибор"». **Это корректируется:** кабель **имеет две точки и не подключается к двум приборам**.

- **Индекс кабеля уникален в рамках проекта** (один кабель — одна запись).
- **Один кабель — два конца** (откуда и куда), каждый — либо прибор, либо точка подключения (на раннем этапе «куда» может быть подсистемой).
- Сигналов в кабеле может быть **несколько** — все от прибора в «откуда» (если «откуда» — прибор).
- Если у прибора несколько кабелей — это несколько записей в таблице кабелей, каждая со своим индексом.

## 4. Эскизы DDL и запросов

### 4.1. Таблицы (эскиз, не финальный DDL)

**`connection_points`** — точки подключения (шкафы, клеммные коробки, панели):

| Поле | Назначение |
|---|---|
| `id` | PK |
| `project_id` | Проект |
| `type` | `шкаф` / `клеммная коробка` / `панель` |
| `designation` | Обозначение («Шкаф РСУ1», «КК-5») |
| `created_at`, `updated_at`, `deleted_at` | Служебные |

**`control_systems`** — системы управления (РСУ, ПАЗ, ПЛК) — уже есть в ADR-004.

**`cables`** — кабели проекта:

| Поле | Назначение |
|---|---|
| `id` | PK |
| `project_id` | Проект |
| `index` | Индекс кабеля (уникален в рамках проекта) |
| `from_instrument_id` | «Откуда» — ссылка на прибор (nullable) |
| `from_point_id` | «Откуда» — ссылка на точку подключения (nullable) |
| `to_instrument_id` | «Куда» — ссылка на прибор (nullable) |
| `to_point_id` | «Куда» — ссылка на точку подключения (nullable) |
| `to_system_id` | «Куда» — подсистема (nullable; на раннем этапе, если точка неизвестна) |
| `created_at`, `updated_at`, `deleted_at` | Служебные |

**Ограничения (для обсуждения):**
- Ровно одна из пар `from_instrument_id`/`from_point_id` заполнена (у кабеля есть «откуда»).
- Для «куда»: заполнено **либо** `to_instrument_id`, **либо** `to_point_id`, **либо** `to_system_id`. Возможно сочетание `to_point_id` + `to_system_id` (если подсистема известна и точка известна) — открытый вопрос.
- Кабель не может иметь два «откуда» или два «куда».

**`cable_signals`** — связь «кабель ↔ сигнал»:

| Поле | Назначение |
|---|---|
| `id` | PK |
| `cable_id` | FK на `cables` |
| `signal_id` | FK на `signals` (сигнал прибора) |
| `order_index` | Порядок сигнала в кабеле (для отображения) |

**Ограничение:** сигнал `signal_id` должен принадлежать прибору `cables.from_instrument_id` (если «откуда» — прибор). Проверяется на уровне приложения.

**`signal_core_rules`** — справочник правил расчёта числа жил по типу и электрической характеристике сигнала (см. раздел 9):

| Поле | Назначение |
|---|---|
| `id` | PK |
| `signal_type` | `AI`, `AO`, `DI`, `DO` |
| `characteristic` | `I420`, `HART`, `DRY_NO`, `NAMUR`, `RTD_3W`, `RTD_4W`, … |
| `cores` | Число жил (1–4) |
| `note` | Примечание (для инженера) |

### 4.2. Пример запроса: перечень кабелей с составом сигналов

```sql
SELECT
    c.index,
    COALESCE(i.tag, cp.designation) AS from_point,
    COALESCE(i2.tag, cp2.designation, cs.designation) AS to_point,
    string_agg(
        s.prefix || ' (' || sc.name || ')',
        ', ' ORDER BY csig.order_index
    ) AS signals,
    SUM(r.cores) AS total_cores_used
FROM cables c
LEFT JOIN instruments i ON i.id = c.from_instrument_id
LEFT JOIN connection_points cp ON cp.id = c.from_point_id
LEFT JOIN instruments i2 ON i2.id = c.to_instrument_id
LEFT JOIN connection_points cp2 ON cp2.id = c.to_point_id
LEFT JOIN control_systems cs ON cs.id = c.to_system_id
LEFT JOIN cable_signals csig ON csig.cable_id = c.id
LEFT JOIN signals s ON s.id = csig.signal_id
LEFT JOIN signal_characteristics sc ON sc.id = s.characteristic_id
LEFT JOIN signal_core_rules r
       ON r.signal_type = s.signal_type
      AND r.characteristic = sc.code
WHERE c.project_id = :project_id
  AND c.deleted_at IS NULL
GROUP BY c.id, c.index, i.tag, cp.designation, i2.tag, cp2.designation, cs.designation
ORDER BY c.index;
```

### 4.3. Пример: вычисление занятости точки подключения

```sql
-- Сколько жил приходит в точку подключения X (по правилам signal_core_rules)
SELECT
    cp.designation,
    COUNT(DISTINCT c.id) AS cable_count,
    SUM(r.cores) AS total_cores
FROM cables c
JOIN connection_points cp ON cp.id = c.to_point_id
LEFT JOIN cable_signals csig ON csig.cable_id = c.id
LEFT JOIN signals s ON s.id = csig.signal_id
LEFT JOIN signal_characteristics sc ON sc.id = s.characteristic_id
LEFT JOIN signal_core_rules r
       ON r.signal_type = s.signal_type
      AND r.characteristic = sc.code
WHERE cp.id = :point_id
  AND c.deleted_at IS NULL
GROUP BY cp.designation;
```

### 4.4. Пример: кабели, идущие в подсистему (без конкретной точки)

```sql
SELECT c.index, i.tag AS from_instrument
FROM cables c
JOIN instruments i ON i.id = c.from_instrument_id
JOIN control_systems cs ON cs.id = c.to_system_id
WHERE cs.code = 'РСУ'
  AND c.to_point_id IS NULL
  AND c.deleted_at IS NULL
ORDER BY c.index;
```

## 5. Совместимость 

| Решение | Совместимость |
|---|---|
| **(трёхуровневая модель)** | Кабель — сущность **вне трёх уровней** (как документы, параметры процесса, электрика). Он не наследуется от модели или проекта, а вводится инженером. Модель прибора не меняется. |
| **(переопределения)** | Кабель — не характеристика прибора, а отдельная сущность. Переопределения на него не распространяются. |
| **(сигналы: тип и характеристика)** | Расчёт числа жил использует существующие поля `signal_type` (Уровень 2) и `characteristic` (Уровень 3) — без добавления новых полей в модель. |
| ** (системы управления)** | Подсистема кабеля использует существующий справочник `control_systems` (РСУ/ПАЗ/ПЛК) — отдельный справочник подсистем не создаётся. |
| **(аудит)** | Изменения кабелей аудируются: `field_name` = `cable.index`, `cable.from_instrument_id`, `cable.to_point_id`, `cable.to_system_id` и т.д.; `changed_by` — пользователь. Для связи «кабель ↔ сигнал» — аудит добавления/удаления сигнала из кабеля. |
| ** (импорт)** | Кабели могут импортироваться из Excel/CSV вместе с приборами; маппинг — по правилам ADR-006. Если в файле есть колонка «кабель», её значения создают/обновляют записи в `cables` и `cable_signals` (upsert по `(project_id, index)`). |
| **(пункт 7, корректировка)** | Индекс кабеля **уникален в рамках проекта**; один кабель — две точки (откуда и куда), каждая — прибор или точка подключения (на раннем этапе «куда» может быть подсистемой). Не «справочная строка с warning», а **полноценная сущность с уникальным индексом**. |

## 7. Кабель как «логическая» сущность: что в Register, что в Generator

### 7.1. Обсуждение

Рассматривался вопрос: хранить ли в Register физические свойства кабеля (марку, типоразмер, экран, броню, огнестойкость) или ограничиться «логическими» атрибутами (откуда, куда, индекс, привязка к сигналам).

**Аргументы за хранение физических свойств в Register:**
- В практике AVEVA Instrumentation все проектные кабели **обязательно** основываются на каталоге типов: свойства проекта (размер, число жил, тип) соответствуют «реальному» кабелю.
- Если марка кабеля меняется, в AVEVA она меняется пакетно (все проектные кабели ссылаются на каталог).

**Аргументы за ограничение Register «логической» моделью:**
- Register — учётная система, а не детальный проект. Выбор марки/типоразмера — задача стадии «Detailed Design», которую выполняет Generator.
- «Прото-кабель» (набор жил) в Register достаточен для учёта и построения перечня; физические свойства выбираются позже.
- Это упрощает Register и соответствует стадийности проектирования (Basic/Conceptual → Detailed).

### 7.2. Практика

В профессиональных САПР существует подход **«логический → физический»**: на раннем этапе работают с логическим кабелем (набор соединений, жил, маршрутов), на позднем — сопоставляют ему физический (конкретную марку, тип, диаметр). В Dassault 3DEXPERIENCE для этого есть специальный инструмент «Logical to Physical Assistant».

В управлении EPC-проектами кабельный журнал (Cable Schedule) на стадии Basic/Conceptual содержит «откуда», «куда», предварительное количество жил, но **конкретная марка и физические свойства ещё не выбраны**. Окончательный выбор кабеля (Cable Selection) происходит на стадии Detailed Design с учётом типа сигнала, экранирования, целостности сигнала, сегрегации.

### 7.3. Приоритетное направление (для обсуждения в управляющем чате)

Представляется, что для лёгкого Register **приоритетным является «логическая» модель кабеля**:

- **Register хранит:** индекс, «откуда», «куда» (точка или подсистема), привязку к сигналам (для подсчёта жил). Это «прото-кабель» — набор жил.
- **Register не хранит:** марку, типоразмер, экран, броню, огнестойкость, длину. Это «физический» кабель — зона ответственности Generator.
- **Register вычисляет:** количество занятых жил (по правилам, см. раздел 9) и может выдавать предупреждение, что окончательный выбор кабеля — следующий этап.

### 7.4. Важный нюанс из практики

Практика предупреждает: **нельзя выбирать кабель только по количеству жил**. В EPC-примере инженер выбрал кабели, просто посчитав нужное число жил, но ведущий инженер отклонил выбор, потому что не были проверены характеристики сигналов (тип, искробезопасность, экранирование) и философия проекта (сегрегация).

Для Register это означает: подсчёт жил — **полезная функция**, но она должна сопровождаться предупреждением, что окончательный выбор кабеля (с учётом экрана, брони, огнестойкости и т.д.) остаётся за Generator.

## 8. Обсуждение жил, экранов и брони

### 8.1. Контекст обсуждения

При обсуждении полей кабеля и связи «кабель ↔ сигнал» рассматривался вопрос: нужно ли хранить в KIP Register номера жил и их привязку к конкретным сигналам, или достаточно вычислять занятость жил из состава сигналов.

Отдельно уточнено, что **число жил на сигнал не является постоянным**. По инженерной практике:

- **4–20 мА** — обычно 2 жилы;
- **дискретный сигнал** — 2 жилы, но в практике гражданского строительства встречается 1 жила + общая обратная;
- **термопара** — 2 жилы;
- **термосопротивление (RTD, Pt100)** — 2, 3 или 4 жилы в зависимости от схемы подключения (2-, 3-, 4-проводная).

Поэтому модель должна допускать переменное число жил на сигнал, а не фиксировать «2».

### 8.2. Рассмотренные варианты

**Вариант A. Хранить номера жил и привязку к сигналам** (отдельная сущность «жила» или поля `core_start`/`core_end` в связи).
- Даёт точность: видно, какая жила занята каким сигналом.
- Позволяет учитывать нестандартные раскладки (1 жила + общая, резервные жилы).
- Но требует ручной работы инженера и усложняет структуру (дополнительная сущность или поля).
- В практике тяжёлых САПР (AVEVA, кабельные журналы) жилы действительно моделируются отдельно — но там это нужно для монтажных схем и генерации документов.

**Вариант B. Не хранить номера жил; хранить только число жил у сигнала и общее число жил у кабеля; занятость вычислять.**
- Структура проще: нет отдельной сущности «жила», нет полей в связи «кабель ↔ сигнал».
- Меньше ручной работы инженера.
- Контроль переполнения возможен: занятые жилы = сумма жил по привязанным сигналам; свободные = общее число жил минус занятые.
- Ограничение: нельзя ответить на вопрос «какая именно жила занята сигналом X» — только «сколько жил занято».

**Вариант C. Гибрид:** вариант B по умолчанию, но с необязательными полями для номеров жил, если инженер захочет указать.
- Даёт гибкость, но добавляет поля и потенциальную путаницу («почему у одного кабеля жилы указаны, а у другого нет»).

### 8.3. Приоритетное направление (для обсуждения в управляющем чате)

Представляется, что для KIP Register **приоритетным является Вариант B**: не хранить номера жил, а хранить только **число жил у сигнала** (1–4, по умолчанию 2, см. раздел 9) и **общее число жил у кабеля** (если оно известно из каталога). Номера жил и их раскладка — задача **KIP Generator** (будущая утилита, которая строит схемы соединений), а не учётной системы Register.

При этом вариант A не отвергается полностью: если по результатам эксплуатации выяснится, что Register должен уметь отвечать на вопрос «какие жилы свободны», можно добавить необязательные поля `core_start`/`core_end` в связь «кабель ↔ сигнал» без изменения остальной модели.

### 8.4. Экран и броня: вариант вычисления

Обсуждение показало, что экран и броня — это свойства **кабеля**, а не точки подключения. В практике экран часто заземляют только со стороны шкафа, а броню подключают разными способами (клемма заземления, шина, кабельный ввод). Для Register (в «логической» модели) экран и броня **не хранятся** — это «физические» свойства, зона ответственности Generator.

Если будет принято решение хранить их в Register (для контроля количества кабелей с экраном/бронёй в точке подключения), то достаточно:
- хранить у кабеля признаки `экран` (`нет` / `общий` / `индивидуальный`) и `броня` (`да` / `нет`);
- не хранить место заземления (это проектное решение, которое определит Generator);
- вычислять для точки подключения количество кабелей с общим экраном, с индивидуальными экранами, с бронёй — запросом.

Это соответствует подходу «ёмкость точки — производная величина»: не хранить в справочнике «Куда» отдельные поля ёмкости, а считать их из фактически приходящих кабелей.

### 8.5. Риски и условия пересмотра (по жилам)

- **Нет привязки к конкретным жилам.** Если в эксплуатации понадобится отчёт «какие жилы свободны» или «какая жила занята сигналом», вернуться к варианту A или C и добавить необязательные поля в связь «кабель ↔ сигнал».
- **Переменное число жил (1–4).** Модель должна допускать 1–4 жилы на сигнал; жёсткое «2» не подходит из-за термосопротивлений (3/4 жилы) и дискретных с общей обратной (1 жила).
- **Generator.** Если Generator потребует от Register данных о жилах, их можно добавить в **формат выгрузки**, не меняя модель (например, отдельной таблицей в выгрузке).

## 9. Расчёт числа жил по типу и электрической характеристике сигнала

### 9.1. Контекст обсуждения

Рассматривался вопрос: можно ли учитывать электрическую характеристику и тип сигнала при подсчёте жил, не утяжеляя модель данных.

### 9.2. Что уже есть в модели

В ADR-004 у сигнала уже есть два нужных атрибута:

- **Тип сигнала** (Уровень 2): `AI`, `AO`, `DI`, `DO`. Задаётся в составе сигналов на уровне проекта.
- **Электрическая характеристика** (Уровень 3): `I420` (4–20 мА), `HART`, `DRY_NO`, `DRY_NC`, `NAMUR`, `D24` и т.д. Переопределяется для каждого экземпляра сигнала.

Этого достаточно, чтобы **вычислять** число жил, не добавляя новых полей в модель.

### 9.3. Предлагаемый справочник правил

**`signal_core_rules`** — справочник соответствий «тип + характеристика → число жил». Пример содержимого:

| `signal_type` | `characteristic` | `cores` | Примечание |
|---|---|---|---|
| `AI` | `I420` | 2 | Аналоговый 4–20 мА |
| `AI` | `HART` | 2 | 4–20 мА + HART |
| `AO` | `I420` | 2 | Аналоговый выход |
| `DI` | `DRY_NO` | 2 | Сухой контакт (типовой случай) |
| `DI` | `DRY_NO` | 1 | Сухой контакт + общая обратная (вариант) |
| `DI` | `NAMUR` | 2 | NAMUR |
| `DO` | `D24` | 2 | Дискретный 24 В |
| `AI` | `RTD_3W` | 3 | Термосопротивление, 3-проводная схема |
| `AI` | `RTD_4W` | 4 | Термосопротивление, 4-проводная схема |

**Примечание:** для `DI/DRY_NO` в таблице два варианта (1 и 2 жилы). Выбор — за проектом (задаётся в проектном стандарте или явно при привязке сигнала к кабелю). Либо можно ввести два разных кода характеристики (`DRY_NO_2W`, `DRY_NO_1W`), чтобы не было неоднозначности.

### 9.4. Как это работает при подсчёте

Для кабеля:
- занятые жилы = `SUM(cores)` по всем сигналам, привязанным к кабелю, через `signal_core_rules`.

Для точки подключения:
- занятые жилы = `SUM(cores)` по всем кабелям, приходящим в точку.

Справочник `signal_core_rules` — одна небольшая таблица, она **не меняет структуру модели** и не добавляет полей в `instruments` или `signals`. Дополняется ответственным при настройке проекта (как и другие справочники).

### 9.5. Ограничения и предупреждение

- **Расчёт — «логический»:** Register считает **ожидаемое** число жил (2 для 4–20 мА, 3 для 3-проводного RTD и т.д.), но окончательный выбор кабеля (с учётом экрана, брони, огнестойкости) — за Generator.
- **Практика предупреждает:** выбор кабеля только по числу жил — ошибка. Поэтому при выводе перечня кабелей Register должен показывать предупреждение: «Число жил рассчитано. Окончательный выбор кабеля (марка, экран, броня) — на этапе Generator».
- **Неоднозначности:** если для одного и того же типа и характеристики возможно разное число жил (например, `DRY_NO` — 1 или 2), нужно либо задавать это явно при привязке сигнала, либо ввести отдельные коды характеристик.

## 10. Риски и условия пересмотра (общие)

| Риск | Мера |
|---|---|
| **Сигнал из одного прибора попал в кабель другого прибора** (ошибка ввода) | Проверка на уровне приложения: `signal.instrument_id == cable.from_instrument_id`. При импорте — ошибка строки. |
| **Изменение прибора в «откуда» после того, как сигналы уже привязаны к кабелю** | При смене `from_instrument_id` — проверить, что все привязанные сигналы принадлежат новому прибору; иначе — ошибка/предупреждение. |
| **Неоднозначность правил числа жил** (например, `DRY_NO` — 1 или 2) | Задавать явно при привязке сигнала или ввести отдельные коды характеристик. |
| **Ошибочное мнение «жил хватает → кабель подходит»** | Предупреждение в перечне: окончательный выбор — за Generator. |
| **Кабель без `to_point_id` (только подсистема)** | На раннем этапе допустимо; на стадии детализации инженер заменяет подсистему на точку, аудит фиксирует уточнение. |
| **Клеммные коробки как отдельная сущность** | Рассматривались варианты (отдельные справочники / один справочник с типом / шкаф как прибор). Приоритетным представляется один справочник с типом. |
| **Импорт кабелей из Excel** | Маппинг по правилам ADR-006; `cable.index` — ключ идемпотентности `(project_id, index)`. |
| **Перечень кабелей для Generator** | Формат выгрузки фиксируется (колонки: индекс, откуда, куда, сигналы, жил занято). Generator забирает его как табличный файл; прямых API нет. |

**Условия пересмотра:**

- Если появятся **клеммные коробки** как отдельная сущность с особым поведением — расширить модель (новый ADR).
- Если один кабель всё же должен обслуживать **несколько приборов** — вернуться к обсуждению.
- Если Generator потребует **дополнительных полей** в перечне кабелей (например, длину кабеля, способ прокладки) — расширить `cables` или формат выгрузки.
- Если понадобится **отчёт по конкретным жилам** — добавить необязательные поля `core_start`/`core_end` в связь «кабель ↔ сигнал».
- Если понадобится **хранить физические свойства кабеля** в Register (марка, экран, броня) — добавить их в `cables` и справочник кабелей (новый ADR).
- Если на практике окажется, что **для большинства кабелей точка подключения известна сразу** (например, при импорте из детального проекта) — вернуть обязательность `to_point_id` для этих случаев.

## 11. Резюме для управляющего чата (для возможного ADR-007)

> Это резюме — для принятия решения в управляющем чате. Здесь нет «принятых решений», а есть результаты исследования: что обсуждалось, какие варианты рассматривались, какие представляются приоритетными.

### 11.1. Проблема

Текущая модель (ADR-004) не позволяет вывести перечень кабелей с составом сигналов: кабель привязан к прибору целиком, а не к конкретным сигналам.

### 11.2. Что обсуждалось

1. **Кабель как сущность** — вынесение кабеля в отдельную таблицу проекта (индекс, «откуда», «куда»). Рассматривались варианты: привязать кабель к прибору целиком (как в ADR-004) vs вынести в отдельную сущность. Приоритетным представляется вынесение — это даёт возможность строить перечень кабелей и избежать дублирования.

2. **«Логический» vs «физический» кабель** — рассматривалось, хранить ли в Register физические свойства кабеля (марка, типоразмер, экран, броня, огнестойкость) или ограничиться «логическими» атрибутами (откуда, куда, индекс, привязка к сигналам). Приоритетным представляется **«логическая» модель**: Register — учётная система, выбор кабеля — задача Generator. Это соответствует стадийности проектирования (Basic/Conceptual → Detailed) и практике «Logical to Physical Assistant» в Dassault 3DEXPERIENCE.

3. **Точки подключения («Куда» и «Откуда»)** — рассматривались три варианта: отдельные справочники для шкафов/коробок/панелей; один справочник с типом; шкаф как тип прибора. Приоритетным представляется **один справочник с типом** (`шкаф` / `клеммная коробка` / `панель`), поля: тип, обозначение, проект.

4. **Подсистема вместо точки подключения на раннем этапе** — рассматривались три варианта: оставить `to_point_id` обязательным; сделать необязательным и использовать подсистему; убрать справочник точек полностью. Приоритетным представляется **второй вариант**: `to_point_id` необязателен, на раннем этапе указывается подсистема (из существующего справочника `control_systems`, уже есть на уровне сигнала). Справочник точек подключения остаётся и заполняется по мере детализации. Отдельный справочник подсистем для кабелей не создаётся.

5. **Ёмкость точки подключения** — рассматривались варианты: хранить в справочнике (поля «ёмкость жильных клемм», «ёмкость клемм экранов», «ёмкость клемм брони») vs вычислять из кабелей, приходящих в точку. Приоритетным представляется **вычисление** — ёмкость производна от количества кабелей и жил, хранение в справочнике создаёт риск расхождения.

6. **Связь «кабель ↔ сигнал»** — рассматривалась привязка к жилам (номера жил) vs без привязки (только список сигналов). Приоритетным представляется **без номеров жил** — Register остаётся учётной системой, номера жил и раскладка переносятся на этап Generator.

7. **Жилы, экраны, броня** — обсуждались три варианта: (A) хранить номера жил и привязку к сигналам; (B) хранить только число жил у сигнала (1–4) и общее число жил у кабеля, занятость вычислять; (C) гибрид. **Приоритетным представляется вариант B**. Число жил на сигнал переменное: 2 для 4–20 мА и термопар, 3–4 для термосопротивлений (RTD), 1 — для дискретных с общей обратной. Экран и броня в «логической» модели не хранятся — это физические свойства, зона ответственности Generator.

8. **Расчёт числа жил по типу и характеристике сигнала** — обсуждалась возможность учитывать тип сигнала (`AI`, `AO`, `DI`, `DO`) и электрическую характеристику (`I420`, `HART`, `DRY_NO`, `NAMUR`, `RTD_3W`, …) при подсчёте жил. Модель **не утяжеляется**: используются существующие поля ADR-004; добавляется справочник `signal_core_rules` («тип + характеристика → число жил»), который дополняется ответственным. Предупреждение: окончательный выбор кабеля — за Generator.

9. **Корректировка ADR-006 (пункт 7)** — в ADR-006 было записано: «индекс кабеля — справочная строка с проверкой на дубликаты, но без жёсткой уникальности». По итогам обсуждения: кабель **имеет две точки** и не подключается к двум приборам; индекс кабеля **уникален в рамках проекта**; «откуда» и «куда» — ссылки на прибор, точку подключения или подсистему (на раннем этапе).

10. **Экосистема утилит** — прямых API между Reader, Register и Generator нет; обмен — табличными файлами. Перечень кабелей — один из выходных форматов Register для будущего Generator.

### 11.3. Приоритетные варианты (для обсуждения)

| Вопрос | Приоритетный вариант | Условие пересмотра |
|---|---|---|
| Кабель как сущность | Отдельная таблица `cables` | — |
| «Логический» vs «физический» кабель | «Логический» в Register; «физический» в Generator | Если понадобится хранить марку/экран/броню в Register |
| Точки подключения | Один справочник с типом | Если появятся типы с особым поведением |
| «Куда» на раннем этапе | Необязателен; можно указать подсистему (`control_systems`) | Если окажется, что точка обычно известна сразу — вернуть обязательность |
| Ёмкость точки | Вычислять из кабелей | Если понадобится паспортная ёмкость — опциональное поле |
| Жилы | Вариант B (без номеров жил) | Если понадобится отчёт по жилам — `core_start`/`core_end` |
| Расчёт жил по типу/характеристике | Справочник `signal_core_rules` | Если появятся новые типы/характеристики |
| Экран/броня | Не хранить в Register (зона Generator) | Если понадобится — признаки у кабеля |
| Индекс кабеля | Уникален в рамках проекта | — |
| «Откуда»/«Куда» | Ссылки на прибор, точку подключения или подсистему | — |

### 11.4. Главный риск и мера

- **Риск:** сигнал из одного прибора попал в кабель другого прибора (ошибка ввода или импорта).
- **Мера:** проверка на уровне приложения `signal.instrument_id == cable.from_instrument_id`; при импорте — ошибка строки.

## 12. Источники

1. ГОСТ 21.613-2014 — правила выполнения кабельных журналов (графы «Начало»/«Конец», марка, типоразмер).
2. Практика кабельных журналов в электротехнических САПР (EPLAN, AutoCAD Electrical) — кабель как сущность с двумя точками.
3. AVEVA Instrumentation — Cable Catalog, Project Cable, `CABCOR` (моделирование жил), `marshalling cabinet card slot`.
4. CADWorx — кабели и lookup-данные, «первая жила/проводник» как дочерняя запись.
5. Dassault 3DEXPERIENCE — «Logical to Physical Assistant» (логический → физический кабель).
6. Практика EPC-проектов — стадийность Basic/Conceptual → Detailed, Cable Schedule vs Cable Selection.
7. Практика ранних стадий: на предварительном проектировании в графе «To» кабельного журнала часто указывают подсистему или тип панели (например, «Marshalling panel», «DCS»), а конкретный шкаф появляется позже.
8. ADR-004 (трёхуровневая модель) — границы модели, место кабеля вне трёх уровней, существующие поля `signal_type`, `characteristic`, `control_systems`.
9. ADR-006 (импорт) — правила маппинга и идемпотентности, применяемые к кабелям.
10. Практика выбора кабеля по типу сигнала: 4–20 мА — 2 жилы + экран; дискретный — 2 жилы, экран при длине > 50 м; цифровой (RS-485) — витая пара + экран.
11. Практика RTD: 2-, 3-, 4-проводные схемы (3C/4C для Pt100); термопара — 2C.
12. Практика экранов: «shield wires shall be terminated on separate terminal blocks»; заземление экрана со стороны шкафа.
13. Практика брони: подключение к клемме заземления, шине или кабельному вводу.
14. Обсуждения кабельных журналов в инженерных сообществах (кабель «откуда/куда», состав сигналов, резерв жил 10–20%).
15. Практика предупреждения об ошибке выбора кабеля только по числу жил (EPC-пример: отклонение выбора из-за непроверенных характеристик сигналов и сегрегации).
